# Section 2: LangChain 核心组件 — 生产级高频面试题

---

## Q1: LangChain 的核心价值是什么？为什么不用原生 API 直接调用 LLM？

**答：**
原生 API 可以调 LLM，但 LangChain 解决的是**工程化问题**：
1. **统一接口**：换模型（OpenAI -> Claude -> 本地模型）只需改一行配置
2. **组件化**：Prompt、LLM、Parser、Retriever 可自由组合
3. **链式编排**：LCEL 让多步处理像搭积木
4. **生态**：内置 700+ 集成（向量库、文档加载器、工具等）

类比：你完全可以用原生 SQL 操作数据库，但 ORM（SQLAlchemy）让开发效率提升 10 倍。

## Q2: PromptTemplate 和 ChatPromptTemplate 有什么区别？

**答：**

| 维度 | PromptTemplate | ChatPromptTemplate |
|------|---------------|-------------------|
| 输出格式 | 纯文本字符串 | 消息列表（Message 对象） |
| 适用模型 | text completion（GPT-3） | chat model（GPT-4、Claude） |
| 角色支持 | 无 | system / human / ai |
| Few-Shot | 不方便 | 原生支持 |

```python
# PromptTemplate 输出：str
"你是一个AI专家，解释RAG"

# ChatPromptTemplate 输出：list[Message]
[SystemMessage("你是一个AI专家"), HumanMessage("解释RAG")]
```

**生产建议**：99% 的场景用 ChatPromptTemplate，text completion 模型已逐步淘汰。

## Q3: Output Parser 的 format_instructions 为什么必须注入 prompt？

**答：**
LLM 没有"内置"的输出格式概念——它只是预测下一个 token。如果不告诉它"请输出 JSON"，它就输出自然语言。

```python
# 错误：没注入格式指令
prompt = ChatPromptTemplate.from_messages([
    ("system", "分析用户情感"),
    ("human", "{text}"),
])
# LLM 输出："这句话表达了积极的情感"  <- Parser 无法解析

# 正确：注入格式指令
parser = PydanticOutputParser(pydantic_object=Sentiment)
prompt = ChatPromptTemplate.from_messages([
    ("system", f"分析用户情感。{parser.get_format_instructions()}"),
    ("human", "{text}"),
])
# LLM 输出：{"label": "positive", "score": 0.9}  <- Parser 正确解析
```

**本质**：format_instructions 是"告诉 LLM 输出格式的 prompt 工程"，不是代码层面的约束。

## Q4: PydanticOutputParser 比 JsonOutputParser 好在哪？

**答：**

| 维度 | JsonOutputParser | PydanticOutputParser |
|------|-----------------|---------------------|
| 类型校验 | 无（dict 啥都能放） | 严格（字段类型、范围、必填） |
| 错误发现 | 运行时才发现字段错了 | 解析时立即报错 |
| 文档生成 | 无 schema 信息 | 自动生成 JSON Schema 注入 prompt |
| IDE 支持 | dict 无补全 | BaseModel 有完整补全 |

```python
# JsonOutputParser：可能拿到 {"rating": "很高"} <- 类型错误但不报错
# PydanticOutputParser：rating: float 会校验，"很高"直接报错
```

**生产建议**：对外接口一律用 PydanticOutputParser，内部快速原型可用 JsonOutputParser。

## Q5: LCEL 的 `|` 管道符背后做了什么？

**答：**
`|` 是运算符重载，创建了一个 `RunnableSequence` 对象：

```python
chain = prompt | llm | parser
# 等价于：
chain = RunnableSequence(first=prompt, middle=[llm], last=parser)

# 调用 chain.invoke(input) 时：
result = parser.invoke(
    llm.invoke(
        prompt.invoke(input)
    )
)
```

每个节点都实现 `Runnable` 接口（invoke/batch/stream），管道自动处理数据流转。

## Q6: 如何在 LangChain 中实现流式输出（Streaming）？

**答：**
LCEL 链原生支持 `.stream()`：

```python
chain = prompt | llm | StrOutputParser()

# 非流式：等全部生成完再返回
result = chain.invoke({"question": "什么是RAG"})

# 流式：token 逐个返回，前端实时显示
for chunk in chain.stream({"question": "什么是RAG"}):
    print(chunk, end="", flush=True)
```

生产价值：LLM 生成 1000 个 token 可能需要 10 秒，流式输出让用户第 1 秒就看到内容，体感延迟从 10s 降到 <1s。

## Q7: LangChain 的版本迭代很快，如何避免代码过时？

**答：**
1. 锁定版本：`langchain==0.2.x`，不要用 `latest`
2. 优先用 `langchain-core`（稳定，变化小），而非 `langchain`（大包，变化快）
3. LCEL 是官方推荐的稳定范式，优先用 LCEL 而非旧的 `LLMChain` 类
4. 关注官方迁移指南：https://python.langchain.com/docs/versions/v02/

## Q8: RunnableLambda 是什么？什么时候用？

**答：**
RunnableLambda 把任意 Python 函数包装成 LCEL 组件，让它能用 `|` 管道串联：

```python
from langchain_core.runnables import RunnableLambda

def my_custom_logic(input_str: str) -> str:
    # 自定义处理逻辑（数据库查询、API调用、数据清洗等）
    return input_str.upper()

# 包装成 Runnable，可以接入 LCEL 链
custom_step = RunnableLambda(my_custom_logic)

chain = prompt | llm | custom_step | parser
```

使用场景：链中需要插入自定义逻辑（非 LLM 调用、非标准组件）时。
