# Section 4: Embedding 原理与本地向量库 — 生产级高频面试题

---

## Q1: Embedding 和 One-Hot 编码有什么区别？

**答：**
- One-Hot：稀疏高维（词表大小），每个词独立，无法表示语义相似度
- Embedding：稠密低维（128~2048），语义相似的词向量距离近

```
One-Hot: "猫"=[1,0,0,...], "狗"=[0,1,0,...]  相似度=0
Embedding: "猫"=[0.2,0.8,...], "狗"=[0.21,0.79,...]  相似度=0.99
```

---

## Q2: 为什么 RAG 用余弦相似度而不是欧氏距离？

**答：**
余弦相似度衡量**方向**，欧氏距离衡量**绝对位置**。

- 文本长度不同会导致向量模长不同，但语义方向一致
- 余弦相似度不受向量长度影响，只看方向
- 欧氏距离会被长文本的"大数值"干扰

生产中两者都可用，但 RAG 场景余弦相似度更普遍。

## Q3: Chroma、Milvus、Pinecone 有什么区别？

**答：**

| 维度 | Chroma | Milvus | Pinecone |
|------|--------|--------|----------|
| 部署 | 本地嵌入式 | Docker/K8s | 云托管 |
| 适用 | 开发/原型 | 生产级 | 生产级 |
| 规模 | 百万级 | 十亿级 | 十亿级 |
| 索引 | HNSW | HNSW/IVF/DiskANN | 专有 |

课程路线：第1周 Chroma（原型） -> 第2周 Milvus（生产）。

## Q4: chunk_size 和 Embedding 质量有什么关系？

**答：**
chunk_size 决定每个向量"代表"多少文本：
- 太小（<100字符）：向量只编码碎片信息，检索到的内容不完整
- 太大（>1000字符）：向量编码太多信息，语义被稀释，检索精度下降
- 适中（200~500字符）：向量能准确编码一个语义单元

经验值：先从 500 开始，根据检索效果逐步调优。

## Q5: 如何评估 Embedding 模型的好坏？

**答：**
1. **语义相似度**：同义句的相似度是否高（>0.8）
2. **检索准确率**：用标准问答对测试，Top-K 是否包含正确答案
3. **多语言支持**：中文场景需要支持中文的模型（如 bge 系列）
4. **维度/速度**：维度越高越精准但越慢，需要权衡

MTEB 排行榜（https://huggingface.co/spaces/mteb/leaderboard）是评估 Embedding 模型的标准基准。

## Q6: 向量数据库的索引原理是什么？为什么比暴力搜索快？

**答：**
暴力搜索：遍历所有向量，O(n) 复杂度。

向量索引（如 HNSW）：
- 构建时：把向量组织成多层图结构
- 查询时：从顶层开始，逐层向下找最近邻，O(log n)
- 代价：近似搜索，可能漏掉少量最近邻（召回率 95%~99%）

```
暴力搜索：遍历 100万 个向量 -> 100ms
HNSW索引：图搜索 100万 个向量 -> 1ms
```

## Q7: Embedding 向量的维度越高越好吗？

**答：**
不是。维度越高：
- 优点：表达能力更强，语义区分更细
- 缺点：存储更大、计算更慢、高维空间可能出现"维度灾难"

| 维度 | 适用场景 |
|------|----------|
| 128~384 | 轻量/实时场景 |
| 512~768 | 通用 RAG |
| 1536~2048 | 高精度/多语言 |

选择标准：在精度和性能之间找平衡点。
