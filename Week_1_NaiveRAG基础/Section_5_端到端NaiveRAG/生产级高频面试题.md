# Section 5: 端到端 Naive RAG 生产级高频面试题

## 基础题

### Q1: 描述 RAG 系统的完整数据流
**答：** 两个阶段：
- **索引阶段**：原始文档 → 分块（RecursiveCharacterTextSplitter）→ Embedding → 存入向量库（FAISS/Milvus）
- **查询阶段**：用户提问 → Embedding → 向量检索 Top-K → 拼接 Prompt（问题+检索结果）→ LLM 生成回答

### Q2: 为什么 RAG 的 Prompt 要加"只根据参考资料回答"？
**答：** 限制 LLM 只基于检索到的文档内容生成回答，不编造信息。如果不加这个约束，LLM 可能用自己的知识补充内容，导致回答与知识库不一致（幻觉）。temperature 设低（0.3）也是为了减少随机性。

### Q3: chunk_size 和 chunk_overlap 怎么选？
**答：**
- `chunk_size`：太大（>500）→ 检索不精确，噪声多；太小（<100）→ 语义不完整，上下文丢失。一般 200-500。
- `overlap`：防止句子被块边界切断，一般 10%-20% 的 chunk_size。
- 没有万能值，需要根据文档类型和检索效果调优。

### Q4: top_k 取 3 还是 5 还是 10？
**答：** 取决于 LLM 的上下文窗口和文档质量。
- 太小（1-2）→ 可能遗漏关键信息
- 太大（>10）→ 引入大量噪声，且占用 token
- 一般 3-5 是常用起点，需要通过评估实验确定最优值

## 进阶题

### Q5: Naive RAG 有哪些局限？生产中怎么解决？
**答：**
| 局限 | 解决方案 |
|------|---------|
| 分块切断语义 | 语义分块、父子文档策略 |
| 向量检索漏关键词 | 混合检索（向量 + BM25） |
| 检索结果质量参差 | Rerank 重排（Cohere/BGE Reranker） |
| Embedding 语义弱 | 换真实模型（OpenAI/BGE） |
| 向量库不支持分布式 | 换 Milvus（生产级） |

### Q6: LCEL 链中 `RunnablePassthrough` 的作用是什么？
**答：** `RunnablePassthrough()` 把输入原样传递给下一步。在 RAG 链中，用户的问题需要同时走两条路：
- 路径1：question → 检索 → 格式化为 context
- 路径2：question → 原样传递给 prompt 的 `{question}` 占位符
`RunnablePassthrough` 负责路径2，保证问题不被检索逻辑吞掉。

### Q7: 为什么 RAG 用 ChatPromptTemplate 而不是 PromptTemplate？
**答：** ChatPromptTemplate 支持多角色消息（system/human/ai），适合聊天模型（GPT-4、GLM）。RAG 需要 system 设定角色和参考资料，human 提问，这是标准的多轮对话格式。PromptTemplate 只适合纯文本补全模型。

## 场景题

### Q8: 用户上传了 1000 个 PDF，怎么设计 RAG 系统？
**答：**
1. **文档解析**：用 Unstructured/MinerU 解析 PDF（表格、图片）
2. **分块**：RecursiveCharacterTextSplitter 或语义分块
3. **Embedding**：批量调用 API（OpenAI/BGE），注意限流
4. **向量库**：Milvus（支持分布式、十亿级向量）
5. **检索**：混合检索（向量+BM25）+ Rerank
6. **增量更新**：新文档只处理新增部分，不重建全量索引
注：【增量更新会做：
旧的 1000 份完全不动！
只处理新的这 1 份：解析 → 分块 → Embedding → 存入向量库
结束！】

### Q9: RAG 系统回答质量差，怎么排查？
**答：** 按链路逐级排查：
1. **检索质量**：检查 Top-K 文档是否确实包含答案 → 换 Embedding/加 BM25
2. **分块质量**：答案是否被切断在两个块里 → 调 chunk_size/overlap
3. **Prompt 质量**：约束是否足够清晰 → 优化 system prompt
4. **LLM 能力**：模型是否足够强 → 升级模型
5. **用 RAGAs/DeepEval 量化评估**（第2周学）
