# pgvector 向量扩展 — 生产级高频面试题

---

## Q1：pgvector 是什么？和 Milvus / FAISS 有什么区别？

**答：** pgvector 是 PostgreSQL 的向量扩展，让 PG 原生支持 embedding 存储和相似度检索。

| 对比维度 | pgvector | Milvus | FAISS |
|----------|----------|--------|-------|
| 部署 | PG 自带扩展 | 独立 Docker 服务 | Python 库 |
| 事务 | ACID 保证 | 无 | 无 |
| 混合检索 | SQL WHERE + 向量，原生支持 | 需配置 | 需自行拼接 |
| 扩展性 | PG 分区/读副本 | 分布式分片 | 单机 |
| 适用 | 已有 PG 的项目 | 大规模独立向量库 | 研究/原型 |

**核心差异：** pgvector 让向量数据和业务数据在同一个事务里管理，减少架构复杂度。

## Q2：IVFFlat 和 HNSW 索引的原理区别？怎么选？

**答：**

**IVFFlat（倒排文件平坦索引）：**
- 原理：K-Means 将向量聚类为 N 个桶，查询时只搜索最近的几个桶
- 优点：构建快、内存低
- 缺点：近似搜索，精度不如 HNSW
- 参数：`lists`（聚类数），建议 rows/1000

**HNSW（分层可导航小世界图）：**
- 原理：构建多层图，高层稀疏（快速跳转）、底层密集（精确搜索），类似"高速公路→主干道→小巷"的导航
- 优点：查询精度高、速度快
- 缺点：构建慢、内存大
- 参数：`m`（邻居数，默认 16）、`ef_construction`（构建深度，默认 64）

**选择：** 生产环境首选 HNSW；数据量 <10 万且对精度要求不高可用 IVFFlat。

## Q3：pgvector 支持哪些距离度量？各适合什么场景？

**答：** 三种距离算子：

```sql
embedding <=> :q   -- Cosine Distance：[0,2]，越小越相似，适合语义搜索
embedding <-> :q   -- L2 Distance：[0,∞)，越小越相似，适合绝对位置敏感
embedding <#> :q   -- Inner Product：(-∞,∞)，越小越相似，需归一化
```

- **余弦距离**：最常用，只看方向不看大小，语义搜索首选
- **L2 距离**：绝对距离，向量模长敏感（如图像特征）
- **内积**：需归一化后等价余弦，某些模型（如 OpenAI）直接输出归一化向量时使用

## Q4：什么是混合检索？RRF 融合怎么算？

**答：**

**混合检索 = 全文检索 + 向量检索 + 融合排序**

- **全文检索**：精确匹配关键词（"数据库" → 包含"数据库"的文档），用 PG 内置 tsvector/tsquery
- **向量检索**：语义相似度（"数据存储" ≈ "数据库"），用 pgvector 距离算子
- **融合**：RRF（Reciprocal Rank Fusion）综合排名

**RRF 公式：**
```
RRF(doc) = Σ 1/(k + rank_i(doc))
```
- `k = 60`（平滑常数，防止排名为 0 爆炸）
- `rank_i(doc)` = 文档在第 i 个检索源中的排名

**为什么不用分数直接相加？** 全文检索分数和向量检索分数的量纲不同（一个是 BM25 分，一个是余弦距离），不能直接比较。RRF 只依赖排名，完美解决异构分数融合。

## Q5：如何用 pgvector 实现端到端 RAG？画流程。

**答：**

```
1. 文档加载 → 分块（RecursiveCharacterTextSplitter）
   "长文档.pdf" → ["chunk1", "chunk2", ...]
   
2. Embedding → 向量化
   "chunk1" → [0.045, -0.076, ...]（512维）
   
3. 存入 pgvector
   INSERT INTO docs (content, embedding) VALUES (...)
   
4. 用户查询 → 向量化
   "什么是 HNSW？" → query_emb
   
5. 向量检索 Top-K
   SELECT content FROM docs ORDER BY embedding <=> query_emb LIMIT 3
   
6. 构造 Prompt = 系统指令 + 检索到的文档片段 + 用户问题
   
7. 调用 LLM 生成回答
```

**关键点：** RAG 的核心是"检索增强"——LLM 基于检索到的外部知识回答，而非依赖训练时的记忆，大幅减少幻觉。

## Q6：pgvector 做 RAG 比 FAISS/Chroma 强在哪？

**答：**

1. **ACID 事务**：向量数据和业务数据在同一事务中，不会出现"插入了订单但向量没存上"的问题
2. **原生混合检索**：SQL 的 `WHERE` 可以直接过滤向量检索结果（如"只搜 2024 年的文档"），FAISS 需要额外逻辑
3. **运维简单**：不需要额外服务，PG 已有的备份/主从/监控直接复用
4. **元数据管理**：向量 + 标题 + 作者 + 时间等元数据在同一行，一条 SQL 搞定

**劣势：** 纯向量检索性能不如 FAISS（C++ 优化），超大规模（亿级）建议 Milvus。

## Q7：pgvector 向量列建表时需要注意什么？

**答：**

1. **维度固定**：`Vector(512)` 建表后不能改，切换模型（如 512→1536）需要 ALTER TABLE + 重建数据
2. **索引不是免费的**：HNSW 索引构建耗内存，约 5000 条数据索引大小 = 几十 MB
3. **批量插入优于逐条**：单条 `INSERT` 每条都触发 WAL，批量写入性能高 10x+
4. **必须配合 EXPLAIN ANALYZE**：确认查询走了索引（Index Scan），而不是全表扫描（Seq Scan）
