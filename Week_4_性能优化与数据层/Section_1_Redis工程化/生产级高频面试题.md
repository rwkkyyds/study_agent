# Section 1 生产级高频面试题：Redis 工程化

---

## Q1: Cache-Aside 模式的读写流程是什么？

**答：**
- **读**：先查 Redis → 命中直接返回 → 未命中查 DB → 写入 Redis（带 TTL）→ 返回
- **写**：先更新 DB → 再删除 Redis 缓存（非更新）

为什么删除而非更新缓存？并发场景下更新缓存可能导致脏数据，删除后下次读自动从 DB 加载最新。

---

## Q2: 缓存穿透、击穿、雪崩有什么区别？怎么解决？

**答：**

| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 穿透 | 查询不存在的数据，缓存永远 miss | 布隆过滤器 / 缓存空值（TTL 短） |
| 击穿 | 热点 key 过期，大量请求同时打 DB | 互斥锁（setnx） / 永不过期+后台刷新 |
| 雪崩 | 大量 key 同时过期 | TTL 加随机偏移 / 多级缓存 / 限流 |

---

## Q3: 为什么用 Redis 存储 Agent 会话而不是 MemorySaver？

**答：**

| 维度 | MemorySaver | Redis |
|------|-------------|-------|
| 存储 | 内存（进程内） | 独立服务 |
| 持久化 | 进程重启丢失 | 支持 RDB/AOF 持久化 |
| 多进程 | 不支持 | 支持多进程/多服务共享 |
| 过期 | 无 | TTL 自动过期 |
| 适用 | 开发/原型 | 生产环境 |

## Q4: Redis 的 String 和 Hash 分别适合什么场景？

**答：**
- **String**：简单键值对、缓存、计数器（INCR）、分布式锁（SETNX）
- **Hash**：对象存储（用户信息、会话状态），支持字段级读写，比 JSON 序列化更高效

```python
# String：整体读写
r.set("user:001", json.dumps({"name": "张三", "role": "AI工程师"}))

# Hash：字段级读写（只改一个字段不用读整个对象）
r.hset("user:001", "role", "AI架构师")
```

## Q5: 滑动窗口限流的原理是什么？为什么比固定窗口好？

**答：**

### 固定窗口的"边界问题"（为什么会允许 2x 流量？）

**设定**：限流 10 次请求 / 分钟

```
第 1 分钟窗口（59 秒 - 60 秒）：
  59 秒：10 个请求来临 → 全部进第 1 分钟窗口 → 全部通过 ✅
  
第 2 分钟窗口（60 秒 - 61 秒）：
  60 秒：窗口切换！前 1 分钟的计数清零
  60-61 秒：10 个请求来临 → 全部进第 2 分钟窗口 → 全部通过 ✅

结果：59-61 秒这 2 秒内，20 个请求全部通过！（限制是 10 个）
```

**图示**：
```
时间轴：
59秒 ────────── 60秒 ────────── 61秒
 │第1分钟窗│窗口切换│第2分钟窗│
 10请求   │清零   │10请求
 ┗━━━━━━━┛      ┗━━━━━━━┛
  窗口1         窗口2
  
在 59-61 秒短时间内，可以通过 20 个请求！（2x 流量）
```

**为什么会发生？**
- 第 1 分钟末尾（59 秒）：计数已达上限
- 窗口切换（60 秒）：计数瞬间清零
- 第 2 分钟开始（60-61 秒）：立即可以再放 10 个请求
- **结果**：窗口边界处突然放宽了限制

### 滑动窗口的解决方案

用 Sorted Set 存储每次请求的**精确时间戳**，不以窗口为单位：

```python
# 滑动窗口核心逻辑
r.zadd(key, {request_id: timestamp})      # 添加请求（成员=UUID，分数=时间戳）
r.zremrangebyscore(key, 0, window_start)  # 清除超过 60 秒前的记录
count = r.zcard(key)                      # 统计窗口内请求数
if count > limit:
    return False  # 拒绝
```

**区别**：
```
固定窗口：
  [0-60秒) 和 [60-120秒) 是两个独立的计数器
  
滑动窗口：
  任意连续 60 秒都被统计（如 [10-70秒)、[11-71秒) 都各自计数）
  → 无边界问题
```

### 性能对比

| 方案 | 边界问题 | 实现复杂度 | Redis 开销 |
|------|---------|---------|---------|
| 固定窗口 | ❌ 有（2x 流量） | 简单（INCR） | 低 |
| 滑动窗口 | ✅ 无 | 中等（Sorted Set）| 中等（pipeline） |

**生产级建议**：除非高并发且流量波动小，否则用**滑动窗口**避免边界问题。

## Q6: Redis Pub/Sub 适合什么场景？有什么局限？

**答：**
- **适用**：实时事件通知、Agent 工具调用日志、任务分发
- **局限**：消息不持久化，订阅者离线会丢失消息

生产级方案：需要可靠消息用 Redis Streams 或 RabbitMQ。

## Q7: 如何防止 Redis 缓存和 DB 数据不一致？

**答：**
1. **Cache-Aside 写时删除缓存**（而非更新）
2. **TTL 兜底**：即使不一致，TTL 过期后自动从 DB 重新加载
3. **延迟双删**：更新 DB → 删缓存 → 延迟一段时间 → 再删一次（防并发）
4. **最终一致性**：大多数场景接受短暂不一致

## Q8: Redis 的 INCR 命令为什么是原子的？有什么用？

**答：**
Redis 单线程模型保证 INCR 是原子操作（不会出现并发竞态）。

用途：
- **计数器**：页面访问量、API 调用次数
- **限流**：固定窗口限流的核心命令
- **分布式 ID**：自增生成唯一 ID

## Q9: Redis 的 TTL 机制有什么注意事项？

**答：**
1. `SETEX` 设置 key 过期时间（秒）
2. `PTTL` 查看剩余毫秒数
3. 惰性删除：访问时才检查是否过期
4. 定期删除：后台随机抽样检查过期 key
5. **注意**：大量 key 同时设置相同 TTL 会导致雪崩，加随机偏移
