# Celery + RabbitMQ — 不理解的部分

## 已修复的问题

### 1. Python 退出时 `ImportError: sys.meta_path is None`
- **原因**：Celery 的 `AsyncResult.__del__` 在 Python 进程 shutdown 时尝试取消 Redis 订阅，但此时解释器已部分销毁
- **修复**：加 `atexit.register(lambda: None)` 强制绑定 atexit hook，延迟 shutdown 清理
- **影响**：仅终端输出噪音，不影响功能

### 2. 没有 Worker 时 .delay() 不报错但 .get() 超时
- **原因**：`.delay()` 只把消息发到 Redis（成功），但没人消费执行
- **修复**：每个 demo 开头加了 Worker 连通性检测，没 Worker 时提前报错提示
- **正确步骤**：先开 Worker，再跑 demo

### 3. Windows 上必须用 `--pool=solo`
- `celery worker --pool=solo` — Windows 不支持 fork

## 概念疑问

### 4. `smart_retry` 没设 `retry_backoff=True`，为什么能实现指数退避？

**原问题**：`demo2_celery_retry.py` 中 `smart_retry` 任务没有配置 `retry_backoff=True`，但代码里用了 `2 ** self.request.retries` 算延迟，这不也是指数退避吗？

**解释**：Celery 有两条完全不同的重试路径，都能达到指数退避效果，但机制不同。

| | 自动重试 (`call_unstable_api`) | 手动重试 (`smart_retry`) |
|---|---|---|
| 谁触发 | Celery 捕获异常后自动重试 | 程序员 `raise self.retry()` 手动触发 |
| 谁算退避 | **Celery** 按 `retry_backoff=True` 算 | **你自己** 通过 `countdown` 参数算 |
| 需要 `retry_backoff`？ | ✅ 必须 | ❌ 不需要（你已手动指定了 countdown）|

**类比**：
- `retry_backoff=True` = 打车时选"舒适型"，平台自动匹配一辆 B 级车
- `countdown=2 ** retries` = 自己选"打一辆奔驰 E 级"，手动指定了车型

两个方式最终都打到车了（指数退避），但一个是平台帮你选，一个是你自己指定。

**配套示例**：

```python
# 方式一：自动重试 + Celery 帮你算退避
@celery_app.task(
    bind=True,
    autoretry_for=(Exception,),   # 捕获这些异常自动重试
    retry_backoff=True,           # Celery 自动算：1s→2s→4s→8s
    max_retries=3,
)
def auto_backoff(self):
    raise Exception("自动重试")

# 方式二：手动重试 + 自己算退避（效果完全一样）
@celery_app.task(bind=True, max_retries=3)
def manual_backoff(self):
    if self.request.retries < 3:
        raise self.retry(countdown=2 ** self.request.retries)  # 手动算：1s→2s→4s

# 方式二的额外优势：可以按业务条件动态调整退避
@celery_app.task(bind=True, max_retries=3)
def dynamic_backoff(self, order_amount: float):
    if self.request.retries < 3:
        # 大额订单更谨慎，等更久
        wait = 10 ** self.request.retries if order_amount > 10000 else 2 ** self.request.retries
        raise self.retry(countdown=wait)
```

**易错点**：
- `retry_backoff=True` 只对 `autoretry_for` 自动重试生效，对手动 `self.retry(countdown=...)` 无影响
- 手动重试时如果不传 `countdown`，消息**立即**重回队列（无延迟），可能造成重试风暴
- `self.request.retries` 从 0 开始计数：第 1 次重试 = 0，第 2 次 = 1，第 3 次 = 2

### 5. `retry_backoff` 是系数不是底数——指数退避公式

**原问题**：`show_backoff_strategy()` 表格看不懂，`backoff=3` 列为什么是 3, 9, 27, 60？

**错误原因**：demo2 原代码把 `backoff` 当成了底数，写成了 `3^attempt`。实际上 `backoff` 是一个**系数**，底数永远是 2。

**正确公式**：`countdown = backoff × 2^retries`

| retries | backoff=1 | backoff=2 | backoff=3 |
|---------|-----------|-----------|-----------|
| 0（第1次重试） | 1×1=**1s** | 2×1=**2s** | 3×1=**3s** |
| 1（第2次重试） | 1×2=**2s** | 2×2=**4s** | 3×2=**6s** |
| 2（第3次重试） | 1×4=**4s** | 2×4=**8s** | 3×4=**12s** |
| 3（第4次重试） | 1×8=**8s** | 2×8=**16s** | 3×8=**24s** |
| 4（第5次重试） | 1×16=**16s** | 2×16=**32s** | 3×16=**48s** |

**修复**：代码从 `3 ** attempt` → `3 * 2 ** (attempt - 1)`（已更新到 demo2_celery_retry.py）。

**易错点**：`retry_backoff=True` = `retry_backoff=1`（默认系数为 1），所以大部分人用的就是 `1×2^n = 2^n` 的纯指数退避。
