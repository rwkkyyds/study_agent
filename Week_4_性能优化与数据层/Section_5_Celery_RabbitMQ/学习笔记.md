# Celery 异步任务队列 + RabbitMQ — 学习笔记

## 一、Celery 架构

```
Producer(.delay) → Broker(Redis/RabbitMQ) → Worker(独立进程) → Result Backend(Redis)
```

| 组件 | 作用 | 常见选型 |
|------|------|----------|
| Producer | 发送任务消息 | FastAPI / Django / 脚本 |
| Broker | 消息中间件，存储和分发任务 | Redis / RabbitMQ |
| Worker | 独立进程，消费任务并执行 | `celery worker` |
| Result Backend | 存储任务结果 | Redis / PostgreSQL |

---

## 二、基础用法

### 2.1 定义和调用任务

```python
from celery import Celery

celery_app = Celery("myapp",
    broker="redis://localhost:6379/0",
    backend="redis://localhost:6379/0",
)

@celery_app.task
def add(x, y):
    return x + y

# 调用
task = add.delay(3, 4)    # 异步发送到队列，立即返回
result = task.get(timeout=10)  # 阻塞等待结果 → 7
```

### 2.2 状态查询

```python
task = add.delay(3, 4)
print(task.status)  # PENDING → STARTED → SUCCESS
print(task.id)      # UUID 任务 ID
```

## 三、重试机制

### 3.1 自动重试

```python
@celery_app.task(
    bind=True,
    autoretry_for=(Exception,),  # 捕获这些异常时自动重试
    retry_backoff=True,          # 指数退避：1s → 2s → 4s → 8s...
    retry_backoff_max=60,        # 最大退避等待 60s
    max_retries=3,               # 最多重试 3 次
)
def call_api(self, url):
    response = requests.get(url)
    if response.status_code >= 500:
        raise Exception("服务不可用")
    return response.json()
```

### 3.2 手动重试

```python
@celery_app.task(bind=True, max_retries=5)
def smart_task(self, data):
    if data["status"] == "pending":
        raise self.retry(countdown=10)  # 10s 后重试
    return process(data)
```

### 3.3 指数退避策略

| 重试次数 | backoff=1 | backoff=2 | backoff=3 |
|----------|-----------|-----------|-----------|
| 第 1 次 | 1s | 2s | 3s |
| 第 2 次 | 2s | 4s | 9s |
| 第 3 次 | 4s | 8s | 27s |

#### 公式： backoff * 2^(重试次数-1)

## 四、任务编排

### 4.1 Chain — 串行流水线

```python
from celery import chain

chain(
    fetch_data.s("user"),  # .s() 创建签名（signature）
    process_data.s(),      # 接收上一步返回值
    save_result.s(),       # 接收上一步返回值
)().get()
```

### 4.2 Group — 并行执行

```python
from celery import group

group(
    analyze.s("A"),
    analyze.s("B"),
    analyze.s("C"),
)().get()  # → ["A 结果", "B 结果", "C 结果"]
```

### 4.3 Chord — 并行 + 汇总

```python
from celery import chord

chord(
    group(analyze.s("A"), analyze.s("B")),  # 并行
    summarize.s(),                            # 汇总回调
)().get()
```

## 五、RabbitMQ 核心概念

| 概念 | 说明 | 类比 |
|------|------|------|
| Producer | 发送消息 | 快递寄件人 |
| Exchange | 消息路由器 | 快递分拣中心 |
| Queue | 消息缓冲区 | 快递柜 |
| Consumer | 消费消息 | 收件人 |
| Binding | Exchange→Queue 路由规则 | 分拣规则 |
| Routing Key | 路由匹配关键字 | 快递单号 |

### Exchange 类型

| 类型 | 行为 | Celery 使用 |
|------|------|------------|
| **direct** | 按 routing key 精确匹配 | ✅ Celery 默认 |
| **topic** | 通配符匹配（`*` `#`） | 复杂路由 |
| **fanout** | 广播到所有绑定的 Queue | 群发通知 |
| **headers** | 按 header 匹配 | 少用 |

## 六、消息丢失与可靠性

| 问题 | 原因 | 解决 |
|------|------|------|
| Producer 发送前崩了 | 任务没进队列 | 用数据库做任务持久化（发送前先写 DB） |
| Broker 挂了 | 内存中消息丢失 | RabbitMQ 持久化（delivery_mode=2）/ Redis AOF |
| Worker 崩了 | 正在执行的任务丢失 | `acks_late=True`（任务执行完才确认） |
| 结果丢失 | Result Backend 过期 | 关键结果存 DB，不要仅依赖 Redis TTL |

## 七、RabbitMQ 实战（pika 原生操作）

### 7.1 为什么学 pika？

Celery 把 RabbitMQ 封装了一层，`.delay()` 一行代码就搞定了。但面试官会问：
- "Exchange 有哪几种类型？各用于什么场景？"
- "消息怎么持久化？ACK 机制怎么工作？"

不亲手写一次 Producer / Consumer，这些问题很难答深。学 pika 就是**把 Celery 的壳剥开，看清底层**。

### 7.2 Connection 与 Channel

```python
import pika

# 【Connection】TCP 长连接，一个进程一般只建一个
params = pika.ConnectionParameters(host="localhost", port=5672)
connection = pika.BlockingConnection(params)

# 【Channel】虚拟连接，一个 Connection 上可开多个 Channel
# 类比：Connection = 高速公路，Channel = 车道
channel = connection.channel()
```

### 7.3 Producer — 发送消息

```python
# 声明队列（幂等操作：存在就不重建）
channel.queue_declare(queue="my_queue", durable=True)  # durable 队列持久化

# 发送消息
channel.basic_publish(
    exchange="",              # 默认 Exchange（direct 类型）
    routing_key="my_queue",   # routing_key = 队列名
    body="Hello RabbitMQ",
    properties=pika.BasicProperties(
        delivery_mode=2,      # 【2 = 持久化到磁盘】RabbitMQ 重启后消息还在
    ),
)
```

### 7.4 Consumer — 消费消息

两种模式：

| 模式 | 方法 | 行为 | 适用场景 |
|------|------|------|----------|
| **Pull（拉）** | `basic_get()` | 主动拉一条，处理完再拉 | 按需消费 |
| **Push（推）** | `basic_consume()` | 注册回调，RabbitMQ 有消息就推 | 持续监听（生产标配）|

**Push 模式 + 手动 ACK（推荐）**：

```python
def on_message(ch, method, properties, body):
    # 处理消息...
    ch.basic_ack(delivery_tag=method.delivery_tag)  # 处理成功→确认删除
    # 或 ch.basic_nack(delivery_tag=..., requeue=True)  # 处理失败→重回队列

channel.basic_qos(prefetch_count=1)  # 【公平分发】每次只推1条，处理完才推下一条
channel.basic_consume(
    queue="my_queue",
    on_message_callback=on_message,
    auto_ack=False,  # 【手动ACK】必须 basic_ack 才算消费成功
)
channel.start_consuming()  # 阻塞循环接收
```

**auto_ack=True 的风险**：
Consumer 拿到消息后立即 ACK，如果处理过程中 Consumer 崩溃 → 消息已从队列删除 → 消息**永久丢失**。生产环境必须用 `auto_ack=False`。

### 7.5 Exchange 类型实战对比

```
┌──────────┬──────────────────┬──────────────────────────────┐
│ 类型     │ 路由规则          │ 一句话总结                     │
├──────────┼──────────────────┼──────────────────────────────┤
│ direct   │ routing_key 精确  │ "error" → error_queue        │
│ topic    │ 通配符 * 和 #     │ "china.#" → 所有中国数据       │
│ fanout   │ 忽略 routing_key  │ 一条消息所有队列都收到         │
└──────────┴──────────────────┴──────────────────────────────┘
```

**Binding 的本质**：告诉 Exchange "routing_key 匹配这个规则的，投递到那个 Queue"

```python
# Direct：精确匹配
channel.queue_bind(exchange="logs", queue="error_queue", routing_key="error")

# Topic：通配符匹配
channel.queue_bind(exchange="iot", queue="china_all", routing_key="china.#")  # # 匹配零个或多个
channel.queue_bind(exchange="iot", queue="beijing", routing_key="*.beijing.*") # * 匹配一个

# Fanout：不传 routing_key
channel.queue_bind(exchange="broadcast", queue="all_services")  # 无需 routing_key
```

### 7.6 Celery 底层用了哪种 Exchange？

Celery 默认用 **Direct Exchange**：
- 每个 Task 名 = Queue 名 = routing_key
- Celery `add.delay(1, 2)` 本质是：`basic_publish(exchange="celery", routing_key="add", body=...)`
- Celery Worker 本质是：`basic_consume(queue="add", callback=执行任务函数)`

理解了 pika，就等于理解了 Celery 的底层原理。
