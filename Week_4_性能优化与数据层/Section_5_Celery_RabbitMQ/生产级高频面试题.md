# Celery + RabbitMQ — 生产级高频面试题

---

## Q1：Celery 的架构是什么？各组件的作用？

**答：**

```
Producer → Broker → Worker → Result Backend
(FastAPI)  (Redis)  (celery)   (Redis)
```

- **Producer**：发送任务消息（.delay()）
- **Broker**：消息队列，存储待执行的任务。常用 Redis / RabbitMQ
- **Worker**：独立进程，从 Broker 拉取任务并执行
- **Result Backend**：存储任务执行结果，供 Producer 查询

## Q2：RabbitMQ 和 Redis 做 Broker 有什么区别？

**答：**

| 维度 | Redis | RabbitMQ |
|------|-------|----------|
| 协议 | 自有的 List/ Pub-Sub | AMQP 0-9-1 标准协议 |
| 消息确认 | 无原生 ACK | 原生 ACK + 持久化 |
| 消息路由 | 简单（按 key） | 丰富（Exchange + Binding + Routing Key）|
| 性能 | 更快（内存） | 稍慢（但可靠） |
| 可靠性 | 可能丢消息 | 持久化 + 确认机制，几乎不丢 |
| 运维 | 简单 | 复杂 |

**选择：** 轻量场景用 Redis，对消息可靠性要求高（金融/订单）用 RabbitMQ。

## Q3：Celery 任务失败后怎么重试？指数退避是什么？

**答：**

```python
@celery_app.task(
    autoretry_for=(Exception,),  # 捕获哪些异常自动重试
    retry_backoff=True,          # 指数退避
    retry_backoff_max=60,        # 最大退避上限
    max_retries=3,               # 最多重试次数
)
def task():
    ...
```

**指数退避**：第 1 次重试等 1s，第 2 次等 2s，第 3 次等 4s……避免瞬时故障时所有重试同时打过来（雪崩）。上限 `retry_backoff_max` 防止无限等待。

## Q4：Chain、Group、Chord 分别是什么？怎么用？

**答：**

| 原语 | 行为 | 示意图 |
|------|------|--------|
| **chain** | 串行管道，前一个的输出是下一个的输入 | A → B → C |
| **group** | 并行执行，互不依赖 | A┐ B┤ C┘（同时） |
| **chord** | group + 回调，并行完成后汇总 | (A,B,C) → summarize |

```python
# Chain
chain(fetch.s("user"), process.s(), save.s())()

# Group
group(analyze.s("A"), analyze.s("B"), analyze.s("C"))()

# Chord
chord(group(analyze.s("A"), analyze.s("B")), summarize.s())()
```

## Q5：消息队列是怎么保证消息不丢的？

**答：四层防护：**

1. **Producer 发送确认**：任务成功写入 Broker 才返回（Redis 用 `LPUSH` 返回长度验证）
2. **Broker 持久化**：RabbitMQ `delivery_mode=2`（持久化到磁盘）
3. **Worker 确认机制**：`acks_late=True` 让 Worker 执行完才 ACK，崩了消息重回队列
4. **死信队列 (DLX)**：重试耗尽的消息不丢弃，转到死信队列人工排查

## Q6：Celery Worker 崩了怎么办？有哪些监控手段？

**答：**

- **Worker 崩溃**：消息重回队列，其他 Worker 接管（需 `acks_late=True`）
- **监控**：Celery Flower（Web 监控面板）、Prometheus + Grafana
- **守护进程**：supervisor / systemd 自动重启 Worker
- **健康检查**：定期 ping Worker，无响应则告警

## Q7：Celery 在 Windows 上有什么注意事项？

**答：**

- Windows **不支持 fork**，必须用 `--pool=solo` 或 `--pool=threads`
- `celery worker --pool=solo`：单线程执行，适合开发调试
- `celery worker --pool=threads`：多线程执行，但受 GIL 限制
- 生产环境不推荐 Windows 跑 Celery Worker（用 Linux/Docker）

## Q8：RabbitMQ 的 Exchange 有哪几种类型？各自的使用场景？

**答：**

| 类型 | 路由规则 | 典型场景 |
|------|----------|----------|
| **direct** | routing_key 精确匹配 | 任务分发、日志分级路由（error→error_queue，info→info_queue）|
| **topic** | 通配符 `*`（一个单词）`#`（零或多个单词）| IOT 设备数据路由、消息订阅（`china.#` 订阅所有中国数据）|
| **fanout** | 忽略 routing_key，广播到所有绑定的 Queue | 系统公告、配置更新、缓存失效广播 |
| **headers** | 按消息 headers 字段匹配（少用）| 复杂条件路由 |

**Binding 的本质**：一条绑定规则 = "Exchange + Queue + routing_key"。一个消息可以匹配多条 Binding，投递到多个 Queue。

## Q9：RabbitMQ 怎么保证消息不丢？从 Producer 到 Consumer 全链路分析。

**答：四道防线：**

1. **Producer 端 — Publisher Confirm**：发送方确认消息已写入 Broker 才返回成功
2. **Broker 端 — 持久化**：
   - Queue 声明 `durable=True`（队列元数据持久化）
   - 消息 `delivery_mode=2`（消息体持久化到磁盘）
3. **Consumer 端 — 手动 ACK**：`auto_ack=False`，Consumer 处理完才 `basic_ack()`，处理失败 `basic_nack(requeue=True)` 让消息重回队列
4. **兜底 — 死信队列 (DLX)**：重试耗尽或过期的消息转入死信队列，人工排查

```
Producer ──confirm──▶  Broker  ──persist──▶  Disk
                          │
                    push + ack
                          │
                      Consumer ──ack──▶  Broker 删除消息
                          │
                      nack/超时 ──▶  重回队列 或 → 死信队列
```

## Q10：RabbitMQ 手动 ACK 和自动 ACK 的区别？为什么生产环境必须手动 ACK？

**答：**

| 模式 | auto_ack=True | auto_ack=False |
|------|:---:|:---:|
| 确认时机 | Consumer 收到消息立即确认 | Consumer 处理完手动 `basic_ack()` |
| Consumer 崩溃 | 消息已删除 → **永久丢失** | 消息未确认 → 重回队列由其他 Consumer 处理 |
| 性能 | 快 | 略有开销 |
| 适用 | 可容忍丢消息的场景 | **生产环境（订单/支付/金融）**|

**生产为什么必须手动 ACK？**

假设订单支付回调：Consumer 收到消息 → 自动 ACK 删除 → 处理过程中 Consumer OOM 崩溃 → 支付消息丢了，用户付了钱但订单状态未更新。手动 ACK 模式下，消息未确认，RabbitMQ 会重新投递给其他 Consumer。

## Q11：RabbitMQ 的 `basic_qos(prefetch_count=1)` 是干什么的？

**答：QoS（Quality of Service）限流机制。**

不加 QoS：RabbitMQ 把消息尽可能快地推给 Consumer，不管 Consumer 处理能力。结果：某个 Consumer 堆积大量未确认消息 → 其他 Consumer 闲着。

`prefetch_count=1`：RabbitMQ 每次只推送 1 条消息，Consumer 处理完并 ACK 后才推送下一条 → **公平分发（fair dispatch）**。

```
不设 prefetch_count：
  Consumer A: [msg1][msg2][msg3][msg4] ← 堆积  Consumer B: [] ← 空闲

prefetch_count=1：
  Consumer A: [msg1]  Consumer B: [msg2]  ← 轮询分发，负载均衡
```

## Q12：Topic Exchange 的通配符 `*` 和 `#` 有什么区别？举一个实际业务例子。

**答：**

| 通配符 | 匹配 | 例子 | 匹配结果 |
|--------|------|------|----------|
| `*` | **恰好 1 个**单词 | `order.*.paid` | `order.us.paid` ✅  `order.us.east.paid` ❌ |
| `#` | **0 个或多个**单词 | `order.#` | `order.us` ✅  `order.us.east.paid` ✅  `order` ❌ |

**实际业务例子 — 电商订单系统**：

```
订单消息 routing_key 格式：order.<国家>.<状态>

  order.us.created    → 新订单
  order.us.paid       → 已支付
  order.eu.shipped    → 已发货

Queue 绑定规则：
  美国订单队列：  routing_key="order.us.#"       → 收所有美国订单
  支付通知队列：  routing_key="order.*.paid"     → 收全球支付通知
  发货处理队列：  routing_key="order.*.shipped"  → 收全球发货通知
```

一条 `order.us.paid` → 同时投递到"美国订单队列"和"支付通知队列"。
