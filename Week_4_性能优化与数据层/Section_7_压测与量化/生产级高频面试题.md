## Q1: 为什么生产环境要关注 P99 延迟而不是平均延迟？

### 标准答案

**平均延迟的致命缺陷：**
- 被极端值拉偏，掩盖真实用户体验
- 无法发现尾部延迟问题（长尾效应）
- 10% 用户遇到 5 秒延迟，平均值可能只显示 200ms

**P99 的价值：**
- 反映 99% 用户的真实最差体验
- 能暴露系统瓶颈（缓存失效、数据库锁、GC停顿）
- 是生产环境 SLA 协议的核心指标

**数字示例：**
```
1000 次请求：990 次 50ms，10 次 5000ms
平均值 = 99.5ms（看起来很好，但实际 1% 用户体验极差）
P99 = 5000ms（真实暴露问题）
```

**面试加分点：**
- 提到 Google SRE 推荐关注 P50/P90/P99/P999
- 提到 P99 × 并发量 = 系统实际需要的资源
- 提到"延迟放大效应"：微服务调用链中，单个服务 P99 高会导致整体延迟雪崩

## Q2: 如何对一个 RAG 系统进行性能压测？需要关注哪些指标？

### 标准答案

**压测流程：**

```
1. 环境准备 → 2. 逐步加压 → 3. 持续监控 → 4. 瓶颈定位 → 5. 优化验证
```

**各环节关注指标：**

| 环节 | 指标 | 典型值 |
|------|------|--------|
| Embedding | 单次延迟 / 批处理吞吐 | 50-100ms / 200 texts/s |
| 向量检索 | 检索延迟 / recall@k | 20-50ms / > 0.9 |
| LLM 生成 | TTFT / 生成延迟 | 200ms / 1-3s |
| 端到端 | P99 延迟 / QPS / 错误率 | < 5s / > 10 / < 0.1% |

**压测工具选择：**
- **Locust**：Python 原生、易扩展、支持分布式
- **k6**：Go 编写、性能好、适合 CI/CD
- **JMeter**：Java 生态、GUI 操作、功能丰富

**面试加分点：**
- 提到瓶颈在 LLM 调用（占 80-90% 延迟）
- 提到缓存优化可以让热门查询延迟降低 99%
- 提到压测要模拟真实流量分布（热门 vs 长尾查询比例）

## Q3: 系统压测中发现 P99 延迟突然飙升，如何排查？

### 标准答案

**排查步骤（四层定位法）：**

```
第1层：资源层
├─ CPU 是否打满？→ top / htop
├─ 内存是否不足？→ free -m
├─ 磁盘 I/O 是否饱和？→ iostat
└─ 网络是否丢包？→ netstat / ss

第2层：中间件层
├─ 数据库连接池是否耗尽？→ pg_stat_activity
├─ Redis 内存是否满了？→ redis-cli info memory
├─ 消息队列是否积压？→ RabbitMQ 管理面板
└─ Nginx/LB 是否限流？→ access log

第3层：应用层
├─ GC 停顿？→ GC 日志
├─ 线程池/协程池是否满了？→ thread dump
├─ 慢查询？→ EXPLAIN ANALYZE
└─ 外部 API 超时？→ 链路追踪

第4层：业务层
├─ 缓存失效（缓存穿透/击穿/雪崩）？
├─ 热点数据倾斜？
├─ 突发流量？
└─ 数据量增长导致全表扫描？
```

**实战经验：**
- 80% 的 P99 飙升问题出在中间件层（连接池耗尽、缓存失效）
- 快速止血方案：限流 → 扩容 → 降级
- 根治方案：优化慢查询、加缓存、异步化

## Q4: Locust 和 JMeter 的区别？什么场景下选 Locust？

### 标准答案

| 维度 | Locust | JMeter |
|------|--------|--------|
| **语言** | Python | Java |
| **定义方式** | 代码（Python 脚本） | GUI + XML |
| **扩展性** | 高（Python 生态随意扩展） | 中（插件机制） |
| **协议支持** | HTTP 为主（可扩展） | HTTP/JDBC/JMS/FTP/SOAP |
| **资源占用** | 低（gevent 协程） | 高（线程模型） |
| **分布式** | 原生支持 master-worker | 支持但配置复杂 |
| **CI/CD** | 天然集成（命令行） | 需要额外配置 |
| **学习曲线** | 低（会 Python 即可） | 中（需学 GUI） |

**选 Locust 的场景：**
- 团队以 Python 技术栈为主
- 需要高度自定义的压测逻辑
- 需要集成到 CI/CD 流水线
- 压测 AI/ML 相关 API（方便调用模型 SDK）

**选 JMeter 的场景：**
- 需要压测非 HTTP 协议（数据库、消息队列）
- QA 团队不熟悉编程，偏好 GUI
- 需要录制浏览器操作回放

## Q5: 如何量化缓存对 RAG 系统的性能提升？

### 标准答案

**量化公式：**

```python
# 整体延迟估算
avg_latency = hit_rate × cache_latency + (1 - hit_rate) × db_latency

# 示例：
# 缓存命中率 65%，缓存延迟 10ms，无缓存延迟 1500ms
avg_latency = 0.65 × 10 + 0.35 × 1500 = 531ms
# 对比无缓存：1500ms → 降低 64.6%
```

**压测对比方法：**

| 指标 | 无缓存 | 有缓存 | 提升 |
|------|--------|--------|------|
| P50 | 1200ms | 15ms | 98.7% ↓ |
| P99 | 3500ms | 1500ms | 57% ↓ |
| QPS | 12/s | 85/s | 608% ↑ |
| 错误率 | 2.5% | 0.1% | 96% ↓ |

**缓存关键设计：**
```python
# 1. 缓存键设计（查询归一化）
cache_key = f"rag:{hashlib.md5(query.lower().strip()).hexdigest()}"

# 2. TTL 策略（根据内容更新频率）
redis.setex(key, TTL_SECONDS, value)

# 3. 缓存预热（热门查询提前加载）
for hot_query in top_100_queries:
    result = rag_pipeline(hot_query)
    redis.set(f"rag:{hash(hot_query)}", result)
```

**面试加分点：**
- 提到"二八定律"：20% 的查询占 80% 的流量，缓存这 20% 即可
- 提到缓存穿透防护：Bloom Filter / 空值缓存
- 提到缓存一致性：RAG 知识库更新时需要清理相关缓存

## Q6: 如何设计一个压测方案？从零到一的步骤？

### 标准答案

**完整压测方案设计（5 步法）：**

```
Step 1: 确定目标
├─ 目标 QPS（业务预估峰值 × 2 倍余量）
├─ 目标延迟（P99 < Xms）
├─ 目标错误率（< 0.1%）
└─ 容量规划（支撑多少并发用户？）

Step 2: 环境准备
├─ 搭建压测环境（与生产同配置或等比例缩放）
├─ 准备测试数据（覆盖热门 + 长尾场景）
├─ 部署监控（CPU/内存/连接池/缓存命中率）
└─ 基线测试（单用户响应时间）

Step 3: 逐步加压
├─ 预热阶段：10 用户，持续 2 分钟
├─ 爬坡阶段：每 30 秒增加 10 用户
├─ 峰值阶段：目标并发，持续 5 分钟
└─ 降压阶段：逐步减少，观察恢复

Step 4: 瓶颈定位
├─ 分析各环节耗时占比
├─ 找到第一个饱和的资源
├─ 确认是 CPU/内存/IO/网络哪个先到上限
└─ 优化瓶颈环节

Step 5: 优化验证
├─ 实施优化（缓存/连接池/索引/异步）
├─ 重新压测对比数据
├─ 输出压测报告（优化前后量化对比）
└─ 制定容量规划建议
```

**压测报告模板：**
```markdown
## 压测报告

### 测试环境
- 服务器：4C8G × 2
- 数据库：PostgreSQL 16（连接池 20）
- 缓存：Redis 7.0（2GB 内存）
- 向量库：Milvus 2.3（10 万文档）

### 测试结果
| 并发 | QPS | P50 | P99 | 错误率 |
|------|-----|-----|-----|--------|
| 10   | 45  | 80ms | 150ms | 0% |
| 50   | 180 | 120ms | 350ms | 0.05% |
| 100  | 250 | 200ms | 800ms | 0.2% |
| 200  | 260 | 500ms | 3000ms | 2.5% |

### 结论
- 系统饱和点：100 并发
- 瓶颈：数据库连接池（20 → 建议 50）
- 建议：增加缓存 + 扩容一台服务器
```

## Q7: 微服务架构下，如何做全链路压测？

### 标准答案

**全链路压测 vs 单服务压测：**

```
单服务压测：
  Client → [Service A] ← 压测这个

全链路压测：
  Client → [Gateway] → [Service A] → [Service B] → [DB]
                                    → [Service C] → [Cache]
  ← 压测整条链路
```

**全链路压测方案：**

1. **流量标记**（影子流量）
```python
# 给压测请求打标
headers = {"X-Stress-Test": "true"}

# 各服务识别标记，路由到影子库
if request.headers.get("X-Stress-Test"):
    db = shadow_db  # 不污染生产数据
```

2. **数据隔离**
```python
# 影子库：与生产库结构相同，数据独立
SHADOW_DB_URL = "postgresql://localhost/shadow_db"
SHADOW_REDIS_DB = 15  # 使用独立的 Redis DB
```

3. **监控覆盖**
```python
# 每个服务暴露 /metrics
# Prometheus 采集所有服务指标
# Grafana 大盘展示全链路延迟
```

**面试加分点：**
- 提到"木桶效应"：整体性能取决于最慢的服务
- 提到"延迟放大"：5 个服务各 P99=100ms → 整体 P99 可能 > 500ms
- 提到生产全链路压测的风险控制（流量比例、熔断、快速回滚）

## Q8: 压测时发现数据库连接池耗尽，怎么解决？

### 标准答案

**症状识别：**
```
错误日志：
- "connection pool exhausted"
- "too many connections"
- "QueuePool limit of size 5 overflow 10 reached"
```

**排查步骤：**

```python
# 1. 查看当前连接数
# PostgreSQL
SELECT count(*) FROM pg_stat_activity;

# 2. 查看等待锁的连接
SELECT * FROM pg_stat_activity WHERE wait_event_type IS NOT NULL;

# 3. 查看连接池状态（SQLAlchemy）
print(engine.pool.status())
# Pool size: 5  Connections in pool: 0  Current Overflow: 10
```

**解决方案（按优先级）：**

```python
# 方案1：增大连接池（快速止血）
engine = create_engine(
    url,
    pool_size=20,        # 5 → 20
    max_overflow=40,     # 10 → 40
    pool_timeout=30,     # 等待连接超时（秒）
    pool_recycle=3600,   # 回收过期连接
)

# 方案2：优化连接使用（减少持有时间）
async def query():
    async with session_factory() as session:
        result = await session.execute(sql)
        return result
    # with 块结束自动归还连接 ← 确保快速释放

# 方案3：增加缓存减少数据库请求
@cache(ttl=300)
async def get_user(user_id):
    # 缓存命中 → 不需要数据库连接
    return await db.query(User).get(user_id)

# 方案4：读写分离
WRITE_DB = "postgresql://master:5432/app"
READ_DB = "postgresql://replica:5432/app"
```

**面试加分点：**
- 提到连接泄漏排查（未正确关闭的 session）
- 提到 PgBouncer 连接池中间件（进程级 → 更高效）
- 提到"连接数 ≠ 并发数"：异步框架下少量连接也能支撑高并发

## Q9: 如何判断系统已经达到性能瓶颈（饱和点）？

### 标准答案

**三个核心信号：**

```
信号1：QPS 不再增长
├─ 并发从 50 → 100，但 QPS 从 200 → 205（几乎不变）
└─ 说明系统某个环节已经饱和

信号2：延迟指数级上升
├─ 并发 50：P99 = 200ms
├─ 并发 100：P99 = 800ms
├─ 并发 150：P99 = 3000ms（非线性增长）
└─ 说明请求在排队等待

信号3：错误率突增
├─ 并发 100 以下：错误率 0%
├─ 并发 120：错误率 0.5%
├─ 并发 150：错误率 5%
└─ 说明系统开始拒绝服务
```

**饱和点定位公式（Little's Law）：**
```
L = λ × W

L = 系统中的平均请求数
λ = 到达率（QPS）
W = 平均响应时间

例：连接池 20，平均响应时间 100ms
最大 QPS = 20 / 0.1 = 200 req/s
```

**面试加分点：**
- 提到 USL（Universal Scalability Law）预测扩容效果
- 提到"拐点"比"极限点"更有实际意义（系统在拐点前运行才安全）
- 提到预留 30-50% 余量（峰值流量是日常的 3-5 倍）

            └────────────────────┼────────────────────┘

                    ┌────────────▼───────────────────────────────┐

**Week 4 技术栈对应：**

| S3 pgvector | 向量字段 + HNSW + 混合检索 | 统一数据库方案 |

| S5 Celery | 异步任务 + 重试 + 工作流 | 耗时任务后台处理 |
| S6 批处理 | Embedding/Reranker 批量化 | 提升吞吐量 |
| **S7 压测** | **Locust + 指标量化** | **验证优化效果** |

**一句话总结：**
> 高性能 RAG 系统 = Redis 缓存热数据 + PostgreSQL/pgvector 统一存储 + 异步处理耗时操作 + 批处理提升吞吐 + Locust 压测验证
