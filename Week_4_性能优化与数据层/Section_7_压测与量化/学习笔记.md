## 📚 核心知识点

### 1. Locust 压测框架基础

#### 1.1 核心概念

**HttpUser 类**
```python
from locust import HttpUser, task, between

class MyUser(HttpUser):
    wait_time = between(1, 3)  # 任务间等待时间
    
    @task(3)  # 权重 3
    def my_task(self):
        self.client.get("/api/endpoint")
```

- **HttpUser**: Locust 提供的 HTTP 客户端基类，模拟用户行为
- **wait_time**: 每次任务执行后的等待时间（模拟真实用户思考）
- **@task**: 标记为压测任务，可设置权重（数字越大，执行频率越高）
- **self.client**: 内置的 HTTP 客户端，自动记录响应时间和状态

#### 1.2 任务权重机制

```python
@task(5)  # 50% 执行概率
def task_a(self):
    pass

@task(3)  # 30% 执行概率
def task_b(self):
    pass

@task(2)  # 20% 执行概率
def task_c(self):
    pass
```

权重计算：`任务权重 / 所有任务权重之和`

#### 1.3 响应处理

```python
# 自动标记成功/失败
self.client.get("/api/endpoint")

# 手动控制成功/失败
with self.client.get("/api/endpoint", catch_response=True) as response:
    if response.status_code == 200:
        response.success()
    else:
        response.failure(f"Got {response.status_code}")
```

### 2. 性能指标体系

#### 2.1 核心指标

| 指标 | 英文 | 含义 | 生产级标准 |
|------|------|------|-----------|
| **QPS** | Queries Per Second | 每秒查询数 | 简单查询 > 100，RAG > 10 |
| **RPS** | Requests Per Second | 每秒请求数 | 同 QPS |
| **P50** | 50th Percentile | 50% 请求的响应时间 | < 100ms（简单），< 2s（RAG） |
| **P90** | 90th Percentile | 90% 请求的响应时间 | < 200ms（简单），< 3s（RAG） |
| **P99** | 99th Percentile | 99% 请求的响应时间 | < 500ms（简单），< 5s（RAG） |
| **错误率** | Error Rate | 失败请求占比 | < 0.1% |
| **吞吐量** | Throughput | 单位时间处理数据量 | 根据业务需求 |

#### 2.2 为什么关注 P99 而非平均值？

**平均值的问题：**
- 被极端值影响（少数超慢请求拉高平均值）
- 无法反映"最差情况"
- 掩盖了尾部延迟问题

**P99 的优势：**
- 99% 用户的真实体验
- 能发现系统瓶颈（如数据库锁、缓存失效）
- 生产环境 SLA 通常基于 P99

**实例对比：**
```
场景：1000 次请求
- 990 次：50ms
- 10 次：5000ms

平均值 = (990×50 + 10×5000) / 1000 = 99.5ms  ✗ 误导性强
P99 = 5000ms  ✓ 真实反映最差情况
```

### 3. RAG 系统性能优化

#### 3.1 各环节耗时占比（典型）

```
完整 RAG 流程（无缓存）：
├─ Embedding: 50-100ms      (5-10%)
├─ 向量检索: 20-50ms        (2-5%)
└─ LLM 生成: 500-2000ms     (80-90%)  ← 主要瓶颈

优化后（带缓存）：
└─ 缓存命中: < 10ms         (延迟降低 99%)
```

#### 3.2 性能优化策略

**1. 缓存优化（最高优先级）**
```python
# 热门查询缓存
cache_key = f"rag:{query_hash}"
if cached := redis.get(cache_key):
    # 把右边的值赋值给左边变量
    # 同时把这个值本身作为表达式结果，用于判断、循环等场景
    return cached  # 延迟从 2s → 10ms

# 典型收益：缓存命中率 60% → 整体 P99 降低 80%
```

**2. 批处理优化**
```python
# Embedding 批处理
vectors = model.embed_batch(texts)  # 比循环快 3-5 倍

# 向量检索批处理
results = vector_db.search_batch(queries)
```

**3. 异步并发**
```python
# 并发调用多个 LLM
tasks = [llm.agenerate(ctx, q) for q in queries]
results = await asyncio.gather(*tasks)
```

**4. 数据库连接池**
```python
engine = create_engine(
    url,
    poolclass=QueuePool,
    pool_size=10,        # 连接池大小
    max_overflow=20,     # 最大溢出连接
    pool_pre_ping=True   # 连接前检查可用性
)
```

### 4. 压测实战技巧

#### 4.1 压测准备清单

- [ ] **隔离环境** - 不要对生产环境压测
- [ ] **数据预热** - 提前准备测试数据，避免冷启动
- [ ] **资源监控** - 监控 CPU、内存、数据库连接、Redis 连接
- [ ] **逐步加压** - 从 10 用户开始，逐步增加到目标并发
- [ ] **持续时间** - 每次压测至少 3-5 分钟，取稳定阶段数据

#### 4.2 Locust Web UI 参数设置

```
Number of users: 100        # 模拟 100 个并发用户
Spawn rate: 10 users/s      # 每秒增加 10 个用户（避免瞬间压垮系统）
Host: http://localhost:8000 # 被测服务地址
```

#### 4.3 结果分析维度

**1. 响应时间分布**
- 查看响应时间柱状图
- 识别延迟峰值和异常点

**2. 错误率变化**
- 并发增加时错误率上升 → 系统瓶颈
- 查看具体错误类型（连接超时、500 错误等）

**3. 吞吐量曲线**
- RPS 不再增长 → 系统饱和
- 定位饱和点（如 50 并发时 RPS 到顶）

### 5. 瓶颈定位方法

#### 5.1 数据库瓶颈

**症状：**
- 并发增加时延迟线性上升
- 数据库连接池耗尽日志
- 慢查询日志增多

**排查：**
```sql
-- PostgreSQL 查看活跃连接
SELECT count(*) FROM pg_stat_activity;

-- 查看慢查询
SELECT * FROM pg_stat_statements 
ORDER BY mean_exec_time DESC 
LIMIT 10;
```

**解决：**
- 增加连接池大小
- 添加索引
- 优化 SQL 查询
- 使用缓存

#### 5.2 向量检索瓶颈

**症状：**
- 检索延迟随文档数增长
- CPU 使用率高

**排查：**
```python
# 记录检索耗时
import time
t0 = time.time()
results = vector_db.search(query_vector)
print(f"检索耗时: {(time.time() - t0) * 1000}ms")
```

**解决：**
- 优化 HNSW 索引参数（ef_search、M）
- 分片存储（按类别、时间切分）
- 使用更高效的向量库（Milvus、Qdrant）

#### 5.3 LLM 调用瓶颈

**症状：**
- 80-90% 延迟来自 LLM
- 并发增加时超时错误增多

**排查：**
```python
# 分段计时
timings = {}
t0 = time.time()
answer = await llm.agenerate(context, query)
timings["llm_ms"] = (time.time() - t0) * 1000
```

**解决：**
- 缓存热门查询结果
- 使用流式输出（减少用户等待感知）
- 增加 LLM 并发限制配额
- 考虑本地部署模型

#### 5.4 缓存未命中

**症状：**
- 相同查询响应时间差异大
- 缓存命中率低于预期

**排查：**
```python
# 监控缓存命中率
hits = redis.info("stats")["keyspace_hits"]
misses = redis.info("stats")["keyspace_misses"]
hit_rate = hits / (hits + misses)
print(f"缓存命中率: {hit_rate:.2%}")
```

**解决：**
- 调整缓存 TTL（避免过期过快）
- 优化缓存键设计（查询归一化）
- 预热热门查询
- 增加缓存容量

### 7. 生产级压测注意事项

#### 7.1 压测环境隔离

```
✓ 使用测试环境/预发布环境
✓ 数据库使用从库或测试库
✓ 告知团队压测时间（避免误报警）
✗ 永远不要对生产环境直接压测
```

#### 7.2 压测数据准备

```python
# 提前准备测试数据（避免冷启动影响）
def prepare_test_data():
    # 预热缓存
```

#### 7.3 监控告警

```python
# 压测时监控关键指标
import psutil

def monitor_resources():

    if cpu_percent > 90:
```

## 🎯 本节核心要点总结

1. **Locust 是生产级压测工具**：简单易用、Web UI 直观、支持分布式压测
2. **关注 P99 而非平均值**：P99 反映真实用户最差体验，是 SLA 基准
3. **RAG 系统瓶颈在 LLM**：80-90% 延迟来自 LLM，缓存是最有效优化手段
4. **逐步加压 + 持续监控**：避免瞬间压垮系统，及时发现资源瓶颈
5. **量化优化效果**：用数据说话（P99 降低 X%，QPS 提升 X 倍）
