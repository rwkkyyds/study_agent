## 1. __table_args__ 里的索引定义参数详解

### Index() 的参数结构

```python
Index(索引名, 要索引的列, 其他选项...)
```

| 参数 | 含义 | 类比 |
|------|------|------|
| `"idx_product_category"` | 索引的名字 | 给目录起个名字 |
| `"category"` | 索引哪一列 | 目录是按什么排序的 |
| `postgresql_using="gin"` | 用什么算法建索引 | 用什么方式排目录 |
| `postgresql_where=...` | 只索引满足条件的行 | 只给"在售商品"建目录 |
| `postgresql_include=[...]` | 索引里额外存哪些列 | 目录里顺便写上价格 |

---

### 索引 1：B-tree（最基础）

```python
Index("idx_product_category", "category"),
```

**拆解：**
- `"idx_product_category"` → 索引名叫 idx_product_category
- `"category"` → 索引 category 这一列
- 没写 `postgresql_using` → 默认用 B-tree 算法

**作用：** 给 category 列建一个 B-tree 排序目录。

**例子：**
```sql
-- 没有索引：全表扫描 10 万行，13ms
SELECT * FROM products WHERE category = '电子产品';

-- 有索引：直接跳到"电子产品"那一堆，4ms
-- 快了 3 倍
```

---

### 索引 2：复合索引（两列联合）

```python
Index("idx_product_cat_price", "category", "price"),
```

**拆解：**
- `"idx_product_cat_price"` → 索引名
- `"category", "price"` → 索引两列，先按 category 排，再按 price 排

**作用：** 同时按分类+价格排序，支持两列联合查询。

**最左前缀原则：**
```sql
-- ✅ 两列都用上了（完全命中）
WHERE category = '电子产品' AND price < 500

-- ✅ 只用第一列（最左前缀，也能用）
WHERE category = '电子产品'

-- ❌ 只用第二列（不能用！因为 price 在 category 后面排的）
WHERE price < 500
```

**为什么违反最左前缀就不能用？**
想象电话簿：先按姓排，同姓再按名排。
- 查"姓张的" → 能快速定位 ✅
- 查"姓张且名三的" → 更精确 ✅
- 查"名叫三的" → 没用！因为"三"分散在各个姓里 ❌

---

### 索引 3：部分索引（只索引一部分行）

```python
Index("idx_product_active_price", "price",
      postgresql_where=text("is_active = true")),
```

**拆解：**
- `"idx_product_active_price"` → 索引名
- `"price"` → 索引 price 列
- `postgresql_where=text("is_active = true")` → 只索引 is_active=true 的行

**作用：** 只给"在售商品"建价格索引，下架商品不管。

**例子：**
```sql
-- 10 万条数据：8 万在售，2 万下架
-- 部分索引只存 8 万条 → 索引更小，更快

-- ✅ 命中部分索引（条件匹配 is_active=true）
WHERE is_active = true AND price < 100

-- ❌ 不命中（没有 is_active=true 条件）
WHERE price < 100
```

**为什么有用？** 如果 90% 的查询都是查"在售商品"，只为它们建索引，省空间、省维护成本。

---

### 索引 4：覆盖索引（索引里多存几列）

```python
Index("idx_product_cat_cover", "category",
      postgresql_include=["name", "price", "stock"]),
```

**拆解：**
- `"idx_product_cat_cover"` → 索引名
- `"category"` → 按 category 排序（主索引列）
- `postgresql_include=["name", "price", "stock"]` → 索引里额外存 name, price, stock

**作用：** 索引不光告诉你"在哪一行"，还直接把数据给你。

**例子：**
```sql
-- 普通索引（只存 category）
-- 查 name, price, stock → 先在索引里找到行号 → 再回原表取数据（两步）
SELECT name, price, stock FROM products WHERE category = '电子产品';

-- 覆盖索引（category + name + price + stock 都在索引里）
-- 直接从索引返回数据，不用回表（一步）
-- PostgreSQL 执行计划：Index Only Scan（最快）
```

**类比：**
- 普通索引 = 目录只写"第12页" → 还要翻到12页看内容
- 覆盖索引 = 目录直接写"第12页，手机，¥999，库存50" → 不用翻页

---

### 索引 5：GIN 索引（JSONB 专用）

```python
Index("idx_product_tags", "tags", postgresql_using="gin"),
```

**拆解：**
- `"idx_product_tags"` → 索引名
- `"tags"` → 索引 tags 列（JSONB 类型）
- `postgresql_using="gin"` → 用 GIN 算法（不是默认的 B-tree）

**作用：** 为 JSON 数组建立"倒排索引"，支持"包含"查询。

**例子：**
```sql
-- tags 是 JSONB：["热销", "新品", "包邮"]
-- 普通 B-tree 查不了 JSON 内部
-- GIN 索引建好后，能快速查"包含某个标签"的商品

-- 查标签包含"热销"的商品
WHERE tags @> '["热销"]'       -- @> 是 PostgreSQL 的"包含"操作符

-- 查同时包含"热销"和"新品"的
WHERE tags @> '["热销", "新品"]'
```

**为什么需要 `postgresql_using="gin"`？**
因为 JSONB 不是普通字符串，B-tree 不知道怎么排序它。GIN（Generalized Inverted Index）专门处理这种"一个字段里有多个值"的场景。

---

### 总结：5 个索引的对比

```
索引1  Index("name", "category")
       → 最基础，查单列

索引2  Index("name", "category", "price")
       → 两列联合，必须从左用起

索引3  Index("name", "price", postgresql_where=...)
       → 只索引满足条件的行

索引4  Index("name", "category", postgresql_include=[...])
       → 索引里多存几列，不用回表

索引5  Index("name", "tags", postgresql_using="gin")
       → JSONB 专用，查"包含"
```

## 2. ROUND 函数在 PostgreSQL 中的类型问题

**问题：** `ROUND(double precision, 2)` 在 PostgreSQL 中报错，因为 ROUND 只接受 `numeric` 类型。

**解决：** 加 `::numeric` 类型转换。

```sql
-- ❌ 报错
ROUND(amount * 100.0 / total, 2)

-- ✅ 正确
ROUND((amount * 100.0 / total)::numeric, 2)
```

## 3. 连接池事件监听 @event.listens_for

### 什么是事件监听

**类比：** 在家门口装摄像头，有人进出自动记录。

```python
@event.listens_for(engine, "事件名")
def 回调函数(参数):
    当事件发生时，自动执行这段代码
```

### 三个事件

| 事件 | 触发时机 | 类比 |
|------|---------|------|
| `connect` | 新连接被创建（第一次连数据库） | 新买了一辆车 |
| `checkout` | 连接从池子里被"借出去" | 把车从车库开出来 |
| `checkin` | 连接被"还回"池子 | 把车开回车库 |

### 回调函数参数

```python
@event.listens_for(engine, "connect")
def on_connect(dbapi_conn, connection_record):
    # dbapi_conn        → 底层数据库连接对象（psycopg2 的 connection）
    # connection_record → SQLAlchemy 的连接记录（元信息）
    logger.info("新连接被创建")

@event.listens_for(engine, "checkout")
def on_checkout(dbapi_conn, connection_record, connection_proxy):
    # dbapi_conn        → 底层数据库连接
    # connection_record → 连接记录
    # connection_proxy  → 连接代理（Session 用的就是这个）
    logger.info("连接被借出")

@event.listens_for(engine, "checkin")
def on_checkin(dbapi_conn, connection_record):
    # dbapi_conn        → 底层数据库连接
    # connection_record → 连接记录
    logger.info("连接被归还")
```

### 实际运行效果

```python
# 第一次查询
with Session(engine) as session:
    session.execute(text("SELECT 1"))
# 输出：
# → 新连接被创建（connect，第一次需要新建）
# → 从连接池借出连接（checkout）
# → 连接归还到连接池（checkin）

# 第二次查询
with Session(engine) as session:
    session.execute(text("SELECT 2"))
# 输出：
# → 从连接池借出连接（checkout，复用旧连接，不触发 connect）
# → 连接归还到连接池（checkin）
```

**关键：** connect 只在第一次触发，后续复用旧连接只触发 checkout/checkin。

### 连接的生命周期

```
第一次请求：创建连接 → 放入连接池 → 借出 → 使用 → 归还
后续请求：  借出（从池子里拿现成的）→ 使用 → 归还
连接池满了：等待（pool_timeout 秒）→ 还是拿不到 → 报错
```

## 4. relationship 关联关系详解

### 什么是 relationship

数据库里两个表是分开存的，relationship 让你在 Python 里直接通过对象访问关联数据，不用自己写 JOIN。

```python
# 没有 relationship：要自己写 SQL
orders = session.execute("SELECT * FROM orders WHERE user_id = 1")

# 有了 relationship：直接用 Python 属性
user = session.query(User).get(1)
print(user.orders)  # 自动查出这个用户的所有订单
```

### 逐个拆解

```python
# 用户侧
orders = relationship("Order", back_populates="user", lazy="select")
# 订单侧
user = relationship("User", back_populates="orders")
```

| 参数 | 含义 | 类比 |
|------|------|------|
| `"Order"` / `"User"` | 关联到哪个 Model | "我的订单们"是什么类型 |
| `back_populates="user"` | 双向绑定 | 互相认识，知道对方是谁 |
| `lazy="select"` | 用到时才查（延迟加载） | 不提前查，用到再查 |

### back_populates：双向绑定

```python
# 没有 back_populates：只能单向
user.orders  # ✅ 能查到订单
order.user   # ❌ 不知道是谁

# 有 back_populates：双向都能访问
user.orders  # ✅ 查到这个用户的所有订单
order.user   # ✅ 查到这个订单属于哪个用户
```

类比：没有 back_populates = 你认识他，他不认识你。
有 back_populates = 互相认识，双向都能找到对方。

### lazy：加载策略

```python
lazy="select"   # 用到时才查（默认值）
lazy="joined"   # 提前用 JOIN 一起查出来
lazy="subquery" # 提前用子查询查出来
```

```python
# lazy="select"（默认）
user = session.query(User).get(1)    # 查 users 表
print(user.orders)                    # 用到了，才查 orders 表
# → 两次 SQL（如果不用 orders，就只查 1 次）

# lazy="joined"
user = session.query(User).options(joinedload(User.orders)).get(1)
# → 1 次 SQL（LEFT JOIN 一起查出来）
print(user.orders)  # 直接有数据
```

### 关系图

```
User 表                         Order 表
┌─────┬──────┬───────┐         ┌─────┬─────────┬─────────┬────────┐
│ id  │ name │ email │         │ id  │ user_id │ product │ amount │
└─────┴──────┴───────┘         └─────┴─────────┴─────────┴────────┘
      │                               │
      └───── 一对多 ──────────────────┘

user.orders → SELECT * FROM orders WHERE user_id = ?
order.user  → SELECT * FROM users WHERE id = ?
```

## 5. Base.metadata.create_all(engine) 详解

### 三个部分

```python
class Base(DeclarativeBase):      # 1. 基类（登记簿）
    pass

class User(Base):                 # 2. 继承基类，定义表结构
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    name = Column(String(50))

Base.metadata.create_all(engine)  # 3. 把表建到数据库里
```

| 部分 | 含义 | 类比 |
|------|------|------|
| `Base` | 基类，所有 Model 都注册到这里 | 登记簿 |
| `Base.metadata` | 记录所有表结构的"花名册" | 花名册 |
| `.create_all(engine)` | 拿着花名册去数据库建表 | 拿着名单去办事 |

### 等价于执行的 SQL

```sql
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50) NOT NULL,
    email VARCHAR(100) NOT NULL
);

CREATE TABLE IF NOT EXISTS orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id),
    product VARCHAR(100) NOT NULL,
    amount FLOAT NOT NULL
);
```

### 完整流程

```python
# 1. 定义表结构（Python 代码里）
class User(Base):
    __tablename__ = "users"
    id = Column(Integer, primary_key=True)
    name = Column(String(50))

# 2. 连接数据库
engine = create_engine("postgresql+psycopg2://...")

# 3. 把 Python 定义的表结构，真正建到 PostgreSQL 里
Base.metadata.create_all(engine)
```

**注意：** `create_all` 自带 `IF NOT EXISTS`，表已存在不会报错，可以重复调用。

## 6. N+1 问题代码详解

### 什么是 N+1 问题

场景：想知道每个用户有多少订单。

错误做法（N+1）：
```
第 1 步：查出所有用户          → 1 次 SQL
第 2 步：遍历每个用户，查他的订单 → 每个用户 1 次 SQL
10 个用户 → 1 + 10 = 11 次 SQL
100 个用户 → 1 + 100 = 101 次 SQL
```

正确做法（JOIN）：一次 SQL 搞定所有数据。

### 代码逐行拆解

#### 第一步：查出 10 个用户（1 次 SQL）

```python
users = session.execute(
    text("SELECT id, name FROM users LIMIT 10")
).fetchall()
# 返回：[(1, "user_1"), (2, "user_2"), ..., (10, "user_10")]
```

#### 第二步：遍历每个用户，查他的订单（N 次 SQL）

```python
for user in users:
    # user = (1, "user_1")
    #         ↑     ↑
    #       [0]   [1]
    #        id   name

    orders = session.execute(
        text(f"SELECT * FROM orders WHERE user_id = {user[0]}")
    ).fetchall()
    result.append((user[1], len(orders)))
```

每次循环执行一条 SQL：
```sql
SELECT * FROM orders WHERE user_id = 1   -- 第 1 次
SELECT * FROM orders WHERE user_id = 2   -- 第 2 次
...
SELECT * FROM orders WHERE user_id = 10  -- 第 10 次
```

#### 第三步：统计 SQL 次数

```python
result, query_count = count_queries(engine, n_plus_one_query)
```

count_queries 通过监听 before_cursor_execute 事件，每次 SQL 执行前 +1。

为什么用 `query_count = [0]` 而不是 `query_count = 0`？
闭包里修改外部变量需要可变对象。列表是可变的，整数不是。

### 执行流程

```
SQL #1:  SELECT id, name FROM users LIMIT 10
         → 返回 10 个用户

SQL #2:  SELECT * FROM orders WHERE user_id = 1
SQL #3:  SELECT * FROM orders WHERE user_id = 2
...
SQL #11: SELECT * FROM orders WHERE user_id = 10

总计：11 次 SQL（1 + 10）
```

### 为什么是问题

10 个用户 → 11 次 SQL
100 个用户 → 101 次 SQL
1000 个用户 → 1001 次 SQL

每次 SQL 都有网络开销（发送请求 + 等待响应），1000 次就是 1000 次网络往返。
用 JOIN 只需要 1 次 SQL。

## 7. joinedload vs selectinload 选择纠正

### 之前的笔记写得太绝对了

实际区别不是"能不能用"，而是"用了会怎样"。

### joinedload 用于一对多的问题：数据膨胀

```python
# User 一对多 Order
users = session.query(User).options(joinedload(User.orders)).limit(10).all()
```

生成的 SQL：
```sql
SELECT users.*, orders.*
FROM users LEFT JOIN orders ON users.id = orders.user_id
LIMIT 10
```

问题：10 个用户，每个有 10 个订单 → JOIN 后 100 行。
LIMIT 10 本意是取 10 个用户，实际只取到 1 个用户（因为 1 个用户就占了 10 行）。

### 三种方式对比

```
场景：10 个用户，每个用户 10 个订单

joinedload（LEFT JOIN）：
  → 100 行结果，用户数据重复 10 次，LIMIT 语义被破坏

selectinload（IN 子查询）：
  → SQL #1: SELECT * FROM users LIMIT 10
  → SQL #2: SELECT * FROM orders WHERE user_id IN (1,2,...,10)
  → 2 次 SQL，数据不重复，LIMIT 语义正确

lazy loading（默认）：
  → 11 次 SQL（N+1 问题）
```

### 选择建议

| 关系类型 | 推荐方式 | 原因 |
|---------|---------|------|
| 多对一（Order → User） | joinedload | JOIN 后一行对一行，不膨胀 |
| 一对一 | joinedload | JOIN 后一行对一行，不膨胀 |
| 一对多（User → Orders） | selectinload | 避免数据膨胀，LIMIT 语义正确 |
