# Embedding / Reranker 批处理优化吞吐 — 学习笔记

## 一、为什么批处理能加速？

### 1.1 核心原因：矩阵运算的天然并行性

深度学习模型的推理本质上是**矩阵乘法**。以 Embedding 为例：

```
单条编码： (1, token_len) × (token_len, 384) = (1, 384)
批量编码： (32, token_len) × (token_len, 384) = (32, 384)
```

当 batch_size=32 时，所有 32 条文本被拼成一个大矩阵一次性送入模型。GPU/CPU 的矩阵运算单元可以**同时处理**这 32 条，而不是分 32 次串行计算。

### 1.2 IO-Bound vs Compute-Bound

| 类型 | 瓶颈 | 典型场景 | 优化方向 |
|------|------|----------|----------|
| IO-Bound | 网络/磁盘读写 | API 调用、数据库查询 | 异步并发（Week_4 Section_4 asyncio） |
| Compute-Bound | CPU/GPU 计算 | 模型推理、Embedding | **批处理**（本 Section） |

批处理是 compute-bound 问题的最优解，因为它把反复启动推理引擎的**固定开销**（模型加载、kernel launch、内存分配）摊薄到多条数据上。

## 二、Embedding 批处理

### 2.1 单条 vs 批量对比

```python
# ❌ 逐条编码 —— 低效
embeddings = []
for text in texts:
    emb = list(model.embed([text]))  # 每次只传 1 条
    embeddings.append(emb)

# ✅ 批量编码 —— 高效
embeddings = list(model.embed(texts, batch_size=32))  # 一次传 32 条
```

### 2.2 加速原理图解

```
单条模式（batch_size=1）：
  [文档1] → GPU推理 → 向量1
  [文档2] → GPU推理 → 向量2    ← GPU 大部分时间在等 CPU 喂数据
  [文档3] → GPU推理 → 向量3
  ...

批量模式（batch_size=32）：
  [文档1-32] → GPU推理 → 向量1-32   ← GPU 满载运行
  [文档33-64] → GPU推理 → 向量33-64
  ...
```

**加速比通常可达 5~20x**（取决于模型大小和硬件）。

### 2.3 batch_size 对吞吐的影响

| batch_size | 典型吞吐 (docs/sec) | 加速比 | 备注 |
|------------|---------------------|--------|------|
| 1 | ~50 | 1x | 基准线 |
| 4 | ~150 | 3x | 开始享受批处理红利 |
| 8 | ~250 | 5x | |
| 16 | ~380 | 7.6x | |
| 32 | ~450 | 9x | **常用默认值** |
| 64 | ~480 | 9.6x | 边际递减开始 |
| 128 | ~500 | 10x | 提升很小，但内存开销翻倍 |

**关键规律**：
- **前半段（1→32）**：加速比近似线性增长，因为 GPU 从"饥饿"变"吃饱"
- **后半段（32→128）**：边际递减，GPU 已满载，继续加大 batch 只会增加内存压力
- **过大风险**：batch_size 超过 GPU/CPU 显存上限会导致 **OOM**

### 2.4 fastembed 的 batch_size 参数

```python
from fastembed import TextEmbedding

model = TextEmbedding(model_name="BAAI/bge-small-zh-v1.5")

# batch_size 控制每次送入模型的文本数量
vectors = list(model.embed(texts, batch_size=32))
# fastembed 内部自动：
#   1. 将 texts 按 batch_size 分块
#   2. 每个 chunk 做 tokenize → padding → 模型推理 → 返回向量
```

## 三、Reranker 批处理

### 3.1 Reranker 与 Embedding 的本质区别

| 维度 | Embedding（Bi-Encoder） | Reranker（Cross-Encoder） |
|------|-------------------------|---------------------------|
| 输入 | 单条文本 | **(query, doc) 对** |
| 计算方式 | 分别编码 query 和 doc，用余弦相似度 | query 和 doc 拼接后一起过 Transformer |
| 精度 | 较低（速度换精度） | **更高**（精度换速度） |
| 推理代价 | 轻量 | 重量级（每对都要完整前向传播） |
| 批处理收益 | 有 | **更明显**（因为单次推理更重） |

### 3.2 单条 vs 批量 Rerank

```python
# ❌ 逐条 Rerank —— 每个 pair 独立调用一次模型
for passage in passages:
    request = RerankRequest(query=query, passages=[passage])
    scored = ranker.rerank(request)  # 模型只处理 1 对

# ✅ 批量 Rerank —— 一次传入所有 pair
request = RerankRequest(query=query, passages=passages)
results = ranker.rerank(request)  # 模型一次处理全部 N 对
```

### 3.3 为什么 Reranker 批处理加速更明显？

Cross-Encoder 的推理比 Bi-Encoder 重得多：

```
Bi-Encoder:  query → Encoder → vec_q
             doc  → Encoder → vec_d     → dot(vec_q, vec_d)   ← 编码可缓存

Cross-Encoder: [CLS] query [SEP] doc [SEP] → 完整 Transformer 前向传播  ← 每对都要算
```

因此单条调用的固定开销占比更高，批量带来的节省也更明显。**Reranker 批处理加速比通常 10~50x**。

### 3.4 FlashRank 的 RerankRequest

```python
from flashrank.Ranker import RerankRequest

# RerankRequest 接受一个 passages 列表，内部做批量 Cross-Attention
request = RerankRequest(
    query="如何优化数据库查询性能？",
    passages=[
        {"id": 0, "text": "文档0: 索引优化..."},
        {"id": 1, "text": "文档1: 查询缓存..."},
        # ... 一次传 20 条
    ]
)
results = ranker.rerank(request)
# results 按 score 降序排列：[{"id": 5, "score": 0.92}, {"id": 3, "score": 0.78}, ...]
```

## 四、管道级批处理优化

### 4.1 检索管道中的两个批处理点

```
文档(500条)
  │
  ├──[优化点1: 批量Embedding]──→ 逐条 50s → 批量 5s (10x)
  │
  ▼
FAISS 向量索引 ←── 瓶颈不在计算，而在索引构建
  │
  ▼
检索 Top-K（20条）
  │
  ├──[优化点2: 批量Rerank]──→ 逐条 10s → 批量 0.5s (20x)
  │
  ▼
最终结果 Top-5
```

### 4.2 Naive vs Optimized 对比

| 管道阶段 | Naive（逐条） | Optimized（批量） | 加速比 |
|----------|--------------|-------------------|--------|
| Embedding 建索引 | for 循环逐条 encode | `model.embed(docs, batch_size=32)` | ~10x |
| FAISS 检索 | 相同（向量检索本身已优化） | 相同 | 1x |
| Rerank 重排 | for 循环逐对 rerank | `RerankRequest(passages=top_docs)` | ~20x |
| **端到端总耗时** | ~62s | ~6.5s | **~10x** |

### 4.3 代码对比

```python
# Naive：逐条 Embedding
vectors = []
for doc in docs:
    emb = list(emb_model.embed([doc]))  # 500 次推理调用
    vectors.append(emb[0])

# Optimized：批量 Embedding
vectors = list(emb_model.embed(docs, batch_size=32))  # 仅 ~16 次推理调用
```

## 五、如何选择 batch_size

### 5.1 决策因素

| 因素 | 影响 | 建议 |
|------|------|------|
| GPU 显存 | batch_size 上限的硬约束 | 从 32 开始试，OOM 就减半 |
| CPU 内存 | CPU 推理时的上限 | 通常 >128 才需关注 |
| 文本长度 | 长文本占更多内存 | 长文本用更小的 batch_size |
| 延迟要求 | 在线服务需要低延迟 | 宁可小 batch，不让用户等 |

### 5.2 实战经验值

| 场景 | 推荐 batch_size | 原因 |
|------|----------------|------|
| 离线建索引 | 64-256 | 延迟不重要，吞吐优先 |
| 在线 API | 8-32 | 平衡吞吐和响应时间 |
| GPU 推理 | 32-128 | 充分利用 GPU 并行能力 |
| CPU 推理 | 16-64 | CPU 并行度有限 |

### 5.3 寻找最优 batch_size 的方法

```python
# 对每个候选 batch_size 跑 3 轮取平均
for bs in [1, 4, 8, 16, 32, 64, 128]:
    t0 = time.perf_counter()
    for _ in range(3):
        list(model.embed(texts, batch_size=bs))
    avg_time = (time.perf_counter() - t0) / 3
    throughput = len(texts) / avg_time
    print(f"batch_size={bs:>3}: throughput={throughput:.0f} docs/sec")
```

**选点策略**：找到吞吐不再显著提升的那个"拐点"，它就是性价比最高的 batch_size。

## 六、FAISS 向量检索与批处理的关系

### 6.1 FAISS 不需要额外批处理

FAISS 本身已经高度优化，`index.search()` 内部会做批量向量计算，不需要外部再包批处理逻辑。

```python
import faiss

# FAISS 的 search 本身就是批量操作
query_vectors = np.array([...]).astype("float32")  # shape: (batch_size, dim)
D, I = index.search(query_vectors, k=10)
# 一次传入多个 query，内部批量计算
```

### 6.2 FAISS 管道的完整模式

```python
# 1. 建索引（批量 Embedding 加速）
vectors = list(model.embed(docs, batch_size=32))
vectors_np = np.array(vectors).astype("float32")

# 2. FAISS 索引
dim = vectors_np.shape[1]
index = faiss.IndexFlatIP(dim)    # Inner Product（内积）索引
faiss.normalize_L2(vectors_np)    # L2 归一化 → 内积 = 余弦相似度
index.add(vectors_np)

# 3. 检索
query_vec = np.array(list(model.embed([query]))[0]).astype("float32").reshape(1, -1)
faiss.normalize_L2(query_vec)
D, I = index.search(query_vec, k=20)  # D=相似度分数, I=文档索引
```

### 6.3 IndexFlatIP 与余弦相似度

```
L2 归一化后: 内积(IP) = 余弦相似度(Cosine)

证明: 
  Cosine(A,B) = A·B / (||A|| × ||B||)
  L2归一化后: ||A|| = ||B|| = 1
  → Cosine(A,B) = A·B = Inner Product
```

## 七、常见问题与避坑

### 7.1 OOM（显存/内存溢出）

```python
# 症状：batch_size=256 时报 CUDA out of memory

# 解决：逐步减半
batch_size = 128  # 报错 → 64 → 32 → 16（找到稳定值）

# 或者提前估算
# 每条文本 ~512 tokens × 768 维 × 4 bytes ≈ 1.5MB
# batch_size=32 → ~48MB，安全
```

### 7.2 批处理不一定总是更快

极端情况下批处理反而更慢：

| 场景 | 原因 | 建议 |
|------|------|------|
| 只有 1-2 条数据 | 批处理有 padding 开销 | 直接逐条处理 |
| 文本长度差异极大 | padding 浪费大量计算 | 先按长度排序再分批 |
| 模型太小 | 推理本身极快，批处理开销占比高 | 测一下再决定 |

### 7.3 动态 batching

真实系统中通常不会固定 batch_size，而是用**超时 + 攒批**策略：

```python
import asyncio

class DynamicBatcher:
    def __init__(self, max_batch=32, max_wait=0.05):
        self.max_batch = max_batch
        self.max_wait = max_wait  # 最多等 50ms
        self.queue = []
        self._event = asyncio.Event()

    async def add(self, text):
        self.queue.append(text)
        if len(self.queue) >= self.max_batch:
            self._event.set()  # 满了，立即触发
        
        # 等待超时或攒满
        await asyncio.wait_for(self._event.wait(), timeout=self.max_wait)
        # ... 执行批量编码
```

核心思想：**宁等 50ms 凑满一车，也不一辆一辆发车**。

## 八、核心要点速记

| 要点 | 一句话 |
|------|--------|
| 为什么批处理快 | 矩阵乘法天然并行，一次算 32 条 vs 算 32 次 |
| Embedding 批处理 | `model.embed(texts, batch_size=32)` 替代 for 循环 |
| Reranker 批处理 | 一次传入全部 passages，而非逐对调用 |
| 加速比 | Embedding 5-20x，Reranker 10-50x，管道总 10x+ |
| batch_size 选择 | 从 32 起，线性增长到拐点，OOM 则减半 |
| 管道优化 | 两个关键点：建索引(Embedding批量) + 重排(Rerank批量) |
| FAISS | 本身已批量优化，不需要额外批处理包装 |
| 动态 batching | 超时 + 攒批，平衡吞吐和延迟 |
