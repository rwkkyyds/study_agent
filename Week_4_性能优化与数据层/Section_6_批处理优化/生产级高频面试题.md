# Embedding / Reranker 批处理优化 — 生产级高频面试题

## 一、基础概念题

### Q1：为什么要对 Embedding 做批处理？单条推理和批量推理的本质区别是什么？

**回答要点：**

深度学习模型推理的核心是矩阵乘法。单条推理时矩阵形状是 `(1, dim)`，GPU/CPU 的并行计算单元大量空闲；批量推理时矩阵形状是 `(batch_size, dim)`，计算单元被充分利用。

```
单条：启动推理引擎 → 算1条 → 结束  (重复N次，引擎启停开销 × N)
批量：启动推理引擎 → 算32条 → 结束  (引擎启停开销 × 1)
```

加速比通常 5~20x，本质是把固定开销（kernel launch、内存分配、数据搬运）摊薄到多条数据上。

**面试加分：** 提到 "GPU utilization 从 10% 提升到 90%+"、"compute-bound vs io-bound 的区别"。

---

### Q2：batch_size 是不是越大越好？怎么选？

**回答要点：**

不是。存在边际递减效应：

| batch_size | 效果 |
|------------|------|
| 1→32 | 吞吐近似线性增长，GPU 从不饱和到饱和 |
| 32→128 | 增长放缓，GPU 已满载 |
| 128→512 | 几乎不增长，但内存占用翻倍，OOM 风险激增 |

选择策略：
- **离线建索引**：64-256，吞吐优先
- **在线 API**：8-32，延迟优先
- **GPU 推理**：32-128，充分利用并行
- **长文本**：用小 batch，因为单条内存占用大

**面试加分：** 提到"拐点法"——跑 benchmark 找吞吐不再显著提升的那个 batch_size。

---

### Q3：Embedding（Bi-Encoder）和 Reranker（Cross-Encoder）的批处理有什么区别？

**回答要点：**

| 维度 | Embedding (Bi-Encoder) | Reranker (Cross-Encoder) |
|------|------------------------|---------------------------|
| 输入 | 单条文本 | (query, doc) 对 |
| 编码方式 | query 和 doc 独立编码 | query+doc 拼接后一起过 Transformer |
| 单次推理代价 | 轻 | **重**（每对都要完整前向传播） |
| 批处理收益 | 有，5-20x | **更明显，10-50x** |
| 为什么 | 固定开销被摊薄 | 单次推理更重 → 固定开销占比更高 → 批处理节省更多 |

**一句话：Reranker 更需要批处理，因为单次推理代价更大。**

## 二、实战场景题

### Q4：线上 RAG 服务，用户 Query 来了就要实时返回，怎么做批处理？

**回答要点：**

在线服务不能等攒满一批再处理（延迟不可接受），但也不能逐条处理（吞吐太低）。解决方案是**动态 batching（超时 + 攒批）**：

```python
class DynamicBatcher:
    def __init__(self, max_batch=32, max_wait_ms=50):
        self.max_batch = max_batch
        self.max_wait = max_wait_ms / 1000  # 最多等 50ms
        self.queue = []
        self._event = asyncio.Event()

    async def add(self, text):
        self.queue.append((text, asyncio.get_event_loop().create_future()))
        if len(self.queue) >= self.max_batch:
            self._event.set()  # 满了，立即触发
        
        # 等待：要么攒满 max_batch，要么超过 max_wait_ms
        try:
            await asyncio.wait_for(self._event.wait(), timeout=self.max_wait)
        except asyncio.TimeoutError:
            pass  # 超时了，不再等，当前有多少算多少
        
        # 执行批量编码...
```

核心思想：**宁等 50ms 凑满一车，也不一辆一辆发车；但最多只等 50ms，不能无限等。**

**面试加分：** 提到 "Triton Inference Server 的动态 batching 实现" 或 "Ray Serve 的 batching decorator"。

### Q5：5000 条文档需要建向量索引，你怎么设计批量处理流程？写出关键步骤和 batch_size 选择依据。

**回答要点：**

```
Step 1: 加载模型（单例，只加载一次）
Step 2: 估算单条内存 → 选 batch_size
  - 每条 ~512 tokens × 768维 × 4字节 ≈ 1.5MB
  - 可用内存 8GB → 安全 batch_size ≈ 32-64
Step 3: 批量编码（batch_size=32）
  - 5000 ÷ 32 ≈ 157 次推理调用（而非 5000 次）
Step 4: 构建 FAISS 索引（IndexFlatIP + L2 归一化）
Step 5: 可选——分批建索引（数据量 > 100万时用 IVF 索引）
```

**关键代码：**

```python
# ❌ 错误：5000 次调用
for doc in docs:
    emb = model.embed([doc])

# ✅ 正确：~157 次调用
vectors = list(model.embed(docs, batch_size=32))
```

**面试加分：** 提到 "分批建索引 + 增量更新"、 "GPU 推理用更大 batch_size"。

### Q6：批处理时遇到 OOM 怎么办？排查步骤是什么？

**回答要点：**

**排查步骤：**

1. 先看错误信息：`CUDA out of memory` / `MemoryError` / `killed`
2. 确定是显存还是内存溢出（`nvidia-smi` / `htop`）
3. 逐步减半 batch_size：128 → 64 → 32 → 16 → 8，找到稳定值
4. 如果 batch_size=1 仍 OOM → 模型太大，换轻量模型或加硬件

**常见原因：**

| 原因 | 现象 | 解决 |
|------|------|------|
| batch_size 太大 | CUDA OOM | 减半 |
| 文本太长（>2048 tokens） | 单条就 OOM | 截断或分块 |
| 模型太大 | 加载就 OOM | 换 BGE-small / MiniLM 等轻量模型 |
| 内存泄漏 | 越跑越慢 | 检查是否重复加载模型 |

**面试加分：** 提到 "gradient checkpointing" "mixed precision (fp16)" "model offloading"。

### Q8：Embedding 模型更新了（换了一个更大的模型），线上服务如何平滑切换？需要考虑什么？

**回答要点：**

**核心问题：新旧模型生成的向量维度可能不同、语义空间不同 → 不能混用。**

**切换方案：**

```
方案 A：全量重索引（推荐，数据量 < 100万）
  1. 新模型加载到新服务（不停止旧服务）
  2. 后台任务用新模型对所有文档重新 Embedding
  3. 构建新 FAISS/Milvus 索引
  4. 流量一键切换到新索引
  5. 旧服务下线

方案 B：双写 + 渐进切换（数据量 > 100万）
  1. 新模型上线，所有新文档同时写旧索引和新索引
  2. 后台任务逐步迁移历史文档
  3. 按流量百分比灰度切换（10% → 50% → 100%）
  4. 对比新旧结果质量，确认无问题后全量切换
```

**必须考虑的坑：**

| 坑 | 说明 |
|----|------|
| 向量维度变化 | 新模型 768 维，旧模型 384 维 → 索引不兼容，必须重建 |
| 语义空间偏移 | 新旧向量的 cosine 相似度分布不同，阈值需重新校准 |
| 批量任务 OOM | 全量重索引时控制并发和 batch_size |
| 回滚方案 | 保留旧索引至少 24 小时，出问题可秒级回滚 |

## 四、对比与辨析

### Q9：批处理（batching）和异步并发（asyncio）有什么本质区别？各自适用什么场景？

**回答要点：**

| 维度 | 批处理（Batching） | 异步并发（asyncio） |
|------|-------------------|---------------------|
| 解决的问题 | **Compute-Bound**（CPU/GPU 计算密集） | **IO-Bound**（网络/磁盘等待） |
| 加速原理 | 一次处理多条，利用矩阵乘法并行 | 等待 IO 时切换执行其他协程 |
| 典型场景 | Embedding、Reranker 模型推理 | HTTP 请求、数据库查询、文件读写 |
| 是否需要多条数据 | 是（凑批） | 否（单条也能并发多个 IO） |
| CPU 是否空闲 | 否（满载计算） | 是（等在 IO 上） |
| Python 实现 | `model.embed(texts, batch_size=32)` | `async/await` + `asyncio.gather()` |

**一句话：快在计算上用批处理，慢在等待上用异步。两者可组合使用（异步攒批）。**

---

### Q10：为什么 FAISS 检索阶段不需要额外做批处理？

**回答要点：**

FAISS 本身就是为了向量批量计算设计的 C++ 库：

1. `index.search(query_vectors, k=10)` 天然接受多条 query，内部用 SIMD/BLAS 批量计算
2. 索引构建时已经对向量做了优化（如 IVF 聚类、PQ 量化）
3. 检索的计算量远小于 Embedding/Reranker（只是向量点积，没有 Transformer 前向传播）

**结论：FAISS 不需要外部再包批处理，直接传多条 query 即可。**

## 五、代码实战题

### Q11：写一个函数，给定 1000 条文本，用 fastembed 批量编码，对比 batch_size=1、8、32、64 的吞吐，输出最优 batch_size。

**参考实现：**

```python
import time
from fastembed import TextEmbedding

def find_optimal_batch_size(texts, batch_sizes=[1, 8, 16, 32, 64, 128]):
    model = TextEmbedding(model_name="BAAI/bge-small-zh-v1.5")
    results = []
    
    for bs in batch_sizes:
        t0 = time.perf_counter()
        # 跑 3 轮取平均
        for _ in range(3):
            list(model.embed(texts, batch_size=bs))
        avg_time = (time.perf_counter() - t0) / 3
        throughput = len(texts) / avg_time
        results.append((bs, throughput))
    
    # 找吞吐最高的
    best = max(results, key=lambda x: x[1])
    print(f"最优 batch_size={best[0]}, 吞吐={best[1]:.0f} docs/sec")
    return best[0]
```

**面试追问：** "如果文本长度差异很大（有的 10 字，有的 5000 字），怎么改进？"

**回答：** 按长度排序后分批，避免 padding 浪费——长短混合时，短文本被 pad 到长文本长度，浪费大量计算。先排序再分批可以让同批文本长度接近。

### Q12：RAG 管道中，检索返回 50 条候选，需要 Rerank 取 Top-5。写出 Naive（逐条）和 Optimized（批量）两种实现，并计算加速比。

**回答要点：**

```python
# Naive：逐条 Rerank（50 次推理调用）
results = []
for doc in top50_docs:
    request = RerankRequest(query=query, passages=[doc])
    scored = ranker.rerank(request)
    results.append(scored[0])
results.sort(key=lambda x: x["score"], reverse=True)
top5 = results[:5]

# Optimized：批量 Rerank（1 次推理调用）
request = RerankRequest(query=query, passages=top50_docs)
results = ranker.rerank(request)
top5 = results[:5]  # FlashRank 已按 score 降序
```

**加速比：** Reranker 单次推理开销大，50 次 → 1 次调用，加速比通常 10-30x。

## 六、面试杀手锏

### Q13（开放题）：你如何向一个不懂深度学习的产品经理解释"为什么批量处理比一条一条快"？

**参考答案：**

> "你可以把 GPU 想象成一辆公交车。一次拉一个人（单条处理），公交车的油费、司机工资、过路费（固定开销）都得摊到这一张票上，所以每张票很贵。一次拉 32 个人（批量处理），固定开销摊到 32 张票上，每张票就便宜很多。这就是为什么批量处理吞吐高——不是车跑得快了，而是每次拉的人多了。"
