# 02 - 检索服务

> 文件路径：`app/services/question_bank.py`

## 用途

`QuestionBankRetriever` 是阶段五的本地 RAG 检索器。

它负责把岗位名称、简历文本和难度转成检索条件，从本地题库里找出最匹配的问题，并把题库条目转换成面试工作流可以直接使用的 `InterviewQuestion`。

## 核心方法

### `search`

文件路径：`app/services/question_bank.py`

职责：

1. 从岗位和简历中抽取查询关键词
2. 按关键词重叠和难度匹配给题库打分
3. 返回排序后的题库条目

输入模型来自：`app/schemas/question_bank.py` 的 `QuestionBankSearchRequest`。

输出模型来自：`app/schemas/question_bank.py` 的 `QuestionBankSearchResponse`。

### `retrieve_for_interview`

文件路径：`app/services/question_bank.py`

职责：

1. 调用 `search`
2. 取 top_k 个检索结果
3. 转换为 `app/schemas/interview.py` 中的 `InterviewQuestion`
4. 给题目 ID 加上 `kb` 前缀，标识它来自题库检索

这个方法是面试工作流真正调用的入口。

### `extract_query_keywords`

文件路径：`app/services/question_bank.py`

职责：

- 从岗位标题中抽取岗位关键词
- 从简历文本中抽取技能关键词
- 去重并保留出现顺序

例如：

- AI 应用岗位会命中 RAG、Agent、LLM、向量、评估
- 后端岗位会命中 FastAPI、SQLAlchemy、JWT、数据库、缓存
- 简历中出现 Milvus、Docker、LangGraph，也会进入检索关键词

## 打分规则

当前打分是确定性的：

- 关键词重叠越多，分数越高
- 难度完全匹配会额外加分
- mid 难度题作为通用题有一定兜底加分

这不是最终推荐算法，而是一个可测试、可解释的检索替身。

## 为什么 service 层不直接返回原始 dict

题库数据是内部结构，API 和面试工作流需要稳定 schema。

因此 service 层会把原始题库 dict 转成：

- `QuestionBankItemResponse`
- `InterviewQuestion`

这样后续即使题库从 Python 文件换成数据库或向量库，对外响应仍然可以保持稳定。

## 学习重点

- 检索服务是 RAG 的边界层，不应该散落在 workflow 里
- 关键词检索虽然简单，但可以帮助理解召回、排序、top_k 的位置
- 返回对象要面向调用方，而不是暴露内部存储格式
- 后续向量化时，只需要替换检索实现，不需要推翻 API
