# 03 - 面试持久化

> 相关文件：`app/api/interviews.py`、`app/services/interviews.py`

## 用途

面试持久化负责把阶段一的临时结果保存到数据库。

阶段一中，题目和报告只存在于一次 HTTP 响应里。请求结束后，系统无法知道用户做过哪次面试、回答了什么、报告是什么。

阶段二加入持久化后，一次面试就变成可追踪的业务记录。

## 题目生成如何落库

题目生成接口在阶段二多了两个关键动作：

1. 解析当前登录用户
2. 保存面试会话和题目快照

整体流程：

```
用户携带 JWT 请求生成题目
  └── 后端解析当前用户
      └── 工作流生成题目
          └── 创建面试会话
              └── 保存每一道题目快照
                  └── 返回题目响应
```

这样做之后，前端拿到的 `session_id` 不只是一个临时字符串，而是能在数据库里找到对应面试记录。

## 回答评估如何落库

评分接口在阶段二多了归属校验：

1. 根据 `session_id` 查找面试会话
2. 确认会话属于当前登录用户
3. 调用评分工作流生成报告
4. 保存候选人回答
5. 保存评分报告
6. 更新会话状态

整体流程：

```
用户提交回答
  └── 后端解析当前用户
      └── 查找属于该用户的面试会话
          └── 生成评分报告
              └── 保存回答
              └── 保存报告
              └── 标记会话已评估
                  └── 返回报告响应
```

如果用户尝试评估别人的会话，系统会拒绝。

## 为什么要放到 service 层

路由层适合处理 HTTP 相关事情：

- 接收请求
- 注入当前用户
- 注入数据库会话
- 选择响应状态码

持久化服务适合处理业务动作：

- 调用工作流
- 创建会话
- 写入题目
- 保存回答
- 保存报告
- 更新状态

这样拆分后，路由更薄，业务流程更清楚，未来如果新增 CLI、后台任务或异步队列，也能复用服务层逻辑。

## 状态设计

面试会话有状态字段。

阶段二至少区分：

| 状态 | 含义 |
|------|------|
| `questions_generated` | 已生成题目，等待候选人回答 |
| `evaluated` | 已提交回答并生成报告 |

后续多轮面试可以继续扩展：

- `in_progress`
- `waiting_follow_up`
- `completed`
- `archived`

## 学习重点

- 持久化不是简单“保存响应”，而是把业务生命周期记录下来
- 归属校验必须在写入回答和报告之前完成
- service 层可以让 HTTP 细节和业务流程分开
- 会话状态是后续做多轮面试、报告页和历史列表的基础
