# 06 - 阶段二请求流程

> 阶段二中，从用户登录到面试数据落库的完整请求生命周期。

## 注册和登录流程

```
用户提交注册信息
  └── 校验用户名和密码
      └── 检查用户名是否重复
          └── 对密码做哈希
              └── 保存用户
```

```
用户提交登录信息
  └── 查询用户
      └── 校验密码哈希
          └── 生成 JWT
              └── 返回 Bearer Token
```

登录成功后，客户端需要在后续请求中携带 Token。后端不会记住某个浏览器是否登录，而是每次请求都通过 Token 重新识别用户。

## 生成题目流程

```
客户端请求 /interviews/questions
  └── 请求头携带 Bearer Token
      └── 后端解析当前用户
          └── Pydantic 校验简历和岗位输入
              └── 面试工作流生成题目
                  └── 创建面试会话记录
                      └── 保存题目快照
                          └── 返回题目响应
```

和阶段一相比，这里新增了两件事：

- 请求必须知道当前用户是谁
- 生成结果必须写入数据库

## 提交回答和生成报告流程

```
客户端请求 /interviews/evaluate
  └── 请求头携带 Bearer Token
      └── 后端解析当前用户
          └── 根据 session_id 查找当前用户的面试会话
              └── 如果找不到，拒绝请求
              └── 如果找到，执行评分工作流
                  └── 保存候选人回答
                  └── 保存评分报告
                  └── 更新会话状态
                      └── 返回报告响应
```

这个流程的关键点是“先校验归属，再保存结果”。

如果不做归属校验，只要别人猜到或拿到一个 `session_id`，就可能操作不属于自己的面试记录。

## 数据写入顺序

阶段二推荐的写入顺序是：

1. 生成题目时先保存会话
2. 再保存题目快照
3. 提交回答时先确认会话归属
4. 再保存回答
5. 再保存报告
6. 最后更新会话状态

这个顺序符合业务生命周期，也方便排查问题。

## 错误路径

阶段二常见错误路径包括：

| 场景 | 结果 |
|------|------|
| 未携带 Token | 拒绝访问受保护接口 |
| Token 无效或过期 | 拒绝访问受保护接口 |
| 用户不存在或被禁用 | 拒绝访问受保护接口 |
| 非 admin 调用管理员接口 | 返回权限不足 |
| 评估不存在的会话 | 返回会话不存在 |
| 评估其他用户的会话 | 返回会话不存在，避免暴露数据存在性 |

最后一条很重要：系统不应该告诉攻击者“这个会话存在但不是你的”，直接返回找不到更安全。

## 阶段二到后续阶段的扩展

阶段二已经把用户和数据归属打通，后续可以继续扩展：

- 阶段三：简历解析结果保存到会话或候选人画像表
- 阶段四：LangGraph 节点读写面试状态
- 阶段五：RAG 根据题目、回答、简历项目生成追问
- 阶段六：前端根据登录状态展示面试历史和报告
- 阶段七：Docker Compose 中用 PostgreSQL 持久化正式数据

## 学习重点

- 工业系统的请求流程通常包括认证、校验、业务、持久化、响应
- 越权校验要靠数据库条件限制，而不是只在前端隐藏按钮
- `session_id` 是业务标识，用户 ID 是权限边界
- 数据写入顺序应该贴合真实业务生命周期
