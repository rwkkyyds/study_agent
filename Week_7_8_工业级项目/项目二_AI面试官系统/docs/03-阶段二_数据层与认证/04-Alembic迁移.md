# 04 - Alembic 迁移

> 相关文件：`alembic.ini`、`alembic/env.py`、`alembic/versions/`

## 用途

Alembic 用来管理数据库结构变化。

没有迁移工具时，团队很容易出现“我的数据库有这个字段，你的没有”“测试库和生产库结构不一致”的问题。迁移脚本的意义就是让数据库结构像代码一样可以被版本化、审查和重复执行。

## 为什么阶段二要补初始迁移

阶段二新增了用户、面试会话、题目、回答和报告模型。如果只写 ORM 模型，不写迁移，数据库本身并不会自动可靠地变成对应结构。

初始迁移相当于项目数据库的第一条基线：

- 从空数据库创建全部阶段二表
- 明确主键、唯一约束、外键关系
- 保留后续迁移的起点
- 让本地、测试、生产可以使用同一套结构演进方式

## Alembic 目录职责

| 文件或目录 | 作用 |
|------------|------|
| `alembic.ini` | Alembic 主配置，指定迁移目录和数据库连接配置 |
| `alembic/env.py` | 迁移运行环境，加载应用配置和 ORM 元数据 |
| `alembic/script.py.mako` | 新迁移文件的模板 |
| `alembic/versions/` | 保存每一个迁移版本 |

## 初始迁移包含什么

阶段二初始迁移创建五类表：

- 用户表
- 面试会话表
- 面试题目表
- 候选人回答表
- 面试报告表

迁移中还定义了关键约束：

- 用户名唯一，避免重复账号
- 会话 ID 唯一，方便接口通过 `session_id` 定位一次面试
- 面试会话关联用户，保证数据归属
- 题目、回答、报告关联面试会话，形成完整面试链路
- 报告和会话保持一对一关系，避免一次面试出现多份最终报告

## ORM 模型和迁移的关系

ORM 模型描述“应用认为数据应该长什么样”。

迁移脚本描述“数据库应该如何从当前结构变成目标结构”。

两者要保持一致，但不能混为一谈。工业项目里，不能只依赖开发环境自动建表，因为生产数据库需要可控、可回滚、可审查的变更流程。

## 学习重点

- ORM 模型不是迁移脚本的替代品
- 初始迁移是数据库版本管理的起点
- 外键关系体现业务归属和生命周期
- 每次改模型时，都要思考是否需要新增迁移
- 迁移脚本应该可以在空数据库上稳定执行
