# 02 - 数据模型

> 相关文件：`app/models/user.py`、`app/models/security.py`、`app/models/interview.py`

## 用途

数据模型把业务对象变成数据库可以保存、查询和关联的结构。

阶段二的核心不是“建几张表”，而是把一次面试拆成可以复盘、可以扩展、可以权限隔离的数据关系。

## 用户模型

用户模型保存账号和权限相关信息：

| 字段类型 | 业务含义 |
|----------|----------|
| 用户名 | 登录标识，需要唯一 |
| 密码哈希 | 用于登录校验，不能保存明文 |
| 角色 | 兼容当前接口的粗粒度角色，支持 candidate/interviewer/hr/admin |
| 启用状态 | 支持后续禁用用户 |
| 创建时间 | 记录账号创建时间 |

用户是一切业务数据的归属起点。

## 认证与权限模型

阶段八高可用方案要求阶段二补上企业级认证权限底座，因此新增了 `app/models/security.py`：

| 模型 | 业务含义 |
|------|----------|
| `Organization` | 组织/租户边界，后续支持多公司、多团队 |
| `Role` | 角色定义，支持全局角色和组织内角色 |
| `Permission` | 权限点定义，为 RBAC/ABAC 扩展预留 |
| `UserRole` | 用户、组织和角色关系 |
| `RolePermission` | 角色和权限点关系 |
| `AuditLog` | 注册、登录、刷新、退出、管理员操作等关键审计 |

当前接口仍优先使用 `users.role` 做简单角色校验，这是为了保持已有前后端和测试兼容。新增 RBAC 表是企业级扩展底座，不等于已经完成完整权限系统；后续还需要把后台菜单、按钮、资源归属和权限策略接入。

## 面试会话模型

面试会话代表一次模拟面试。

它保存：

- 会话 ID
- 用户 ID
- 简历文本
- 目标岗位
- 难度
- 候选人摘要
- 当前状态
- 创建和更新时间

为什么要单独有“会话”？

因为题目、回答、报告都属于同一次面试。如果没有会话层，后续很难做历史记录、报告详情、多轮追问和状态管理。

## 题目模型

题目模型保存某次面试生成出来的题目快照。

保存快照很重要，因为后续题目生成逻辑可能升级。如果不保存当时的问题，只保存最终回答，用户回看报告时就不知道自己当时回答的是哪道题。

题目快照通常包括：

- 题目 ID
- 题型
- 题干
- 期望要点
- 来源

## 回答模型

回答模型保存候选人对题目的作答。

它和面试会话关联，也记录对应的题目 ID。

阶段二只保存一次提交的回答。后续如果做多轮面试，可以扩展为“轮次”“追问 ID”“回答时间”“音频转写结果”等字段。

## 报告模型

报告模型保存一次面试的评分结果。

报告不是一个简单分数，而是一组结构化复盘信息：

- 总分
- 通过级别
- 评分维度
- 优势
- 风险
- 追问题
- 学习建议

这些字段目前适合用 JSON 保存，因为它们是列表或对象结构，后续如果要做复杂统计，可以再拆成更细的数据表。

## 数据关系

```
User
  ├── AuditLog
  ├── UserRole
  └── InterviewSession
      ├── InterviewQuestion
      ├── InterviewAnswer
      └── InterviewReport

Organization
  └── Role
      └── RolePermission
          └── Permission
```

这个关系表达了三个重要事实：

- 一个用户可以有多次面试
- 一个用户可以有多条审计日志和多种组织内角色
- 一次面试可以有多道题和多个回答
- 一次面试通常对应一份最终报告
- 组织、角色、权限表为后续 HR/面试官/Admin 权限拆分预留空间

## 学习重点

- 数据建模要从业务生命周期出发，而不是从接口字段机械复制
- 会话表常用于连接“输入、过程、结果”
- 快照数据可以保护历史记录不受未来逻辑变化影响
- 权限模型要区分“当前兼容字段”和“长期 RBAC 结构”
- 审计日志是安全合规数据，不能只靠应用日志替代
- JSON 字段适合早期保存半结构化报告，但统计需求变强后可以继续拆表
