# 01 - 认证体系

> 相关文件：`app/api/auth.py`、`app/services/auth.py`、`app/services/audit.py`、`app/models/user.py`、`app/models/security.py`

## 用途

认证体系解决“当前请求是谁发起的”这个问题。

在阶段一里，任何人都可以调用面试接口。阶段二开始，面试数据需要归属到具体用户，因此系统必须先识别用户，再允许用户生成题目或提交回答。

按阶段八企业级高可用方案调整后，阶段二不再只停留在“能登录”，而是补齐 Token 生命周期、退出失效、登录防爆破和关键操作审计。

## 核心能力

### 用户注册

注册用于创建候选人账号。

候选人账号默认是 `candidate` 角色，适合发起模拟面试、提交回答、查看自己的报告。

注册阶段最重要的不是“写入一个用户”，而是保护两个规则：

- 用户名不能重复
- 密码不能明文保存

### 密码哈希

数据库中保存的是密码哈希，不是原始密码。

哈希的意义是：即使数据库泄露，攻击者也不能直接拿到用户原始密码。

学习时要记住：密码哈希和加密不是一回事。密码哈希通常不可逆，系统登录时是把用户输入的密码再次哈希校验，而不是把数据库中的值“解密”回来。

### 用户登录

登录做四件事：

1. 检查用户名是否触发登录失败限流
2. 校验用户名和密码是否匹配
3. 校验通过后签发 access token 和 refresh token
4. 写入登录审计日志

JWT 是一种无状态令牌。后端把用户 ID、角色、用途、过期时间、`jti` 等信息放进令牌里，并使用密钥签名。客户端之后每次请求都带上 access token，后端就能识别用户。

refresh token 用于换取新的 access token。阶段二企业级调整后，refresh token 每次使用都会轮换，旧 refresh token 会进入黑名单，避免长期凭证被重复使用。

### 退出登录和黑名单

纯 JWT 本身是无状态的，签发后只要没过期就能继续使用。企业系统需要支持退出登录和强制失效，因此引入 token 黑名单：

- 配置 Redis 时写入 `jwt:blacklist:{jti}`，TTL 对齐 token 剩余有效期
- 未配置 Redis 时使用进程内回退，方便本地开发和测试
- `/auth/logout` 会让当前 access token 立即失效，也可以同步失效 refresh token

### 当前用户解析

受保护接口会读取请求头中的 Bearer Token。

后端验证 Token 签名、用途、过期时间和黑名单状态后，取出用户 ID，再去数据库查询用户是否存在、是否启用。

这一步很关键：Token 能证明“这个请求声称是谁”，数据库查询能确认“这个用户当前仍然有效”。

### 角色权限

项目二目前支持四个角色：

| 角色 | 权限 |
|------|------|
| `candidate` | 发起面试、提交回答、查看自己的数据 |
| `interviewer` | 后续用于查看分配候选人、补充人工评价 |
| `hr` | 后续用于管理岗位、候选人、批次和报告流转 |
| `admin` | 管理组织、用户、题库和系统配置 |

阶段二仍保留 `users.role` 字段做兼容，但已新增 `organizations`、`roles`、`permissions`、`user_roles`、`role_permissions` 表作为 RBAC 底座。使用过 RBAC 表不等于已经掌握完整权限系统，后续还需要把后台菜单、按钮、资源归属和审计策略接进来。

### 登录限流和审计

登录失败会按用户名计数，超过阈值后返回 429，降低暴力破解风险。

关键认证动作会写入 `audit_logs`：

- 注册
- 登录成功、失败、被限流
- refresh token 轮换
- logout
- admin 创建用户

## 为什么面试接口要认证

面试系统不是匿名问答工具，它会保存简历、回答和评分报告。

这些数据天然属于用户个人数据，因此必须满足：

- A 用户不能评估 B 用户的面试会话
- 未登录用户不能创建持久化面试记录
- 退出登录后旧 token 不能继续访问受保护接口
- 报告、历史记录、学习建议都能归属到具体候选人

## 学习重点

- 认证解决“你是谁”，权限解决“你能做什么”
- 密码永远不要明文保存
- JWT 适合无状态 API，但退出登录、强制下线和 refresh 轮换需要服务端状态
- Redis 在认证体系里不是口号，而是承载黑名单和登录失败限流的状态存储
- 审计日志让安全事件可追踪，但后续还需要配合查询、脱敏和告警
- 用户 ID 是后续所有业务数据归属的根
