# 01 - 认证体系

> 相关文件：`app/api/auth.py`、`app/services/auth.py`、`app/models/user.py`

## 用途

认证体系解决“当前请求是谁发起的”这个问题。

在阶段一里，任何人都可以调用面试接口。阶段二开始，面试数据需要归属到具体用户，因此系统必须先识别用户，再允许用户生成题目或提交回答。

## 核心能力

### 用户注册

注册用于创建候选人账号。

候选人账号默认是 `candidate` 角色，适合发起模拟面试、提交回答、查看自己的报告。

注册阶段最重要的不是“写入一个用户”，而是保护两个规则：

- 用户名不能重复
- 密码不能明文保存

### 密码哈希

数据库中保存的是密码哈希，不是原始密码。

哈希的意义是：即使数据库泄露，攻击者也不能直接拿到用户原始密码。

学习时要记住：密码哈希和加密不是一回事。密码哈希通常不可逆，系统登录时是把用户输入的密码再次哈希校验，而不是把数据库中的值“解密”回来。

### 用户登录

登录做两件事：

1. 校验用户名和密码是否匹配
2. 校验通过后签发 JWT

JWT 是一种无状态令牌。后端把用户 ID、角色、过期时间等信息放进令牌里，并使用密钥签名。客户端之后每次请求都带上这个令牌，后端就能识别用户。

### 当前用户解析

受保护接口会读取请求头中的 Bearer Token。

后端验证 Token 签名和过期时间后，取出用户 ID，再去数据库查询用户是否存在、是否启用。

这一步很关键：Token 能证明“这个请求声称是谁”，数据库查询能确认“这个用户当前仍然有效”。

### 角色权限

项目二目前有两个角色：

| 角色 | 权限 |
|------|------|
| `candidate` | 发起面试、提交回答、查看自己的数据 |
| `admin` | 管理用户，后续可扩展查看全局面试数据 |

阶段二只实现了基础角色校验。后续如果权限变复杂，可以继续演进为权限表、策略对象或 RBAC 模型。

## 为什么面试接口要认证

面试系统不是匿名问答工具，它会保存简历、回答和评分报告。

这些数据天然属于用户个人数据，因此必须满足：

- A 用户不能评估 B 用户的面试会话
- 未登录用户不能创建持久化面试记录
- 报告、历史记录、学习建议都能归属到具体候选人

## 学习重点

- 认证解决“你是谁”，权限解决“你能做什么”
- 密码永远不要明文保存
- JWT 适合无状态 API，但仍要结合数据库确认用户是否有效
- 用户 ID 是后续所有业务数据归属的根
