# 05 - 测试策略

> 相关文件：`tests/conftest.py`、`tests/test_auth.py`、`tests/test_interview_workflow.py`

## 用途

阶段二测试的重点是保护“认证 + 数据落库 + 用户隔离”这些工业项目核心行为。

如果只测试接口能返回 200，并不能说明系统安全可靠。真正需要验证的是：谁能访问、数据是否保存、用户之间是否隔离、数据库是否被测试污染。

## 测试夹具

阶段二使用测试夹具统一创建 TestClient 和临时数据库。

这样每个测试都可以在干净环境中运行，不依赖本地开发数据库，也不会把测试数据写进真实 `interviewer_dev.db`。

测试夹具主要解决三个问题：

- 创建独立 SQLite 内存数据库
- 建立阶段二所有 ORM 表
- 覆盖 FastAPI 的数据库依赖，让接口使用测试数据库

## 认证测试

认证测试覆盖注册、登录、当前用户和管理员能力。

重点验证：

| 测试方向 | 保护的业务规则 |
|----------|----------------|
| 注册 | 新用户能创建，默认是候选人角色 |
| 登录 | 正确用户名密码能换取 Token |
| 当前用户 | Token 能被解析为数据库中的用户 |
| 管理员创建用户 | 只有 admin 能创建指定角色用户 |
| 管理员用户列表 | admin 能查看用户列表 |

这些测试保护的是认证系统的最小闭环。

## 面试持久化测试

面试测试从阶段一的“返回结构正确”升级为“接口行为和数据库状态都正确”。

重点验证：

- 未登录不能访问面试题生成接口
- 登录后可以生成题目
- 生成题目后数据库中存在面试会话
- 生成题目后数据库中存在题目快照
- 提交回答后数据库中存在回答
- 提交回答后数据库中存在报告
- 用户不能评估其他用户的面试会话

## 为什么要测试用户隔离

用户隔离是阶段二最重要的安全规则。

如果 A 用户可以拿着 B 用户的 `session_id` 提交回答或查看报告，那么系统就存在严重的数据越权问题。

因此，测试里要故意创建两个用户，并验证第二个用户无法操作第一个用户的面试会话。

## 为什么不用真实数据库测试

真实数据库适合做集成测试，但不适合所有单元或接口测试都依赖它。

阶段二使用临时 SQLite 的原因：

- 启动快
- 不需要 Docker
- 每个测试隔离
- 不污染开发数据
- 可以稳定在 CI 中运行

后续如果接 PostgreSQL，可以增加单独的集成测试层，而不是替换当前快速测试。

## 学习重点

- 测试要保护业务规则，而不是只追求覆盖率数字
- 测试数据库必须和开发数据库隔离
- 认证系统一定要测失败路径和越权路径
- 持久化测试要同时看 HTTP 响应和数据库结果
- 好的测试能让后续重构服务层、工作流、数据库模型时更放心
