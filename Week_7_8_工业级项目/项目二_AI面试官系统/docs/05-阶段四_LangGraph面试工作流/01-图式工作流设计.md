# 01 - 图式工作流设计

> 核心文件路径：`app/workflow/interview_graph.py`

## 为什么要从函数改成图式工作流

阶段一到阶段三中，面试题生成和评分主要是通过 `InterviewWorkflow` 的方法完成。这个方式简单直接，但随着功能增加，会遇到几个问题：

- 简历解析、岗位画像、题目生成混在一起，不方便单独替换
- 追问、评分、报告之间缺少清晰边界
- 后续接 LangGraph 时，很难判断哪些逻辑应该变成节点
- 调试时看不到一次请求到底经过了哪些步骤

阶段四通过 `InterviewGraphState` 和多个节点方法，把工作流拆成更接近 LangGraph 的结构。

## 当前实现方式

当前没有强制安装真实 LangGraph 包，而是用本地类模拟 LangGraph 思路：

- `InterviewGraphState` 保存工作流状态
- 每个节点接收并更新同一个 state
- 节点按固定顺序执行
- 响应里返回 `workflow_trace` 记录节点执行顺序

这样做的好处是：

- 测试稳定，不受 LLM 或外部服务影响
- 节点边界先稳定，后续可以平滑迁移
- API、service、数据库结构可以先跑通
- 学习时能看清“图工作流”的基本形态

## 文件路径说明

| 路径 | 说明 |
|------|------|
| `app/workflow/interview_graph.py` | 真正的阶段四图式工作流实现 |
| `app/workflow/interview.py` | 兼容导出入口，service 层仍从这里导入 `InterviewWorkflow` |
| `app/services/interviews.py` | 调用 workflow，并负责数据库持久化 |
| `app/api/interviews.py` | HTTP 路由入口，不直接关心节点细节 |

## 状态对象

`InterviewGraphState` 是节点之间传递的信息容器。

它包含：

- 简历文本
- 岗位名称
- 难度
- 会话 ID
- 简历信号
- 岗位画像
- 候选人摘要
- 题目列表
- 回答文本
- 维度分数
- 追问题
- 优势和风险
- 学习建议
- 节点执行轨迹

在真实 LangGraph 中，这个 state 可以迁移为 StateGraph 的状态定义。

## 学习重点

- 图式工作流的关键不是“用了某个库”，而是把业务步骤拆成明确节点
- state 是节点之间传递上下文的核心
- 节点 trace 对调试和教学非常有用
- service 层不应该知道每个节点细节，它只调用工作流门面
