# 阶段三：简历解析与岗位画像

> 把候选人的 text、markdown、PDF 简历解析成结构化画像，并让面试题生成可以复用画像。

## 阶段定位

阶段一解决“能不能生成题和评分”，阶段二解决“数据属于谁、能不能保存”。

阶段三开始进入 AI 面试官系统的核心业务：理解候选人的简历。

这一阶段仍然不急着接 LLM，而是先用确定性规则完成可测试的解析能力。后续 LangGraph 或 LLM Agent 可以替换解析逻辑，但画像结构、接口契约和持久化方式先稳定下来。

## 阶段目标

- 支持 text 简历解析
- 支持 markdown 简历解析和上传
- 支持 PDF 简历上传解析
- 抽取技能栈、项目经历、年限和岗位匹配关键词
- 形成候选人画像并保存到数据库
- 面试题生成接口支持通过 `resume_profile_id` 复用画像
- 用户只能读取和使用自己的候选人画像
- 补充阶段三测试和迁移

## 本阶段学什么

| 学习点 | 重点理解 |
|--------|----------|
| 简历解析入口 | 文本提交和文件上传为什么要分成两个接口 |
| 内容标准化 | 为什么 markdown/PDF 要先变成统一文本 |
| 候选人画像 | 简历原文如何转成可复用的结构化对象 |
| 岗位画像 | 目标岗位如何影响关键词和后续追问方向 |
| 数据归属 | 画像为什么必须绑定用户 |
| 面试联动 | 题目生成为什么不应该每次重新解析简历 |
| 测试边界 | 如何测试解析结果、上传流程和用户隔离 |

## 新增接口

| 接口 | 用途 | 是否登录 |
|------|------|----------|
| `POST /resumes/parse` | 解析 text/markdown 简历正文 | 是 |
| `POST /resumes/upload` | 上传 text/markdown/PDF 简历并解析 | 是 |
| `GET /resumes/{profile_id}` | 读取当前用户自己的候选人画像 | 是 |
| `POST /interviews/questions` | 新增支持 `resume_profile_id` 生成题目 | 是 |

## 候选人画像包含什么

画像不是完整简历的替代品，而是面试系统可直接使用的结构化摘要：

- 简历来源类型
- 原始文本
- 标准化文本
- 候选人摘要
- 技能栈
- 项目经历摘要
- 年限
- 岗位匹配关键词

## 数据闭环

```
用户
  └── 候选人画像
      └── 面试会话
          ├── 题目快照
          ├── 候选人回答
          └── 评分报告
```

阶段三之后，面试题生成不再只能依赖一次请求里的简历文本，也可以复用之前解析好的画像。

## 验收标准

- text 简历可解析并保存画像
- markdown 简历可上传并标准化
- PDF 上传路径已接入解析能力
- 画像中能抽取技能、项目、年限和岗位关键词
- 用户不能读取其他用户的画像
- 题目生成可通过 `resume_profile_id` 使用画像
- Alembic 迁移可以创建阶段三表和关联字段
- `python -m pytest -q` 通过
