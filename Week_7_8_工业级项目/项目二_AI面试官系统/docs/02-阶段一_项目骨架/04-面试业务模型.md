# 04 - 面试业务模型

> 相关文件：`app/schemas/interview.py`、`app/workflow/interview.py`

## 用途

面试业务模型定义了系统最核心的输入、输出和中间对象。

阶段一先不追求模型智能，而是先回答几个问题：

- 候选人需要输入什么？
- 系统生成的问题长什么样？
- 候选人的回答如何提交？
- 评分报告应该包含哪些维度？
- 后续 LLM 或 LangGraph 要替换哪个位置？

## 请求模型

### 题目生成请求

题目生成请求描述一次模拟面试的起点：

| 字段 | 业务含义 |
|------|----------|
| 简历文本 | 用于识别候选人的项目、技能和经历 |
| 目标岗位 | 决定题目方向和追问重点 |
| 难度 | 控制题目深度，当前支持初级、中级、高级 |
| 题目数量 | 控制一次面试生成多少道题 |

这里的校验规则很重要。

比如简历文本不能太短，岗位名称不能为空，题目数量不能无限大。这些限制不是为了“刁难用户”，而是为了保护后端工作流的输入质量。

### 回答提交请求

回答提交请求代表候选人完成一轮答题后的输入：

| 字段 | 业务含义 |
|------|----------|
| 会话 ID | 指向哪一次面试 |
| 岗位名称 | 用于报告中的岗位上下文 |
| 回答列表 | 每道题对应的候选人回答 |

阶段二以后，会话 ID 还承担数据归属校验：用户只能提交和评估自己的面试会话。

## 响应模型

### 面试题响应

一次题目生成会返回：

- 会话 ID
- 岗位名称
- 难度
- 候选人简要画像
- 题目列表

每道题包含题目 ID、题型、题干、期望要点和来源。

“来源”字段很关键，因为后续接 RAG 或简历解析时，需要知道这道题来自岗位通用能力、简历项目、知识库，还是面试官追问策略。

### 评分报告响应

评分报告不是只给一个总分，而是拆成多个可学习的部分：

- 总分
- 通过级别
- 评分维度
- 优势
- 风险
- 追问题
- 学习建议

这个结构更接近真实面试复盘。

候选人不只想知道“我是多少分”，更想知道“哪里像真实项目、哪里容易被追问、下一步怎么补”。

## 确定性工作流

阶段一的工作流使用规则而不是 LLM：

1. 从简历文本中识别弱信号，例如 RAG、Agent、后端、前端、部署
2. 根据岗位、难度和简历信号生成题目
3. 根据回答中的关键词计算维度分
4. 汇总为报告、风险和学习建议

这套规则的作用是“模拟未来智能工作流的形状”。

后续接 LangGraph 时，可以把每个步骤替换成 Agent 节点，但 API 输出结构不变。

## 后续替换点

| 当前阶段一模块 | 后续替换方向 |
|----------------|--------------|
| 简历关键词识别 | 简历解析 Agent，支持 PDF、Markdown、项目抽取 |
| 题目生成规则 | LangGraph 节点 + 岗位题库 RAG |
| 评分关键词规则 | Rubric 评分 Agent + 多维度证据分析 |
| 固定追问题 | 根据回答动态追问 |

## 学习重点

- Schema 是前后端和工作流之间的合同
- 先定义稳定输出，比一开始追求 AI 效果更重要
- 题目、回答、报告都应该结构化，否则后续无法检索、复盘和可视化
- 面试系统的价值在“可反馈、可追问、可沉淀”，不只是生成几道题
