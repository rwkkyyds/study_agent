# 05 - 接口与测试

> 相关文件：`app/api/health.py`、`app/api/interviews.py`、`tests/`

## 阶段一接口说明

### GET /health

健康检查接口用于确认服务是否正常运行。

它通常给开发者、部署系统、负载均衡器或容器健康检查使用。

学习重点不是返回内容有多复杂，而是理解：每个后端服务都应该有一个非常轻量、非常稳定的探活入口。

### GET /health/ready

就绪检查接口用于判断服务是否已经准备好处理业务请求。

阶段一没有真实外部依赖，所以它返回就绪。后续可以扩展为检查数据库、Redis、向量库或 LLM Provider 是否可用。

健康检查和就绪检查的区别：

| 接口 | 更关注什么 |
|------|------------|
| `/health` | 进程是否活着 |
| `/health/ready` | 服务是否能处理业务 |

### POST /interviews/questions

题目生成接口是面试系统的入口。

它接收简历、岗位、难度和题目数量，返回结构化面试题。

阶段一重点验证：

- 输入太短时会被拒绝
- 简历中出现 RAG、Agent、Docker 等信号时，会影响题目类型
- 返回的题目数量符合请求
- 每道题都有题型、题干、期望要点和来源

### POST /interviews/evaluate

评分接口接收一次面试的回答，输出评分报告。

阶段一重点不是评分多么准确，而是报告结构是否完整。

报告至少应该回答：

- 候选人整体表现如何
- 哪些维度强、哪些维度弱
- 有哪些可继续追问的问题
- 候选人下一步应该怎么补

## 测试说明

阶段一测试重点是接口行为，而不是内部实现。

| 测试方向 | 验证点 |
|----------|--------|
| 健康检查 | 服务基础路由可访问 |
| 就绪检查 | 服务可以进入业务请求状态 |
| 题目生成 | 输入简历和岗位后返回结构化题目 |
| 输入校验 | 太短的简历会触发校验错误 |
| 评分报告 | 提交回答后返回完整报告 |

## 为什么使用 TestClient

`TestClient` 可以在不启动真实 Uvicorn 服务的情况下测试 FastAPI 接口。

它直接调用应用对象，模拟 HTTP 请求和响应。

这样做的优势：

- 测试速度快
- 不占用端口
- 不依赖浏览器或 curl
- 可以在 CI 中稳定运行
- 可以很方便地覆盖依赖，例如数据库连接

## 测试的学习方法

写测试时不要只看“有没有通过”，还要看它保护了什么业务假设：

- 面试题必须可结构化展示
- 简历太短不应该进入工作流
- 评分报告不能只有总分
- 后续换成 LLM 后，接口响应结构仍应保持一致

## 学习重点

- 接口测试应该验证业务契约，而不是复制实现细节
- 阶段一测试越稳定，后续替换工作流越放心
- 错误输入也要测试，因为真实用户不会总是输入理想数据
- 测试名称应表达业务意图，让后续复习时能读懂系统能力
