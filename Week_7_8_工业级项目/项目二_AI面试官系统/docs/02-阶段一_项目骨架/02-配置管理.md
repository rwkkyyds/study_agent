# 02 - 配置管理

> 文件路径：`app/core/config.py`

## 用途

配置管理用于集中处理不同环境下会变化的值，例如数据库地址、JWT 密钥、应用版本、CORS 来源。

这些值不应该散落在业务代码里，否则后续迁移环境、部署 Docker、接 PostgreSQL、替换密钥时会非常痛苦。

## 核心对象

### Settings

`Settings` 是项目的配置中心。

它负责从默认值、环境变量和 `.env` 文件中读取配置，统一提供给应用入口、数据库层和认证服务。

当前关键配置包括：

| 配置项 | 作用 |
|--------|------|
| `app_name` | 应用名称，用于文档和健康信息 |
| `app_version` | 应用版本，便于部署和排障 |
| `environment` | 当前环境，例如 development、testing、production |
| `cors_origins` | 允许访问后端的前端来源 |
| `database_url` | 数据库连接字符串 |
| `jwt_secret_key` | JWT 签名密钥 |
| `jwt_algorithm` | JWT 签名算法 |
| `jwt_expire_minutes` | Token 有效期 |

### get_settings

`get_settings` 是缓存后的配置读取入口。

它的意义不是“少写几行代码”，而是避免每次请求都重新解析环境变量，同时确保项目里读取配置的方式统一。

## 配置加载原则

```
环境变量 > .env 文件 > 默认值
```

这个顺序适合工业项目：

- 本地开发可以直接用默认值
- 个人环境可以写 `.env`
- CI/CD 和生产环境可以用环境变量覆盖

## 为什么不能把密钥写死

JWT 密钥、数据库密码、LLM API Key 都属于敏感配置。

如果写进代码仓库，会带来几个问题：

- 泄露后无法追踪是谁使用了密钥
- 多环境共用密钥，风险扩大
- 团队协作时容易把个人配置提交进去
- 生产部署时需要改代码，不符合自动化部署习惯

阶段二虽然仍以本地 SQLite 为主，但配置体系已经为 PostgreSQL、Docker、真实密钥留好位置。

## 学习重点

- 配置是应用边界，不是业务逻辑
- 默认值用于降低本地启动成本，不代表生产可直接使用
- 所有会随环境变化的值，都应该优先进入 Settings
- 后续接 Docker Compose 时，环境变量会成为服务编排的核心连接方式
