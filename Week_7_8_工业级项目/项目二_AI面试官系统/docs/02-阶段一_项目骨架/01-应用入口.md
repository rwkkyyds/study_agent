# 01 - 应用入口

> 文件路径：`app/main.py`

## 用途

应用入口负责把分散的业务模块组装成一个可运行的 FastAPI 服务。

它不是放业务逻辑的地方，而是负责应用级配置：创建应用实例、注册中间件、挂载路由、暴露 OpenAPI 文档。

## 核心职责

### 创建 FastAPI 应用

应用实例定义了项目在 OpenAPI 文档中展示的名称、版本和描述。

这些信息来自统一配置，而不是写死在多个地方，后续部署到测试、生产环境时更容易维护。

### 注册 CORS 中间件

CORS 用于允许前端页面跨域访问后端接口。

阶段一虽然还没有前端，但先把 CORS 作为应用基础能力放进来，是为了后续阶段接 React 或 Next.js 面试页面时不用再改应用结构。

### 注册路由

项目二目前按业务模块拆路由：

| 路由模块 | 负责内容 |
|----------|----------|
| `health` | 健康检查、就绪检查 |
| `auth` | 用户注册、登录、当前用户、管理员用户管理 |
| `interviews` | 面试题生成、回答评估 |

阶段一重点关注 `health` 和 `interviews`，阶段二开始真正启用 `auth` 和数据库持久化。

## 为什么入口层不写业务逻辑

入口层应保持薄。

如果把题目生成、评分、数据库操作都堆到 `main.py`，后续项目会很快失控：

- 路由难以测试
- 工作流难以替换
- 数据库逻辑难以复用
- 文档和代码都不容易定位

更好的做法是让入口层只做“组装”，业务逻辑下沉到 `api`、`services`、`workflow` 等模块。

## 依赖关系

```
app/main.py
  ├── app.core.config        应用配置
  ├── app.api.health         健康检查路由
  ├── app.api.auth           认证路由
  └── app.api.interviews     面试业务路由
```

## 学习重点

- 一个 FastAPI 项目通常从“应用入口 + 路由模块 + 服务层”开始拆
- `main.py` 越稳定，后续新增业务模块越轻松
- 路由注册顺序一般不承载业务含义，真正的业务边界应体现在模块划分上
- OpenAPI 文档来自路由、Schema、响应模型和字段描述，所以入口层要清晰注册路由
