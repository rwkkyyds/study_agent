# 阶段一：项目骨架与最小业务闭环

> 建立 AI 面试官系统的 FastAPI 基础框架，先跑通“简历输入 -> 生成题目 -> 提交回答 -> 输出报告”的最小闭环。

## 阶段定位

阶段一不是为了做出最聪明的 AI，而是为了把业务对象、接口契约、测试基线和后续扩展点固定下来。

如果一开始就接 LLM、RAG、LangGraph，很容易在模型效果里迷路，反而看不清系统到底需要哪些输入、输出和状态。

本阶段使用确定性规则工作流，目的是让每次测试都稳定、每个接口都能被前端或后续 Agent 工作流复用。

## 阶段目标

- 搭建 FastAPI 应用入口，注册健康检查、认证、面试业务路由
- 建立统一配置体系，集中管理应用名、版本、数据库、JWT 等配置
- 建立 SQLAlchemy 会话基础，为阶段二数据落库做准备
- 定义面试请求与响应模型，明确系统输入输出
- 实现确定性面试工作流，生成题目和评分报告
- 编写基础测试，保证接口可以重复验证

## 本阶段学什么

| 学习点 | 重点理解 |
|--------|----------|
| Web 应用入口 | FastAPI 应用如何创建、配置中间件、注册路由 |
| 配置管理 | 为什么要把环境差异放到 Settings，而不是散落在代码里 |
| 数据库会话 | 为什么请求级数据库 Session 要通过依赖注入管理 |
| Pydantic Schema | API 契约如何约束请求字段、响应结构和校验规则 |
| 业务工作流 | 如何先用稳定规则模拟未来的 LLM/Agent 流程 |
| 接口测试 | 不启动真实服务也能用 TestClient 验证 HTTP 行为 |

## 当前接口

| 接口 | 用途 | 阶段一关注点 |
|------|------|--------------|
| `GET /health` | 服务健康检查 | 服务是否启动、基础路由是否可用 |
| `GET /health/ready` | 服务就绪检查 | 后续可扩展数据库、Redis、LLM 检查 |
| `POST /interviews/questions` | 根据简历和岗位生成题目 | 校验输入，返回结构化题目 |
| `POST /interviews/evaluate` | 根据回答生成评分报告 | 形成评分维度、追问和学习建议 |

## 为什么阶段一不用 LLM

阶段一先不用 LLM，是一个刻意的工程选择：

- **测试稳定**：确定性规则不会因为模型随机性导致测试忽然失败
- **契约稳定**：前后端先围绕固定请求响应开发
- **方便定位问题**：接口错了就是业务或结构问题，不会混入模型不可控因素
- **方便替换**：后续把规则工作流替换成 LangGraph 时，不需要推翻 API 形状

可以把阶段一理解成“先搭轨道，再换引擎”。轨道包括路由、Schema、测试、目录结构和核心业务对象。

## 完成标准

- 应用可以启动，并能访问 OpenAPI 文档
- `/health` 返回服务正常
- `/health/ready` 返回服务就绪
- 题目生成接口能根据简历关键词生成结构化问题
- 评分接口能根据回答生成报告、分数、风险和追问
- 测试可以通过，并覆盖健康检查和面试基础闭环
