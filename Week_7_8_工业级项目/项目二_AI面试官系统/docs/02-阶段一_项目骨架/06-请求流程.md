# 06 - 请求流程

> 阶段一中，一次 AI 面试请求从进入后端到返回结果的完整过程。

## 应用启动流程

```
启动 Uvicorn
  └── 导入 app.main
      └── 读取 Settings 配置
      └── 创建 FastAPI 应用
      └── 注册 CORS 中间件
      └── 注册 health/auth/interviews 路由
      └── 等待 HTTP 请求
```

阶段一启动时的关键不是“做了多少事”，而是应用结构已经可以承载后续功能。

认证、面试、健康检查是独立路由模块，后续加简历解析、题库、报告导出时不会都挤在入口文件里。

## 题目生成流程

```
客户端提交简历和岗位
  └── FastAPI 匹配 /interviews/questions
      └── Pydantic 校验请求字段
          └── 面试工作流抽取简历信号
              └── 生成候选人摘要
              └── 根据岗位和信号生成题目
              └── FastAPI 序列化响应
                  └── 返回 session_id 和 questions
```

这个流程里最重要的是 Pydantic 校验和结构化响应。

只要输入输出稳定，后面把“规则生成题目”替换成“LangGraph + LLM 生成题目”，调用方也不用大改。

## 回答评估流程

```
客户端提交 session_id 和回答列表
  └── FastAPI 匹配 /interviews/evaluate
      └── Pydantic 校验回答结构
          └── 面试工作流分析回答关键词
              └── 计算多个评分维度
              └── 汇总总分和通过级别
              └── 生成优势、风险、追问题、学习建议
                  └── 返回评分报告
```

阶段一的评分规则很简单，但报告结构是面试系统真正的产品形态。

后续无论评分由规则、LLM 还是人工校准模型完成，最终都应该落到可复盘、可学习的报告上。

## 测试流程

```
运行 pytest
  └── 创建 TestClient
      └── 调用健康检查接口
      └── 调用题目生成接口
      └── 调用评分接口
      └── 校验状态码和响应结构
```

测试覆盖的是“系统对外承诺”，不是内部每一行实现。

这让后续重构更安全：只要对外行为不变，内部工作流可以逐步升级。

## 阶段一到阶段二的变化

阶段一：

```
请求 -> 校验 -> 工作流 -> 响应
```

阶段二：

```
请求 -> JWT 认证 -> 校验 -> 工作流 -> 数据落库 -> 响应
```

阶段二多了两个工业项目必备能力：

- 知道“是谁”发起了面试
- 能把每次面试过程保存下来，支持复盘和后续分析

## 学习重点

- 请求流程图能帮助你判断每层代码应该放在哪里
- 校验、认证、业务、持久化是不同职责，不要混成一坨
- 阶段一虽然简单，但已经把后续工业级能力的插槽留出来
- 读一个后端项目时，先画请求流程，比直接钻进代码更容易建立全局感
