# 03 - 数据层基础

> 文件路径：`app/db/session.py`

## 用途

数据层基础负责建立 SQLAlchemy 的数据库连接能力，包括引擎、会话工厂、模型基类和请求级数据库依赖。

阶段一主要是铺好基础，阶段二开始真正让用户、面试会话、问题、回答和报告落库。

## 核心组件

### Base

`Base` 是所有 ORM 模型的声明式基类。

项目中的用户模型、面试会话模型、问题模型、回答模型、报告模型都会继承它。

可以把 `Base` 理解成“所有数据表模型的共同登记处”。Alembic 做迁移对比时，也需要从这里知道有哪些模型。

### engine

`engine` 是 SQLAlchemy 和数据库之间的连接入口。

它根据 `database_url` 判断连接 SQLite 还是 PostgreSQL。

阶段一默认使用 SQLite，因为它无需额外服务，适合学习和快速验证。阶段二以后保留切换 PostgreSQL 的能力，避免未来改造时推翻数据层。

### SessionLocal

`SessionLocal` 是数据库会话工厂。

每次请求需要访问数据库时，都会创建一个独立 Session，用完后关闭。

这比全局共用一个 Session 更安全，因为 HTTP 请求是并发的，不同用户、不同请求之间不应该共享事务状态。

### get_db

`get_db` 是 FastAPI 的数据库依赖入口。

路由或服务需要数据库时，通过依赖注入拿到当前请求的 Session。请求结束后，Session 会被关闭。

## 请求级 Session 的意义

```
HTTP 请求进入
  └── 创建数据库 Session
      └── 路由和服务层执行查询或写入
          └── 提交或回滚事务
      └── 请求结束关闭 Session
```

这种模式解决了三个问题：

- **隔离性**：每个请求独立管理数据库状态
- **可测试性**：测试中可以替换 `get_db`，使用内存数据库
- **可维护性**：业务层不用关心连接创建和关闭细节

## SQLite 与 PostgreSQL 的关系

阶段一和阶段二默认 SQLite，原因是学习成本低。

但项目结构按 PostgreSQL 方向设计：

- 用 ORM 模型描述数据结构
- 用 Alembic 管理迁移
- 用 `DATABASE_URL` 切换数据库
- 业务层不直接依赖 SQLite 特性

后续真正部署时，可以将 `DATABASE_URL` 换成 PostgreSQL 连接字符串。

## 学习重点

- `engine` 管连接，`Session` 管一次业务操作中的数据状态
- Web 项目里不要长期持有全局数据库 Session
- 数据库依赖注入是测试隔离的关键
- ORM 模型、迁移脚本、数据库三者需要保持一致
