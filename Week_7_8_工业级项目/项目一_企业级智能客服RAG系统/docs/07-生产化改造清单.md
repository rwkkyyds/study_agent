# 生产化改造清单

> 基于当前项目代码（阶段一至六）的系统性审计结果，列出从"学习型项目"升级为"生产级项目"需要替换和增强的所有点，按优先级分类。

## 一、总览

当前项目可以概括为：

```text
能运行、能测试、有文档
    ↓ 但
Embedding 是哈希、向量库在内存、订单是占位、
回答没有 LLM、数据库是 SQLite、注册能提权成 admin
    ↓
距离生产级还有三类差距：必须替换 / 强烈建议 / 生产增强
```

---

## 二、P0：必须替换（不替换无法上线）

### 1. 数据库：SQLite → PostgreSQL

| 项 | 现状 | 问题 |
|----|------|------|
| 连接 | `app/db/session.py` 已支持 `DATABASE_URL` 切换 | 但 `requirements.txt` 缺少 PostgreSQL 驱动 `psycopg2-binary`，docker-compose 切到 PostgreSQL 后应用启动即失败 |
| 方言 | `app/models/document.py` 第 1 行 `from sqlalchemy.dialects.sqlite import JSON` | **生产硬伤**：PostgreSQL 下 SQLite 专用 JSON 类型不可用，建表直接报错 |
| 建表 | `init_db()` 用 `create_all` | 生产需要 Alembic 迁移管理 schema 变更 |

**替换方案**：
- `requirements.txt` 增加 `psycopg2-binary`
- `document.py` 改用通用 `from sqlalchemy import JSON`
- 引入 Alembic，编写初始迁移，替换 `create_all`

### 2. Embedding：MockEmbedding → 真实 Embedding Provider

**现状**（`app/rag/embeddings.py`）：SHA-256 哈希文本，生成 768 维伪向量。

**问题**：哈希没有语义，语义相近的句子向量完全不相似，检索质量趋近于零。当前客服回答"命中"知识库本质上靠关键词巧合。

**替换方案**（接口已对齐，替换成本低）：

| 方案 | 说明 |
|------|------|
| OpenAI `text-embedding-3-small` | 1536 维，质量高，需要 API Key |
| 通义/百度/智谱 embedding | 国内可用，需要 API Key |
| `fastembed`（BGE 系列本地模型） | 本地推理，无需外部 API，离线可用 |

替换点：只改 `Retriever.__init__` 中 embedding 的构造，测试中保留 MockEmbedding。

### 3. 向量库：InMemoryVectorStore → Milvus / pgvector

**现状**（`app/rag/vector_store.py`）：进程内字典 + 暴力余弦搜索。

**问题**：
- 重启即丢，知识库入库后不持久化
- 单进程内存上限，无法承载企业级文档量
- 多实例部署时每个实例的向量库互相独立
- 无 HNSW/IVF 索引，数据量大后检索退化为全表扫描

**替换方案**：
- **Milvus**：docker-compose 已预留模板，启动后替换 `Retriever` 的 vector_store
- **pgvector**：如果希望数据库单一化，用 PostgreSQL 扩展，适合 <100 万向量场景

### 4. 回答生成：无 LLM → 接入真实 LLM（RAG 的核心闭环）

**现状**（`app/workflow/customer_service.py` `_knowledge_search`）：检索到文本块后**直接返回第一块原文**，没有 LLM 总结。

**问题**：这不是 RAG，是"文档回显"。用户得到的答案没有组织、没有引用、没有上下文整合。

**替换方案**：

```text
检索 Top-K 块
    ↓
拼装 Prompt（系统指令 + 检索片段 + 用户问题）
    ↓
LLM 生成答案（OpenAI / 通义 / 本地 vLLM / Ollama）
    ↓
返回 answer + sources 引用
```

替换点：`CustomerServiceWorkflow._knowledge_search` 增加 LLM 生成步骤，接口不变。

### 5. 订单工具：占位替身 → 真实订单服务

**现状**（`app/tools/customer_service.py` `lookup_order`）：返回固定文案"订单系统适配器将在后续阶段接入"。

**问题**：`order` 意图的请求不会得到任何真实业务数据。

**替换方案**：
- 通过 HTTP 调用真实订单服务（带超时、重试、熔断——阶段五的 `call_with_retry` + `CircuitBreaker` 正好复用）
- 区分四种结果：参数不完整 / 订单不存在 / 服务超时 / 服务熔断

## 三、P1：强烈建议（安全和可靠性硬伤）

### 6. 注册接口允许客户端指定角色（严重安全漏洞）

**现状**（`app/schemas/auth.py`）：

```python
role: str = Field(default="customer", pattern="^(admin|agent|customer)$")
```

**问题**：任何客户端可以 `POST /auth/register` 直接注册 `admin` 账号，拿到全部管理员权限。**这是当前项目最严重的安全问题。**

**替换方案**：
- 注册接口固定 `role="customer"`，不接受客户端传入
- 管理员/客服账号由已有 admin 通过内部管理接口创建，或由部署时脚本初始化
- `test_auth.py` 中注册测试同步调整为不传 role

### 7. JWT_SECRET_KEY 无强制校验

**现状**（`app/core/config.py`）：默认 `"change-me-in-env"`，不配置也能启动。

**问题**：生产环境若漏配，Token 可被任何人伪造签名。

**替换方案**：config 中校验 `environment == "production"` 时 `jwt_secret_key` 必须是强随机值（≥32 字节），否则启动失败。

### 8. 登录接口无限流（暴力破解风险）

**现状**：`POST /auth/login` 没有限流，攻击者可以无限尝试密码。

**替换方案**：把阶段五的 `SlidingWindowRateLimiter` 复用到 `/auth/login`，按 IP + 用户名双维度限流。

### 9. 意图分类：关键词 → 模型分类

**现状**（`IntentClassifier`）：只匹配"人工/订单"等 6 个关键词，漏判率极高，如"我要退货怎么办"（退货不在关键词表，实际走 knowledge）。

**替换方案**：
- LLM 结构化分类（few-shot + JSON 输出）
- 或部署轻量文本分类模型（fasttext / BGE-classify）

### 10. 多 worker 指标不共享

**现状**（`app/stability/metrics.py`）：进程内 Counter，Dockerfile 配置 `--workers 2`。

**问题**：两个 worker 各自计数，`/metrics` 看到的只有当前 worker 的数据，总量被低估。

**替换方案**：使用 `prometheus-client` 库（多进程模式 `PROMETHEUS_MULTIPROC_DIR`）或推送聚合网关。

### 11. 会话记忆本地回退在多实例下失效

**现状**：Redis 不可用时回退进程内字典，多实例部署时每个实例只能看到自己的会话。

**问题**：生产多实例 + Redis 故障时，用户多轮对话上下文断裂。

**替换方案**：生产环境强制要求 Redis（启动时校验），本地回退仅限 development 环境。

## 四、P2：生产增强（体验与运维）

### 12. 结构化日志

**现状**：`logging.basicConfig` 纯文本日志，无 trace id、无请求上下文。

**替换方案**：JSON 结构化日志（`python-json-logger`），中间件生成 `request_id` 贯穿请求链路。

### 13. API 版本化

**现状**：`/auth`、`/chat` 无版本前缀。

**替换方案**：`/api/v1/auth`、`/api/v1/chat`，为后续 v2 变更留空间。

### 14. CORS 配置

**现状**：无 CORS 中间件，前端接入会被浏览器拦截。

**替换方案**：配置 `CORSMiddleware`，允许域名白名单（生产不要 `*`）。

### 15. /health 依赖检测

**现状**：只返回 `{"status": "ok"}`，不检查 PostgreSQL / Redis 是否可用。

**替换方案**：`/health/live`（存活）+ `/health/ready`（就绪，检测 DB/Redis 连通性）。

### 16. 反向代理与 HTTPS

**现状**：`/metrics` 直接暴露在公网端口。

**替换方案**：docker-compose 增加 Nginx 服务，`/metrics` 只允许内网访问，443 终止 TLS。

### 17. 业务 API 缺口

| 缺口 | 说明 |
|------|------|
| 文档上传 API | `Document`/`Chunk` 模型存在但没有 `POST /documents` 入库接口，知识库内容无法在生产环境写入 |
| 工单处理 API | `Ticket` 模型存在但 agent 无法领取/处理/关闭工单 |
| 会话上下文注入 | `SessionMemory` 已保存历史但未注入 LLM Prompt，多轮对话没有利用 |

### 18. 密码哈希升级

**现状**：`passlib` 的 `pbkdf2_sha256`（可用但非最优）。

**替换方案**：`bcrypt`（requirements 已含 `passlib[bcrypt]`，直接切换 `bcrypt.hash`）。

## 五、替换优先级路线图

```text
第一步（先修硬伤，半天）
  ├── 6. 注册提权漏洞（P1 最高危）
  ├── 1. psycopg2-binary + JSON 方言修复（PostgreSQL 切换前提）
  └── 7. JWT 密钥生产校验

第二步（让 RAG 真正可用，1-2 天）
  ├── 2. 真实 Embedding（fastembed 本地方案最快）
  ├── 3. 向量库迁移 Milvus（docker-compose 启用）
  └── 4. LLM 回答生成 + 会话上下文注入

第三步（服务接入与加固，1-2 天）
  ├── 5. 真实订单服务 + 熔断重试
  ├── 8. 登录限流
  ├── 9. LLM 意图分类
  └── 18. bcrypt 密码哈希

第四步（运维完善，持续）
  ├── 10. prometheus-client 多进程指标
  ├── 11. 生产强制 Redis
  ├── 12-16. 日志、版本化、CORS、健康检查、Nginx
  └── 17. 文档上传 + 工单处理 API
```

## 六、总结

| 优先级 | 数量 | 一句话 |
|--------|------|--------|
| P0 必须替换 | 5 | 数据库、Embedding、向量库、LLM、订单服务 |
| P1 强烈建议 | 6 | 注册提权、JWT 密钥、登录限流、意图分类、指标、Redis |
| P2 生产增强 | 7 | 日志、版本化、CORS、健康检查、Nginx、业务 API、密码哈希 |

当前项目作为**学习型项目**已经完整交付（六阶段闭环、36 个测试全绿）。生产化改造的关键判断是：**接口边界已经为替换预留好了**（`Retriever` 可注入 embedding/vector_store，`IntentClassifier` 可替换，`CustomerServiceTools` 是门面），所以大部分替换是"换实现、不改接口"，风险可控。
