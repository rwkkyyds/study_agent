# 01 - 稳定性架构

> 相关代码：`app/stability/`、`app/api/chat.py`、`app/main.py`

## 一、稳定性要解决什么问题

阶段四的 `/chat` 已经可以完成意图分类和工具调用，但它默认每个依赖都正常、每个用户都按正常速度请求、每个进程都拥有完整状态。在真实环境中，这些假设都不成立。

阶段五采用“入口保护 + 状态外置 + 失败隔离 + 指标观测”的思路：

1. 在进入工作流前做用户级限流，防止流量直接冲击后端。
2. 将短期会话记忆放进 Redis；没有 Redis 时使用本地实现，方便学习和测试。
3. 为未来的订单、LLM、向量库调用提供重试和熔断边界。
4. 用低基数指标记录系统运行情况，不把用户问题和敏感信息写入指标。

## 二、完整请求流程

```text
HTTP 请求
  │
  ▼
FastAPI 路由
  │
  ▼
get_current_user
  │  解析 JWT，得到 current_user.id
  ▼
SlidingWindowRateLimiter.allow(user_id)
  │
  ├── False → record 429 → 返回 HTTP 429
  └── True
       │
       ▼
SessionMemory.append(user_id, user, query)
       │
       ▼
CustomerServiceWorkflow.run(...)
       │
       ├── knowledge → Retriever
       ├── order     → Order Tool
       └── human     → Ticket Tool
       │
       ▼
SessionMemory.append(user_id, assistant, answer)
       │
       ▼
Metrics.record_request(200, intent)
       │
       ▼
ChatResponse
```

这里有一个重要的安全边界：限流和会话记忆使用的是 JWT 校验后的 `current_user.id`，而不是请求体提供的用户编号。客户端不能通过修改请求体绕过其他用户的限流或读取其他用户的会话。

## 三、组件一：滑动窗口限流

### 1. 为什么选择滑动窗口

固定窗口实现简单，但在窗口边界可能出现短时间内两倍流量。例如上一分钟最后一秒请求 60 次，下一分钟第一秒又请求 60 次，系统在两秒内实际承受了 120 次请求。滑动窗口按最近一段连续时间统计，边界突发更平滑。

### 2. Redis 实现流程

Redis 模式使用 Sorted Set：

```text
key = customer-service:ratelimit:{user_id}

1. 删除 window_seconds 之前的成员
2. 写入当前请求，score 是当前时间戳，member 使用 UUID 保证唯一
3. ZCARD 统计窗口内请求数
4. 设置 key TTL
5. 超过 limit 时删除刚写入的成员并拒绝
```

请求成员必须唯一。如果直接使用时间戳作为 member，高并发下同一时间戳可能覆盖旧请求，导致计数偏小。

### 3. 本地回退实现

未配置 `REDIS_URL`、未安装 Redis 客户端或 Redis `PING` 失败时，使用带锁的 `deque` 保存每个身份的单调时钟记录。它能满足单进程测试和本地开发，但不能在多实例之间共享计数，因此生产多实例必须使用 Redis。

## 四、组件二：会话记忆

`SessionMemory` 保存最近的 user 和 assistant 消息，主要用于后续将上下文传给 LLM 或排查一次会话的处理过程。

写入过程：

1. 校验内容不能是空白。
2. 记录 `role`、`content` 和 UTC `timestamp`。
3. Redis 模式执行 `RPUSH`。
4. 用 `LTRIM` 只保留最近 `SESSION_MAX_MESSAGES` 条。
5. 用 `EXPIRE` 刷新会话 TTL。

会话记忆不是永久审计日志，不应该无限增长，也不应该保存密码、JWT、API Key 或完整外部响应。

## 五、组件三：指标

`Metrics` 当前不强制依赖 `prometheus_client`，而是直接输出 Prometheus 文本格式。这样项目在没有监控依赖时也能运行。

当前指标：

| 指标 | 含义 |
|------|------|
| `customer_service_requests_total` | 进入客服处理的请求总数 |
| `customer_service_rate_limited_total` | 被限流的请求总数 |
| `customer_service_http_responses_total` | 按状态码统计响应数量 |
| `customer_service_intents_total` | 按 `knowledge/order/human` 统计意图数量 |

指标标签只能使用有限枚举值。不能把 `query`、`username`、订单号等高基数或敏感数据作为标签。

## 六、故障降级边界

```text
Redis 正常       → 共享限流 + 共享会话
Redis 未配置/异常 → 进程内限流 + 进程内会话
知识库无结果      → 业务答复引导转人工
外部服务连续失败  → 重试后熔断，由上层返回降级结果
```

降级的目标是“可控地少做一些事”，而不是假装外部服务调用成功。后续接入真实订单服务时，应明确区分“查询不到订单”“订单服务超时”和“订单服务熔断”。

## 七、生产注意事项

- 多实例部署必须配置 Redis，否则每个实例都有独立的限流计数。
- `JWT_SECRET_KEY` 使用至少 32 字节随机值。
- Redis 账号限制在项目 key 前缀范围内，并启用网络访问控制。
- `/metrics` 只开放给监控网络，不直接暴露给普通用户。
- 外部 HTTP 客户端必须设置连接超时、读取超时和最大重试次数。
