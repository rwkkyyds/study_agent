# 05 — 项目总结与后续规划

> 回顾整个企业级智能客服 RAG 系统的技术演进路径，总结每个阶段的核心决策，以及后续可以继续完善的方向。

## 一、六个阶段的技术演进

```text
阶段一：安装 FastAPI → 配置管理 → 数据库会话 → 健康检查
    ↓
阶段二：数据模型（User/Document/Ticket/Message）
    ↓       JWT 认证（注册/登录/角色权限）
    ↓
阶段三：MockEmbedding（不依赖外部 API）
    ↓       InMemoryVectorStore（余弦相似度）
    ↓       TextChunker（重叠分块）+ Retriever
    ↓
阶段四：IntentClassifier（意图分类）
    ↓       LangGraph StateGraph（条件路由）
    ↓       CustomerServiceWorkflow（知识/订单/转人工）
    ↓
阶段五：滑动窗口限流（Redis + 本地回退）
    ↓       SessionMemory（会话保留）
    ↓       call_with_retry（有限重试+指数退避）
    ↓       CircuitBreaker（熔断+半开探测）
    ↓       Metrics（Prometheus 文本指标）
    ↓
阶段六：多阶段 Dockerfile（最小化镜像）
          Docker Compose（App + PostgreSQL + Redis）
          部署文档 + 运维指南
```

## 二、每个阶段的核心决策

### 阶段一：为什么选择 SQLite 而不是 PostgreSQL

本地开发环境不一定有 PostgreSQL，SQLite 零配置即可运行。阶段一使用 SQLite 降低启动成本，阶段六再切换到 PostgreSQL。

### 阶段二：为什么 JWT 而不是 Session

客服系统不需要持久会话，JWT 在客户端保存 Token，服务端无状态。后续阶段添加 Redis 后，只是把短期状态放到 Redis 中，JWT 本身仍然无状态。

### 阶段三：为什么使用 MockEmbedding

真实 Embedding 需要调用外部 API 或下载模型，在本地开发和学习场景中，MockEmbedding 可以稳定生成确定性向量，减少外部依赖。切换到生产时，只需要替换 `embeddings.py` 中的实现。

### 阶段四：为什么使用 LangGraph 而不是原生代码

客服路由可以写成 `if-else`，但后续的状态管理和多 Agent 编排会变得复杂。LangGraph 的 StateGraph 提供了可观测的条件路由和状态管理，适合后续扩展。

### 阶段五：为什么先做稳定性而非功能

在功能可用之后，生产环境的第一个风险不是功能缺失，而是系统在异常情况下的行为。先做限流、熔断和指标，确保系统在故障时可控。

### 阶段六：为什么使用多阶段构建

单阶段构建的镜像体积大，包含编译工具和缓存。多阶段构建分离编译和运行，最终镜像只包含运行时所需的最小文件。

## 三、项目整体技术栈

| 层 | 技术选型 | 替代方案 |
|----|----------|----------|
| Web 框架 | FastAPI | Flask, Django |
| 数据库 | SQLite / PostgreSQL | MySQL, MariaDB |
| ORM | SQLAlchemy 2.0 | Tortoise-ORM, Django ORM |
| 向量库 | InMemory / Milvus | Pinecone, Qdrant |
| 缓存 | Redis | Memcached, Dragonfly |
| 认证 | JWT + SHA-256 | OAuth 2.0, Session |
| 工作流 | LangGraph | LangChain, AutoGen |
| 监控 | Prometheus 文本格式 | OpenTelemetry, Datadog |
| 容器化 | Docker + Docker Compose | Kubernetes, Podman |

## 四、项目亮点

- **零外部 API 依赖**：所有阶段可以在无网络、无 API Key 的本地环境中完成开发和测试。
- **渐进式复杂度**：每个阶段只引入一个核心概念，不会同时引入多个新框架。
- **可替换架构**：MockEmbedding 可替换为真实 Embedding，InMemory 可替换为 Milvus，SQLite 可替换为 PostgreSQL，每个替换点都通过接口隔离。
- **测试先行**：每个阶段交付代码的同时交付测试，阶段一交付健康检查测试，阶段二交付认证测试，以此类推。
- **文档同步**：每个阶段交付代码、测试和文档，文档解释为什么这样设计，而不是只记录命令行。

## 五、后续可以继续完善的方向

### 短期（1-2 周）

- **真实 LLM 接入**：替换 MockLLM，接入 OpenAI、通义千问或本地大模型。
- **真实 Embedding 接入**：替换 MockEmbedding，接入 fastembed 或 text-embedding-3-small。
- **文档上传 API**：实现 `POST /documents` 接口，支持上传 PDF、Markdown 等格式。
- **Swagger 鉴权按钮**：在 Swagger 页面配置 Authorize 按钮，方便测试。

### 中期（1-2 个月）

- **前端接入**：React + Tailwind 的客服聊天界面，支持 SSE 流式响应。
- **Alembic 数据库迁移**：使用 Alembic 管理数据库迁移，支持生产环境有序变更。
- **OpenTelemetry 集成**：替换简单的 Prometheus 指标，加入完整的链路追踪。
- **Grafana 仪表盘**：可视化 Prometheus 指标，构建监控大盘。
- **工单管理系统**：实现工单的分配、处理和关闭流程。

### 长期（3-6 个月）

- **Kubernetes 部署**：将 Docker Compose 迁移到 Kubernetes 集群。
- **多语言支持**：通过 i18n 支持多语言客服。
- **A/B 测试框架**：支持不同检索策略和 LLM 配置的对比实验。
- **CI/CD 流水线**：自动化测试、构建和部署。
- **性能压测**：使用 Locust 或 k6 进行性能基准测试，确定系统容量。
