# 02 客服工具设计

## 1. `search_knowledge`

输入用户问题和 `top_k`，调用阶段三 `Retriever.search()`，返回 `RetrievedChunk`。工具不负责生成答案、不重复 Embedding、不记录敏感原文日志。

## 2. `lookup_order`

当前是订单系统适配器的本地替身，返回 `order_id`、`status` 和 `message`。阶段五或后续接入真实订单服务时，应补充超时、鉴权、重试、幂等和脱敏日志。

## 3. `transfer_to_human`

创建 `Ticket(status=open)`，再写入一条 `Message(sender_role=system)`，最后提交同一数据库事务。返回 `ticket_id`，供 API 和前端展示。

## 4. 工具边界

| 工具 | 读写范围 | 当前实现 | 后续替换 |
|------|----------|----------|----------|
| `search_knowledge` | 读取向量检索结果 | `Retriever` | Milvus + 权限过滤 |
| `lookup_order` | 读取订单摘要 | 本地适配器 | 订单服务 API |
| `transfer_to_human` | 写入工单和消息 | SQLAlchemy | 工单服务 + 事件总线 |

## 5. 安全要求

人工转接只能使用已经通过 JWT 校验的 `current_user.id`，不能从客户端请求体接收任意 `customer_id`。知识库和订单查询在生产环境必须增加租户、用户权限和数据脱敏过滤。
