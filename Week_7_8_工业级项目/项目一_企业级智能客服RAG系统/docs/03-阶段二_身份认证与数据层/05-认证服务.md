# 05 - 认证服务

> 对应文件：`app/services/auth.py`

认证服务把业务逻辑从 API 路由中分离出来，让路由只负责接收请求、注入依赖和返回响应。

## 函数清单

| 函数 | 作用 |
|------|------|
| `hash_password()` | 生成 PBKDF2-SHA256 密码哈希 |
| `verify_password()` | 验证明文密码 |
| `create_user()` | 检查重复用户名并创建用户 |
| `authenticate_user()` | 查询用户并校验密码 |
| `create_access_token()` | 生成带过期时间的 JWT |
| `get_current_user()` | 解析 Token 并查询当前用户 |
| `require_role()` | 生成角色校验依赖 |

## 一、create_user()

执行步骤：

1. 根据 `username` 查询已有用户。
2. 已存在则抛出 `400 用户名已存在`。
3. 调用 `hash_password()`。
4. 创建 `User` ORM 对象。
5. `db.add()` 放入会话。
6. `db.commit()` 提交事务。
7. `db.refresh()` 获取数据库生成的 id 和时间。
8. 返回用户对象。

## 二、authenticate_user()

```text
查询 username
  │
  ├── 找不到 → None
  └── 找到 → verify_password()
                 ├── 失败 → None
                 └── 成功 → User
```

API 层收到 `None` 后统一返回 `401 用户名或密码错误`，避免泄露“用户名是否存在”。

## 三、get_current_user()

这是一个 FastAPI 依赖函数，不是普通的业务接口。它依赖：

- `HTTPBearer()`：从请求头提取 Bearer Token。
- `get_db()`：获取数据库会话。

任何路由写出 `Depends(get_current_user)`，就会自动获得已验证的 `User`。

## 四、require_role()

`require_role("agent")` 返回一个新的依赖函数 `role_checker`。它先调用 `get_current_user()`，再判断：

```text
当前角色 == 要求角色？
    是 → 允许
    否，但当前角色是 admin → 允许
    否 → 403
```

当前 API 尚未挂载业务角色接口，但这个依赖已经为后续工单和管理接口准备好。

## 五、服务层边界

服务层不负责：

- 解析 HTTP JSON；
- 定义路由路径；
- 直接返回 HTTP 成功响应。

这些职责分别属于 Schema 和 API 层。
