# 07 - 角色权限与依赖注入

## 一、认证和授权不是一回事

| 概念 | 问题 | 本项目实现 |
|------|------|------------|
| 认证 Authentication | 你是谁？ | JWT + 数据库查询 |
| 授权 Authorization | 你能做什么？ | `require_role()` |

`/auth/me` 当前只验证身份。后续业务接口还要叠加角色权限。

## 二、FastAPI 依赖链

```text
路由函数
  │ Depends(require_role("agent"))
  ▼
role_checker
  │ Depends(get_current_user)
  ▼
get_current_user
  │ Depends(security), Depends(get_db)
  ├── HTTPBearer 提取 Token
  ├── jwt.decode 校验 Token
  └── 查询 User
```

FastAPI 会自动解析这条依赖树，并在执行真正的路由函数前完成校验。

## 三、角色规则

| 角色 | customer 接口 | agent 接口 | admin 接口 |
|------|---------------|------------|------------|
| `customer` | 允许 | 拒绝 | 拒绝 |
| `agent` | 按接口设计 | 允许 | 拒绝 |
| `admin` | 允许 | 允许 | 允许 |

当前 `require_role()` 的设计是管理员拥有其他角色的权限超集。真实项目中还应结合资源归属判断，例如客服只能查看分配给自己的工单。

## 四、为什么角色不能只放在前端

前端隐藏按钮不是安全措施。攻击者可以绕过页面直接调用 API，所以每个后端受保护接口都必须在服务端检查 Token 和角色。

## 五、后续接入示例

后续工单 API 可以使用以下模式：

```text
需要客服权限的接口
  → Depends(require_role("agent"))

需要管理员权限的接口
  → Depends(require_role("admin"))
```

当前阶段不新增示例接口，避免把尚未实现的功能误认为已完成。
