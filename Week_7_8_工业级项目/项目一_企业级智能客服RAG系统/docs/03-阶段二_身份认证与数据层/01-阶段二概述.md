# 01 - 阶段二概述

> 阶段二解决“谁能访问系统”和“业务数据如何持久化”两个基础问题。

## 一、为什么阶段一之后先做这一层

阶段一建立了 FastAPI 入口、配置、数据库会话和健康检查。应用可以启动，但它还不知道：

- 谁在访问系统？
- 这个人是谁？
- 他能执行什么动作？
- 文档、工单和消息如何关联？
- 以后如何证明某个工单属于哪个客户？

阶段二先固定身份和数据结构，是因为后续阶段都依赖它：阶段三需要文档和切分块，阶段四转人工需要 Ticket 和 Message，阶段五限流和会话记忆需要使用 JWT 校验后的用户 ID。

## 二、本阶段架构

```text
客户端
  │
  ├── POST /auth/register ──→ Auth API ──→ hash_password ──→ User ──→ 数据库
  │
  ├── POST /auth/login ─────→ Auth API ──→ authenticate_user ──→ create_access_token
  │
  └── GET /auth/me ─────────→ HTTPBearer ──→ jwt.decode ──→ 查询 User ──→ 响应

业务数据模型：
User ──< Ticket ──< Message
Document ──< Chunk
```

## 三、文件之间如何协作

1. `app/models/` 定义数据库表、字段和外键关系。
2. `app/schemas/auth.py` 定义 API 接收和返回的数据形状。
3. `app/services/auth.py` 封装密码哈希、登录校验、JWT 和角色依赖。
4. `app/api/auth.py` 负责 HTTP 路径、状态码和依赖注入。
5. `app/main.py` 注册路由，并通过 `lifespan` 初始化表结构。
6. `tests/test_auth.py` 使用独立数据库验证完整认证链路。

## 四、三个最重要的理解点

### 重点 1：ORM 模型不是 API Schema

`User` 映射数据库表，包含 `hashed_password`；`UserResponse` 控制客户端可以看到的字段，不应该暴露密码哈希。

### 重点 2：密码不能明文保存

注册时调用 `hash_password()`，数据库只保存哈希。登录时调用 `verify_password()` 比较输入密码和哈希，而不是把密码取出来比较。

### 重点 3：JWT 不等于用户永久存在

JWT 只携带用户标识和过期时间。每次访问受保护接口，服务仍需根据 `sub` 查询数据库，确认用户存在、启用且没有被删除或禁用。

## 五、安全边界

- 客户端不能自行提交任意 `customer_id` 代替当前用户。
- `require_role()` 默认允许管理员访问目标角色能力，但普通角色不能越权。
- JWT 密钥必须来自环境变量，生产不能使用默认值。
- 认证失败向客户端返回通用错误，不泄露用户是否存在等不必要信息。
