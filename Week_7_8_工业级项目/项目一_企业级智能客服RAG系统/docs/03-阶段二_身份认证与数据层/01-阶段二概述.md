# 01 - 阶段二概述

## 一、为什么阶段一之后先做这一层

阶段一只有 FastAPI 入口、配置、数据库会话和健康检查。它能启动，但还不知道：

- 谁在访问系统？
- 这个人是谁？
- 他能做什么？
- 文档、工单和消息应该保存在哪里？

阶段二解决的是“身份”和“数据结构”两个问题。后面的知识库检索、客服 Agent、工单流转都会依赖本阶段的模型和认证能力。

## 二、本阶段架构

```text
客户端
  │
  ├── POST /auth/register ──→ 注册 API ──→ auth service ──→ User ──→ SQLite
  │
  ├── POST /auth/login ─────→ 登录 API ──→ auth service ──→ JWT
  │
  └── GET /auth/me ─────────→ HTTPBearer ──→ JWT 校验 ──→ User ──→ 响应

业务数据模型：
User ──< Ticket ──< Message
Document ──< Chunk
```

## 三、文件之间如何协作

1. `app/models/` 定义数据库表结构。
2. `app/schemas/auth.py` 定义 API 输入输出的数据形状。
3. `app/services/auth.py` 放认证业务逻辑，不直接写在路由中。
4. `app/api/auth.py` 接收 HTTP 请求，调用 service，并注入数据库会话。
5. `app/main.py` 注册认证路由。
6. `tests/test_auth.py` 用独立数据库验证完整链路。

## 四、学习重点

### 重点 1：模型不是 API Schema

`User` 是数据库 ORM 模型，负责映射 `users` 表；`UserResponse` 是 API 响应模型，负责控制返回给客户端的字段。密码哈希字段存在于数据库模型中，但不会出现在响应中。

### 重点 2：密码不能明文保存

注册时使用 `hash_password()` 生成不可逆哈希；登录时使用 `verify_password()` 比较明文密码和哈希。数据库中不保存用户原始密码。

### 重点 3：JWT 不是用户数据本身

JWT 只携带身份标识和过期时间。访问 `/auth/me` 时，服务仍然要根据 Token 中的用户 id 查询数据库，以确认用户存在且仍然启用。
