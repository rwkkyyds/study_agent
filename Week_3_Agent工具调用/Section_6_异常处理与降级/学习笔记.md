# Section 6 学习笔记：Agent 工具调用异常处理、重试与降级

## 一、为什么需要异常处理？

Agent 调用工具时，外部依赖随时可能出问题：

```
网络抖动      → API 请求超时
服务限流      → 429 Too Many Requests
LLM 幻觉     → 调用不存在的工具、传错参数
数据源挂了    → 数据库连接池耗尽、搜索引擎宕机
返回格式异常  → 工具返回了 LLM 无法解析的格式
```

**核心原则：工具出错 ≠ Agent 崩溃。** 要捕获错误、记录日志、想办法恢复或降级。

## 二、异常捕获基础（demo1）

### 2.1 try-except 包裹工具执行

```python
try:
    result = tool.invoke(args)
except TimeoutError as e:
    # 网络超时 → 可重试
except ConnectionError as e:
    # 连接/限流 → 可重试
except Exception as e:
    # 兜底 → 记录错误
```

### 2.2 错误信息返回给 LLM

关键设计：**错误信息要作为 ToolMessage 返回给 LLM**，让它决定下一步：
- LLM 可能换个参数重试
- LLM 可能换一个工具
- LLM 可能直接告诉用户"暂时查不到"

### 2.3 常见异常类型分类

| 异常类型 | 原因 | 是否可重试 |
|---------|------|-----------|
| TimeoutError | 网络超时 | 可重试 |
| ConnectionError | 连接失败/429限流 | 可重试 |
| KeyError/ValueError | 参数错误 | 不可重试，需修正参数 |
| Tool不存在 | LLM 幻觉 | 不可重试，需修正工具名 |

## 三、重试策略（demo2）

### 3.1 为什么不能立即重试？

立即重试 → 服务还没恢复 → 再次失败 → 资源浪费

### 3.2 指数退避（Exponential Backoff）

```
第1次重试：等 1 秒
第2次重试：等 2 秒
第3次重试：等 4 秒
第4次重试：等 8 秒
...
```

给服务恢复的时间，避免"落井下石"。

### 3.3 随机抖动（Jitter）

```
实际等待 = 指数退避时间 + random(0, 1)
```

解决**雷群效应**：100个客户端同时失败 → 如果都按固定时间重试 → 同时发起请求 → 服务再次被打爆。加随机抖动后，请求分散在不同时间到达。

### 3.4 tenacity 库（生产级重试组件）

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception_type

@retry(
    retry=retry_if_exception_type((ConnectionError, TimeoutError)),  # 只对临时异常重试
    stop=stop_after_attempt(3),           # 最多重试3次
    wait=wait_exponential(min=1, max=10), # 指数退避，最小1秒，最大10秒
)
def call_api(query: str) -> str:
    return api.call(query)
```

### 3.5 选择性重试

**不是所有异常都值得重试：**
- 临时性错误（429、超时）→ 重试可能成功
- 永久性错误（400参数错误、403权限不足）→ 重试也没用

用 `retry_if_exception_type` 指定哪些异常需要重试。

## 四、降级策略（demo3）

### 4.1 Fallback 工具链

核心思想：**主工具挂了 → 换备用工具**

```
web_search（主工具）
  ↓ 失败
cache_search（一级 Fallback：数据可能过期但能用）
  ↓ 也失败
static_faq（二级 Fallback：静态兜底方案）
```

### 4.2 Fallback 注册表设计

```python
FALLBACK_CHAIN = {
    "web_search": ["cache_search", "static_faq"],
    "database_query": ["cache_search", "static_faq"],
}
```

好处：
- 新增工具只需注册 fallback 映射
- 降级路径一目了然
- 方便测试和维护

### 4.3 降级等级

```
Level 0: 正常调用主工具 ✅
Level 1: 重试1次后成功 ⚠️
Level 2: 使用 Fallback 工具 🔄
Level 3: 所有方案都失败 ❌
```

### 4.4 LangGraph 条件路由实现降级

```python
graph.add_conditional_edges(
    "tool_call",           # 工具调用节点
    should_degrade_route,  # 路由函数：根据降级等级决定走哪条路
    {
        "normal_response": "normal_response",    # Level 0 → 正常回复
        "degraded_response": "degraded_response", # Level 1-2 → 降级回复
        "failure_response": "failure_response",   # Level 3 → 失败回复
    }
)
```

### 4.5 信息透明原则

降级时一定要告知用户：
```python
"[降级结果 - 来源: cache_search] 缓存数据（可能不是最新）"
```

不要悄悄降级，让用户知道结果的可靠性。

## 五、三级容错体系总结

```
┌─────────────────────────────────────────────────┐
│                Agent 工具调用                      │
├─────────────────────────────────────────────────┤
│ Level 0: 正常调用主工具                            │
│   try: result = tool.invoke(args)                │
│         ↓ 失败                                    │
│ Level 1: 自动重试（指数退避 + 抖动）                 │
│   @retry(stop=3, wait=exponential)               │
│         ↓ 仍然失败                                │
│ Level 2: Fallback 工具链                          │
│   for fb in FALLBACK_CHAIN[tool]:                │
│       try: fb.invoke(args)                       │
│         ↓ 全部失败                                │
│ Level 3: 优雅失败                                 │
│   返回"暂时不可用，请稍后重试"                       │
└─────────────────────────────────────────────────┘
```

## 六、生产实践要点

1. **日志必须完整**：每次重试、每次降级都要记录，方便排查
2. **重试有上限**：不能无限重试，通常 3-5 次
3. **超时要设置**：工具调用必须有 timeout，不能无限等待
4. **降级要透明**：告诉用户结果来自哪个数据源
5. **监控要跟上**：重试率、降级率是重要运维指标
