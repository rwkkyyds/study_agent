## 1. global 关键字的作用

**问题**：代码中的 `global flaky_api` 是什么意思？

**答案**：

`global` 关键字用来告诉 Python：**这个变量是全局的，我要修改全局变量本身，而不是创建新的本地变量**。

### 核心区别

#### ❌ 没有 global（创建本地变量）
```python
flaky_api = FlakyAPI(fail_count=2)  # 全局变量

def demo():
    flaky_api = FlakyAPI(fail_count=5)  # 只创建了本地变量
    # 全局的 flaky_api 不受影响
```

#### ✅ 有 global（修改全局变量）
```python
flaky_api = FlakyAPI(fail_count=2)  # 全局变量

def demo():
    global flaky_api  # 声明：我要修改全局变量
    flaky_api = FlakyAPI(fail_count=5)  # 现在修改的是全局变量
```

### 在这个项目中的用途

```python
def test_scenario_1():
    global flaky_api  
    flaky_api = FlakyAPI(fail_count=2)  # 重置 API 的初始状态
```

**目的**：在每个测试场景之前，重新创建一个新的 `FlakyAPI` 实例，清空调用计数，这样每个场景都能从干净的状态开始。不加 `global` 的话，全局的 `flaky_api` 不会被改变，后续的函数还是会使用旧的实例。

### 何时需要 global？

- ✅ 要**修改**全局变量的值（赋新值）
- ✅ 要修改全局可变对象的**内容**（如重新赋值）
- ❌ 只是**读取**全局变量（不需要 global）
- ❌ 修改全局对象的属性（如 `flaky_api.fail_count = 3`，不需要 global）

## 1.1 global 的作用域（新增）

**问题**：global 只要在一个函数中声明一遍就可以了吗，在其他函数中就不用声明了对吧？

**答案**：❌ **错！global 的声明在每个函数中都需要单独声明**，global 的作用域**只限于当前函数**。

### 正确做法

```python
flaky_api = FlakyAPI(fail_count=2)  # 全局变量

def demo_tenacity_basics():
    global flaky_api  # 声明：在这个函数里要修改全局变量
    flaky_api = FlakyAPI(fail_count=2)
    # ...

def demo_manual_retry():
    global flaky_api  # 必须再声明一次！这个声明只对这个函数有效
    flaky_api = FlakyAPI(fail_count=2)
    # ...

def demo_retry_exhausted():
    global flaky_api  # 每个函数都要单独声明
    flaky_api = FlakyAPI(fail_count=5)
    # ...
```

### 为什么每个函数都要声明？

因为 **global 的声明是函数作用域内的**：

```python
global flaky_api  # 这行只在这个函数内有效

def func1():
    global flaky_api  # func1 知道 flaky_api 是全局变量
    flaky_api = FlakyAPI(fail_count=2)  # ✅ 修改全局变量

def func2():
    # 没有 global 声明
    flaky_api = FlakyAPI(fail_count=5)  # ❌ 创建本地变量，全局变量不变
```

## 2. tenacity 装饰器 vs 手动重试有什么区别？

**问题**：看代码两种方式好像差不多啊，为什么要区分呢？

**答案**：虽然逻辑相似，但有 **5 个重要区别**：

### 对比表

| 方面 | tenacity 装饰器 | 手动重试 |
|------|----------------|--------|
| **代码简洁性** | ⭐⭐⭐⭐⭐ 极简 | ⭐⭐ 代码冗长 |
| **灵活性** | ⭐⭐ 配置固定 | ⭐⭐⭐⭐⭐ 高度灵活 |
| **返回值** | 直接返回结果 | 可返回重试次数等额外信息 |
| **错误处理** | 自动，配置式 | 手动编写，容易遗漏 |
| **学习成本** | ⭐⭐ 需要学库 | ⭐⭐⭐⭐ 原生 Python |

### 1️⃣ 代码简洁性

#### 装饰器版本（声明式）
```python
@retry(
    retry=retry_if_exception_type((ConnectionError, TimeoutError)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(min=1, max=10, multiplier=2),
    before_sleep=before_sleep_log(logger, logging.WARNING),
)
def call_api_with_retry(query: str) -> str:
    logger.info(f"尝试调用 API: {query}")
    result = flaky_api.call(query)
    return result
```

💡 **只需配置参数，tenacity 自动实现重试逻辑**

#### 手动版本（命令式）
```python
def call_api_manual_retry(query: str, max_retries: int = 3) -> tuple[str, int]:
    last_error = None
    retries = 0

    for attempt in range(max_retries):        # ← 需要写循环
        try:
            logger.info(f"第 {attempt + 1} 次尝试调用 API")
            result = flaky_api.call(query)
            return result, retries

        except (ConnectionError, TimeoutError) as e:
            last_error = e
            retries += 1

            wait_time = (2 ** attempt) + random.uniform(0, 1)  # ← 自己计算指数退避
            logger.warning(...)
            import time
            time.sleep(wait_time)               # ← 手动等待

        except Exception as e:
            logger.error(f"不可恢复的错误: {type(e).__name__}: {e}")
            raise

    raise last_error
```

💡 **需要手动编写重试逻辑，代码冗长**

### 2️⃣ 灵活性

#### 装饰器的局限
```python
# 装饰器配置后就是固定的，不能动态改变
@retry(
    stop=stop_after_attempt(3),      # 永远最多重试3次
    wait=wait_exponential(min=1, max=10),
)
def call_api(query: str):
    ...

# 不能根据不同场景改变重试策略
```

#### 手动重试的优势
```python
# 可以根据场景动态调整重试策略
def call_api_flexible(query: str, max_retries: int = None):
    # 参数可以动态传入
    if is_critical_request(query):
        max_retries = 5    # 关键请求多重试
    else:
        max_retries = 2    # 普通请求少重试

    for attempt in range(max_retries):
        # 甚至可以在每次重试时修改策略
        if attempt == 0:
            timeout = 1
        elif attempt == 1:
            timeout = 3
        else:
            timeout = 5
        
        try:
            result = flaky_api.call(query, timeout=timeout)
            return result
        except Exception as e:
            ...
```

### 3️⃣ 返回值差异

#### 装饰器
```python
result = call_api_with_retry("查询天气")  # 直接返回结果
# 如果你想知道重试了几次？→ 没法获取
```

#### 手动重试
```python
result, retries = call_api_manual_retry("查询天气", max_retries=3)
print(f"成功！重试了 {retries} 次")  # 可以获取重试信息
```

### 4️⃣ 何时选择哪种？

| 场景 | 选择 | 原因 |
|------|------|------|
| 简单 API 调用（工作中90%的情况） | 装饰器 | 代码少，配置清晰，不需要重试信息 |
| 需要获取重试次数 | 手动 | 需要返回额外信息 |
| 不同请求用不同重试策略 | 手动 | 配置需要动态变化 |
| 重试逻辑很复杂（比如多层降级） | 手动 | 需要自定义控制流 |

### 5️⃣ 代码复杂度对比

```python
# 装饰器：1 + 5 = 6 行（配置 + 函数）
@retry(
    retry=retry_if_exception_type((ConnectionError, TimeoutError)),
    stop=stop_after_attempt(3),
    wait=wait_exponential(min=1, max=10, multiplier=2),
    before_sleep=before_sleep_log(logger, logging.WARNING),
)
def call_api_with_retry(query: str) -> str:
    return flaky_api.call(query)

# 手动：26 行（循环 + try-except + 计算 + 等待）
def call_api_manual_retry(query: str, max_retries: int = 3) -> tuple[str, int]:
    last_error = None
    retries = 0
    for attempt in range(max_retries):
        try:
            result = flaky_api.call(query)
            return result, retries
        except (ConnectionError, TimeoutError) as e:
            last_error = e
            retries += 1
            wait_time = (2 ** attempt) + random.uniform(0, 1)
            logger.warning(f"调用失败，等待 {wait_time:.1f} 秒后重试...")
            import time
            time.sleep(wait_time)
        except Exception as e:
            logger.error(f"不可恢复的错误: {e}")
            raise
    raise last_error
```

💡 **装饰器快 4 倍！**

## 总结

### global 作用域
- ❌ **错：** "在一个函数声明就够了"
- ✅ **对：** "每个要修改全局变量的函数都需要单独声明 global"
- global 的作用范围 = 当前函数的作用域

### 装饰器 vs 手动重试
- **装饰器**：90%工作场景，简洁、清晰、推荐
- **手动重试**：10%特殊场景，需要高度灵活或获取重试信息

## 3. P99延迟是什么？为什么不看P100或平均值？

**问题**：P99延迟到底是什么意思？为什么不直接看最大延迟或者平均延迟呢？

**答案**：P99是**衡量系统好坏的黄金指标**，因为它能真实反映大多数用户的体验。

### P99的本质定义

P99延迟 = **在所有请求中，排名前99%的请求所需的最长响应时间**

#### 具体例子

假设你有100个API请求，按响应时间从快到慢排序：

```
请求1: 10ms
请求2: 12ms
请求3: 15ms
...
请求99: 150ms  ← P99延迟就是这个值
请求100: 5000ms ← P100延迟（极端情况）

P99 = 150ms 意味着：
✅ 99%的用户体验 ≤ 150ms
❌ 1%的用户遭遇 > 150ms（但这是可接受的容错范围）
```

### 为什么不用其他指标？

#### ❌ P100（最大值）的问题：被异常值毁掉

```
正常系统：
99个请求：10, 12, 15, 20... 150, 150, 150ms
1个极端请求：30000ms（GC卡顿或网络抖动）

结果：
- P100 = 30000ms  ❌ 吓死人！但只影响1个用户
- P99 = 150ms     ✅ 真实反映系统状态
```

**问题**：只要有一个异常值，P100就完全失真，不代表系统整体状态。

#### ❌ 平均值（Mean）的问题：也被异常值拉高

```
同上场景：
平均值 = (10 + 12 + ... + 150 + 30000) / 100 ≈ 3000ms

问题：99%的用户根本遭遇不到这个延迟，被拉高了！
```

#### ❌ P50（中位数）的问题：信息不足

```
P50 = 75ms （只看前一半）
问题：另一半用户（50%-99%）可能很慢，但被忽略了
```

#### ✅ P99的优势

```
| 指标 | 代表含义 | 可靠性 |
|------|--------|-------|
| P50（中位数） | 一半用户 | ⭐⭐ 不够 |
| 平均值 | 平均表现 | ⭐⭐ 易被异常值拉偏 |
| P99 | 99%用户体验 | ⭐⭐⭐⭐⭐ 既包括大多数，又排除极端值 |
| P100（最大值） | 最坏情况 | ⭐ 常被异常值干扰 |
```

### 现实应用：电商平台SLA设置

```
✅ P99 < 100ms   → 99%用户秒开，用户体验好，达标
⚠️  P99 = 200ms   → 1%用户有点卡，但还能接受
❌ P99 > 500ms   → 1%用户超级卡，影响转化率，需要优化

P100 = 5s        → 只有1个人触发了，不是重点关注对象
```

### 为什么这对异常处理很关键？

在 Section 6（异常处理与降级）中：

```python
# 当调用服务出错时，触发降级
try:
    result = llm_service.call()  # 一般情况 P99 = 50ms
except Exception:
    result = fallback_service.call()  # 降级方案 P99 = 200ms
```

**监控指标**：
- ❌ 不看 P100：一次极端故障会误导你
- ✅ 看 P99：能真实看到降级后大多数用户是否满意
- ✅ 看 P99.9：监控极端用户体验，但不是主要KPI

## 4. 重试策略中的"抖动"（Jitter）是什么？

**问题**：指数退避 + 抖动 + 最大次数，这里的抖动到底是什么意思？为什么要加抖动？

**答案**：抖动是指**在重试延迟中添加随机值**，防止多个请求同时重试而导致系统雪崩。

### 问题场景：没有抖动的后果（雷鸣羊群问题）

假设服务器在 `t=0s` 故障，有1000个并发请求：

#### ❌ 没有抖动的指数退避

```
所有请求的重试延迟都是固定的：
请求1: 延迟 2s → t=2.0s 重试 ✓
请求2: 延迟 2s → t=2.0s 重试 ✓
请求3: 延迟 2s → t=2.0s 重试 ✓
...
请求1000: 延迟 2s → t=2.0s 重试 ✓

时间线：
t=0s:    1000个请求同时故障
t=2.0s:  1000个请求同时涌入 → 服务器再次故障！❌❌❌
t=4.0s:  又涌入了1000个 → 继续故障...
```

**结果**：形成"雷鸣羊群"效应，系统陷入恶性循环，无法恢复！

#### ✅ 有抖动的指数退避

```
每个请求的重试延迟都加入随机值：
请求1: 延迟 2.0s + 随机(0-200ms) = 2.15s → t=2.15s 重试 ✓
请求2: 延迟 2.0s + 随机(0-200ms) = 2.08s → t=2.08s 重试 ✓
请求3: 延迟 2.0s + 随机(0-200ms) = 2.31s → t=2.31s 重试 ✓
...
请求1000: 延迟 2.0s + 随机(0-200ms) = 2.12s → t=2.12s 重试 ✓

时间线：
t=0s:    1000个请求同时故障
t=2.0-2.3s:  请求均匀分散重试，每个时刻最多 50 个 ✓
             服务器能正常处理
```

**结果**：请求均匀分散，避免了集中冲击！

### 代码示例

```python
import random
import time

def retry_with_jitter(max_retries=3):
    """带抖动的重试机制"""
    for attempt in range(max_retries):
        try:
            return api_call()
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            
            # 指数退避：基础延迟
            base_delay = 2 ** attempt  # 1s, 2s, 4s...
            
            # 添加抖动：随机延迟
            jitter = random.uniform(0, base_delay * 0.1)  # 0-base_delay的10%
            
            # 总等待时间
            wait_time = base_delay + jitter
            
            print(f"第 {attempt+1} 次重试，等待 {wait_time:.2f}s")
            time.sleep(wait_time)
```

### 业界标准公式

```
总延迟 = min(最大延迟, 基础延迟 × 2^尝试次数 + random(0, 抖动范围))

典型值：
- base_delay = 100ms
- max_delay = 30s  
- jitter = base_delay（即 100ms）
```

#### AWS SDK 的实现

```python
# AWS官方推荐
delay = min(
    max_delay,
    base_delay * (2 ** attempt) + random.uniform(0, base_delay)
)
```

### 为什么对P99延迟很关键？

#### 没有抖动的影响

```
1000并发 + 无抖动：
所有请求在 t=2.0s 同时到达
→ 服务器瞬间压力爆表
→ P99延迟 = 5000ms（全部超时）❌
```

#### 有抖动的影响

```
1000并发 + 有抖动：
请求均匀分散在 t=2.0-2.3s
→ 服务器压力均匀分布
→ P99延迟 = 150ms（正常） ✓
```

### 现实例子：电商秒杀

```
没有抖动：
100万用户同时点击秒杀 → 都在同一时刻重试 → 系统雪崩

有抖动：
100万用户同时点击秒杀 → 分散在100ms内重试 → 系统正常处理
```

### 何时是关键？

| 场景 | 是否需要抖动 |
|------|----------|
| 单个用户的HTTP重试 | ⭐ 可选 |
| 消息队列消费者重试 | ⭐⭐⭐⭐⭐ 必须！ |
| 分布式服务调用 | ⭐⭐⭐⭐⭐ 必须！ |
| 数据库连接池重试 | ⭐⭐⭐⭐⭐ 必须！ |

### 核心结论

```
❌ 无抖动：高并发时系统陷入恶性循环
✅ 有抖动：请求均匀分散，P99延迟稳定

抖动不是可选项，是生产环境必备！
```
