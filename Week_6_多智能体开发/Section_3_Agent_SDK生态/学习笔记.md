# Week 6 Section 3 学习笔记：Agent SDK 生态

## 1. 本节核心结论

Agent SDK 的核心价值不是“换一种方式调模型”。

它真正解决的是：

```text
当 Agent 项目开始有工具、流程、结构化输出、校验、观测和多 Agent 协作时，
SDK 可以帮我们把这些工程能力组织起来。
```

本节重点跑通了：

- SDK 的共同骨架
- PydanticAI 的结构化输出
- OpenAI Agents SDK 的 Agent / Tool 定义方式

## 2. demo1 复盘：SDK 共同骨架

文件：

```text
demo1_sdk_common_runtime.py
```

这个 demo 自己实现了一个极简 SDK 骨架：

```text
Tool
Agent
Runner
RunResult
```

它不是为了造轮子，而是为了让你看懂所有 SDK 背后的共同结构。

### Tool 是什么

Tool 就是 Agent 可以调用的能力。

比如：

```text
查订单
查知识库
计算退款金额
调用搜索 API
读取文件
查询数据库
```

在 demo 里：

```python
Tool("order_lookup", "查询订单和退款状态", order_lookup)
```

意思是：给 Agent 一个订单查询工具。

### Agent 是什么

Agent 是：

```text
角色说明 + 行为指令 + 可用工具
```

在 demo 里：

```python
Agent(
    name="customer_support_agent",
    instructions="你是客服 Agent，根据问题选择合适工具。",
    tools=[...],
)
```

这就是 Agent 的基本形态。

### Runner 是什么

Runner 是执行器。

它负责：

```text
接收用户输入
选择工具
执行工具
返回结果
```

真实 SDK 里的 Runner 会更复杂，比如还会处理：

- 模型调用
- tool calling
- streaming
- tracing
- retries
- guardrails

但本质还是执行 Agent。

## 3. demo2 复盘：PydanticAI 结构化输出

文件：

```text
demo2_pydantic_ai_structured_output.py
```

这个 demo 的重点是：

```text
让 AI 输出变成后端可以稳定使用的数据结构。
```

### 为什么结构化输出重要

普通大模型输出是文本：

```text
用户这个问题应该是支付问题，优先级比较高，建议查订单。
```

人能看懂，但程序不好处理。

后端更需要：

```json
{
  "category": "payment",
  "priority": 4,
  "next_action": "查询订单状态"
}
```

这样才能继续：

```text
写数据库
进入工单系统
路由到不同节点
触发告警
展示到前端
```

### Pydantic 模型的作用

代码里定义了：

```python
class TicketAnalysis(BaseModel):
    category: str
    priority: int = Field(ge=1, le=5)
    next_action: str
```

这代表我们要求输出必须符合这个结构。

其中：

```python
priority: int = Field(ge=1, le=5)
```

意思是优先级必须是 1 到 5。

如果输出不符合结构，SDK 可以帮你发现问题，而不是让错误数据悄悄流进系统。

### TestModel 是什么

本节用了：

```python
from pydantic_ai.models.test import TestModel
```

它是 PydanticAI 提供的测试模型。

作用是：

```text
不需要 API Key，也能验证 Agent 代码结构是否正确。
```

这对学习和单元测试都很有用。

## 4. demo3 复盘：OpenAI Agents SDK 工具形态

文件：

```text
demo3_openai_agents_tool_shape.py
```

这个 demo 的重点是看 OpenAI Agents SDK 里 Agent 和 Tool 怎么声明。

### function_tool 是什么

代码里：

```python
@function_tool
def lookup_policy(topic: str) -> str:
    ...
```

这代表：

```text
把一个普通 Python 函数包装成 Agent 可调用工具。
```

真实运行时，模型可以根据工具说明和参数 schema 决定是否调用它。

### Agent 是什么

代码里：

```python
agent = Agent(
    name="refund_assistant",
    instructions="...",
    tools=[calculate_refund, lookup_policy],
)
```

意思是：

```text
定义一个退款客服助手，并给它两个工具。
```

OpenAI Agents SDK 的开发体验很直观：

```text
定义函数
加 @function_tool
挂到 Agent
用 Runner 执行
```

本 demo 没调用 Runner，是因为真实调用需要模型和 API Key。

## 5. 三个 demo 的关系

你可以这样串起来：

```text
demo1：先理解所有 SDK 的共同骨架
demo2：看 PydanticAI 怎么保证输出结构
demo3：看 OpenAI Agents SDK 怎么声明工具和 Agent
```

它们不是孤立的。

真实项目里可能是：

```text
OpenAI Agents SDK 负责工具调用
Pydantic 负责输出结构
LangGraph 负责流程编排
MCP 负责外部工具接入
```

## 6. SDK 选型不要迷信名字

选 SDK 不要看谁更火。

要看你的项目现在卡在哪里。

如果你卡在流程复杂：

```text
优先看 LangGraph
```

如果你卡在输出不稳定：

```text
优先看 PydanticAI / Pydantic 结构化输出
```

如果你卡在工具调用和官方生态：

```text
优先看 OpenAI Agents SDK
```

如果你卡在工具接入标准化：

```text
优先看 MCP
```

## 7. 本节一句话总结

```text
Agent SDK 不是为了替代你的业务逻辑，而是为了把 Agent 工程里的通用麻烦事标准化。
```

通用麻烦事包括：

- 工具注册
- 模型调用
- 输出校验
- 运行追踪
- 多步骤流程
- 多 Agent 协作
- 外部工具接入
