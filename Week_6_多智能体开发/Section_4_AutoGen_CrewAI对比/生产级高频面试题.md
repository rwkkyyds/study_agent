# Week 6 Section 4：生产级高频面试题

## 1. AutoGen 和 CrewAI 的本质区别是什么？

AutoGen 偏"对话驱动"，多个 Agent 在一个会话里互相说话推进任务。
CrewAI 偏"任务驱动"，把目标拆成一串任务，按顺序分给不同角色，像流水线交棒。

面试可以这样表达：

```text
AutoGen 的基本单位是会说话的 ConversableAgent，协作靠 Agent 在 GroupChat 里轮流发言；
CrewAI 的基本单位是 Task，协作靠任务依赖串行，上一个产出喂给下一个。
```

一句话类比：

```text
AutoGen 像把专家拉进一个群自己聊出结论；CrewAI 像给项目组分派任务每人做完自己的环节。
```

## 2. AutoGen 的 speaker_selection_strategy 有哪几种？分别解决什么问题？

三种：

```text
auto      : 让 LLM 根据对话上下文选下一个说话者
round_robin: 按列表顺序轮流
manual    : 人工指定
```

auto 适合需要动态决定谁接话的场景，round_robin 适合固定流程，manual 适合需要人控制的场景。

核心要理解：AutoGen 的多 Agent 协作，"谁说话"是一个需要显式决策的问题，不是自动的。

## 3. AutoGen 怎么判断对话该结束了？

用 termination 条件判断。

常见做法：

```text
is_termination_msg: 检测某条消息是否是终止信号（比如包含"最终结论"）
max_round         : 限制最大轮次，防止无限聊下去
```

生产建议两个都用：termination_msg 做正常收敛，max_round 做兜底保护，防止 Agent 卡在循环里。

## 4. CrewAI 的 Task 用什么声明依赖？

用 `context_from` 声明它依赖哪些前置任务的产出。

```python
Task("t2", "撰写总结", context_from=["t1"])
```

Crew 据此做拓扑排序，t1 做完才轮到 t2，并把 t1 的产出作为上下文喂给 t2。

这和 Airflow 里的 task 依赖、LangGraph 里的边是同一个思想：显式声明数据依赖，让框架决定执行顺序。

## 5. CrewAI 的 kickoff 做了什么？

kickoff 是 CrewAI 的入口函数，它的职责是：

```text
1. 按依赖顺序遍历所有 Task
2. 对每个 Task，拼接它 context_from 指定的前置产出
3. 把任务交给对应 Agent 执行
4. 把产出存起来，喂给后续依赖它的任务
5. 最后一个任务的产出作为最终结果返回
```

面试可以说：

```text
kickoff 是 CrewAI 的执行入口，本质是按任务依赖做拓扑排序后串行执行，每一步的产出作为下一步的输入。
```

## 6. 什么场景优先选 AutoGen？

适合需要讨论、反复确认、头脑风暴的场景：

```text
多个专家需要互相质询和补充
结论需要经过评审和收敛
任务没法提前拆成清晰步骤，要靠对话推进
```

例如：技术方案评审、文档多轮打磨、研究型讨论。

## 7. 什么场景优先选 CrewAI？

适合流程清晰、能拆成步骤的场景：

```text
调研 → 写作 → 审核 → 发布
数据采集 → 清洗 → 分析 → 出报告
翻译 → 校对 → 排版
```

流程越像流水线，CrewAI 越合适。

## 8. 什么场景其实 LangGraph 更合适？

如果需要精细控制状态机和分支：

```text
复杂的条件路由
人工审批暂停（HITL）
循环重试
子图复用
```

LangGraph 用 StateGraph 显式建模流程，控制力比 AutoGen/CrewAI 都强。

所以选型不是二选一：

```text
要精细流程控制 → LangGraph
要多角色讨论   → AutoGen 思路
要任务流水线   → CrewAI 思路
```

## 9. AutoGen 和 CrewAI 能组合用吗？

可以，真实项目里三者（含 LangGraph）经常组合：

```text
LangGraph 做主流程控制
AutoGen 思路用在需要讨论的环节（让多 Agent 对话）
CrewAI 思路用在流程清晰的环节（任务流水线）
```

面试可以说：

```text
我不把框架当互斥选项。主流程用 LangGraph 控状态机，需要多角色讨论的节点用 AutoGen 思路，
流水线型的环节用 CrewAI 思路。关键是匹配编排方式和业务环节的特性。
```

## 10. 多 Agent 系统上线有哪些风险？

常见风险：

```text
Agent 互相循环调用，停不下来
谁说话/谁干活没有明确控制，乱套
缺少终止条件，成本失控
任务依赖成环，CrewAI 跑不动
产出没有校验，错误悄悄往下传
缺少人工确认，高风险动作直接执行
token 和成本不可控
```

生产建议：

```text
必须有 max_round / termination 兜底
任务依赖要无环（DAG）
关键动作加 HITL 人审
每步产出要校验
加 trace 和 metrics 观测执行过程
```

## 11. 怎么做 AutoGen/CrewAI 选型？

从业务环节的特性出发：

```text
环节需要讨论、协商、多轮确认 → AutoGen 思路
环节能拆成清晰步骤、有明确交接物 → CrewAI 思路
环节需要条件分支、暂停、循环、子图 → LangGraph
```

不要只看框架热度，要看流程特性。一个项目里不同环节可能用不同思路。

## 12. 为什么本节用轻量 dataclass 模拟而不是装真实框架？

可以这样回答：

```text
选型的关键不是 API 熟练度，而是理解编排思路。真实 AutoGen/CrewAI 依赖重、要 LLM API Key 才能跑，
学习时容易卡在环境配置而非理解思想。用 dataclass 抽出"对话驱动"和"任务驱动"的骨架，
差异一目了然，等真要落地再对照思路读官方文档更快。
```

## 13. AutoGen 的 GroupChat 和 LangGraph 的图编排有什么区别？

```text
GroupChat 靠 speaker 策略决定谁说话，偏"会话态"，控制粒度是发言权流转。
LangGraph 靠 StateGraph + 条件边决定流程走向，偏"状态机态"，控制粒度是节点执行顺序。
```

GroupChat 更灵活但可控性弱，LangGraph 可控性强但表达"自由讨论"比较绕。
