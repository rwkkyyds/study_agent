# Week 6 Section 4 学习笔记：AutoGen / CrewAI 框架对比选型

## 1. 本节核心结论

这一节不让你背 AutoGen 或 CrewAI 的 API，只解决一个问题：

```text
看懂这两个框架的编排思路有什么本质不同，以后做选型时能说清"为什么选这个、不选那个"。
```

一句话结论：

```text
AutoGen 偏"对话驱动"：多个 Agent 在一个会话里互相说话推进。
CrewAI 偏"任务驱动"：把一个目标拆成一串任务，按顺序分给不同角色。
```

教学大纲标注「压缩1天，了解即可」，所以本节用零依赖的轻量 dataclass 实现，把两个框架的"编排骨架"抽出来对比，不装真实框架、不调真实大模型。

## 2. 两框架核心差异（先记这张表）

| 维度 | AutoGen | CrewAI |
|------|---------|--------|
| 编排思路 | 对话驱动（多 Agent 互相说话） | 任务驱动（目标拆成任务串行/并行） |
| 基本单位 | ConversableAgent（会说话的角色） | Crew（一队人） + Task（任务） + Agent（角色） |
| 协作方式 | Agent 间发消息，谁回话由流程控制 | 任务按顺序流给下一个 Agent，像流水线 |
| 典型场景 | 需要讨论、反复确认、头脑风暴 | 流程清晰、能拆成步骤、像流水线的业务 |
| 心智模型 | 像一个"群聊" | 像一个"项目组分工" |
| 控制粒度 | 谁先说、谁接话、说几轮 | 任务依赖、串/并行、上一个完成才下一个 |

一句话类比：

```text
AutoGen = 把几个专家拉进一个群，让他们自己聊出结论。
CrewAI = 给一个项目组派一串任务，每人做完自己的环节交棒。
```

## 3. demo1 复盘：核心抽象对比

文件：

```text
demo1_framework_core_abstraction.py
```

这个 demo 用纯 dataclass 同时实现两套骨架，放一起对比。

### AutoGen 的三个核心抽象

```text
ConversableAgent：一个会说话的角色，能收消息、回消息
GroupChat：把多个 Agent 拉进一个"群聊"
next_speaker：决定下一句轮到谁说话
```

关键点：AutoGen 的 Agent 是"活的"，它会在会话里主动发言，协作靠互相说话推进。

### CrewAI 的三个核心抽象

```text
Agent：角色（role + goal），被任务调用时才干活
Task：流程里的一个环节，有 expected_output 和 context_from
Crew：一队 Agent + 一串 Task，按依赖顺序跑
```

关键点：CrewAI 的 Agent 是"静态"的，它不主动发言，只在被分配到任务时才干活，协作靠任务依赖推进。

### 为什么放一起对比

不是为了造轮子，而是让你一眼看清：

```text
AutoGen 的 run() 在群里轮流说话
CrewAI 的 kickoff() 按任务依赖串行执行
```

两种编排方式的差异，看输出日志最直观。

## 4. demo2 复盘：AutoGen 对话驱动

文件：

```text
demo2_autogen_conversation_driven.py
```

这个 demo 细讲 AutoGen 怎么决定"该谁说话"。

### speaker_selection_strategy 是什么

AutoGen 的 GroupChat 最关键的问题是：下一句轮到谁？

三种策略：

```text
auto       : 让 LLM 根据上下文选下一个说话者
round_robin: 按列表顺序轮流
manual     : 人工指定
```

本 demo 用关键词规则模拟 auto 策略（真实场景会把对话历史喂给 LLM 让它选）。

### 收敛条件怎么判断

AutoGen 不能让 Agent 无限聊下去，必须有终止条件。

demo 里用：

```text
if "最终结论" in response:
    对话结束
```

对应真实 AutoGen 的 `is_termination_msg` 机制——检测到总结性发言就停。

### 运行流程

```text
研究员开口 → 给要点 + "请评审"
  ↓ speaker 选评审员（因为含"请评审"）
评审员接话 → "要点2的'可控'需要补充：状态机化"
  ↓ speaker 选总结员（因为含"补充"）
总结员收敛 → "最终结论=轻量+状态机可控+可观测，推荐 LangGraph"
  ↓ 检测到"最终结论"，对话结束
```

### 本 demo 踩过的两个坑（已修复）

1. initiator 只记下 prompt 没真正发言 → selector 看不到关键词，死循环。修复：initiator 先用 reply 产生第一句。
2. selector 关键词判断顺序不对（先判"要点"导致一直还给研究员）→ 修复：先判"请评审"→评审员，再判"补充"→总结员。

## 5. demo3 复盘：CrewAI 任务驱动

文件：

```text
demo3_crewai_task_driven.py
```

这个 demo 细讲 CrewAI 的任务流水线怎么跑。

### Task 的 context_from 是什么

CrewAI 里任务之间的依赖靠 `context_from` 声明：

```python
Task("t2", "撰写技术总结", ..., context_from=["t1"])
```

意思是 t2 依赖 t1 的产出，Crew 据此做拓扑排序，t1 做完才轮到 t2。

### kickoff 做了什么

CrewAI 的入口函数叫 kickoff，它的工作是：

```text
1. 按依赖顺序遍历 tasks
2. 对每个 task，拼接它 context_from 指定的前置产出作为上下文
3. 把任务交给对应 Agent 执行
4. 把产出存起来，喂给后续依赖它的任务
5. 最后一个任务的产出就是最终结果
```

### 运行流程

```text
researcher 执行 t1 → 产出"3个框架对比表"
  ↓ t2 的 context_from=["t1"]
writer 执行 t2 → 拿到 t1 产出，写成"可发布摘要"
  ↓ t3 的 context_from=["t2"]
reviewer 执行 t3 → 拿到 t2 产出，审核通过并发布
```

和 AutoGen 的区别：CrewAI 不靠"说话"推进，靠"任务依赖"推进，流程更可控、更像流水线。

## 6. 三个 demo 的关系

可以这样串起来：

```text
demo1：同时看两种编排骨架的差异
demo2：深入 AutoGen 的对话推进机制（speaker 策略 + 收敛条件）
demo3：深入 CrewAI 的任务推进机制（依赖 + kickoff + 交接）
```

它们不是孤立的，demo1 是骨架对比，demo2 和 demo3 分别把两种思路拆开细讲。


## 8. 选型判断（经验，不是铁律）

```text
任务能拆成清晰流水线      → 优先看 CrewAI 思路
需要多角色反复讨论/协商    → 优先看 AutoGen 思路
要精细控制状态机和分支     → 其实用 LangGraph 更合适（前两节已学）
```

所以本节结论不是"哪个更好"：

```text
没有最好的框架，只有最匹配场景的编排思路。
```

## 9. 为什么用轻量模拟而不是装真实框架

1. 大纲定位是了解思想、做选型判断，不是精通 API
2. 真实 AutoGen/CrewAI 依赖重、要 LLM API Key 才能跑，会卡在环境配置而非学思想
3. 用 dataclass 把"对话驱动"和"任务驱动"的编排骨架抽出来，差异一目了然
4. 以后真要做选型，对照这里的思路读官方文档会更快

## 10. 本节一句话总结

```text
AutoGen 看对话，CrewAI 看任务，LangGraph 看状态图。
```

三者不是互斥，真实项目可能组合使用：

```text
LangGraph 做主流程控制
AutoGen 思路用在需要讨论的环节
CrewAI 思路用在流程清晰的环节
```
