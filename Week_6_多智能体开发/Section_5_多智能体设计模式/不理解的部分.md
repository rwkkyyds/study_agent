## 问题 1：熔断器的"半开（half_open）"状态到底干嘛的？为什么不直接从 open 回到 closed？

**原问题：**
demo2 里 CircuitBreaker 说有"三态"，但代码里只看到 closed 和 open，half_open 到底是什么？为什么要搞这么复杂，熔断后冷却结束直接恢复 closed 不行吗？

**AI 通俗解释：**
想象你家保险丝烧了：

```text
closed  = 正常用电，一切正常
open    = 保险丝断了，完全断电保护
half_open = 修好后先"试探性"通一下电，看看还烧不烧
```

如果冷却后直接恢复 closed，万一下游还没修好，就会瞬间又被打爆。
half_open 是"只允许一次试探调用"：
- 试探成功 → 说明下游恢复了 → 转为 closed 正常服务
- 试探失败 → 说明下游还坏着 → 重新 open，继续冷却

demo2 代码里用 `is_open()` 的冷却判断简化了这一步：冷却结束就重置计数（相当于 half_open 的试探）。真实生产库（如 pybreaker）会严格区分三态。

**配套示例代码：**
```python
class CircuitBreaker:
    def is_open(self) -> bool:
        if self.opened_at is None:
            return False  # closed 态
        # 冷却时间到了 → 进入 half_open，允许试探
        if time.time() - self.opened_at > self.cooldown:
            self.opened_at = None
            self.fail_count = 0
            return False  # 相当于 half_open 放行一次
        return True  # 还在 open 态，拒绝调用
```

**易错点总结：**
- half_open 不是"永久恢复"，是"试探一次"，失败会重新 open
- demo2 是简化版，生产库有严格的三态状态机
- 冷却时间 ≠ 恢复，冷却只是给 half_open 的机会

## 问题 2：指数退避为什么是 `0.1 * 2^(attempt-1)`？这个公式怎么来的？

**原问题：**
`backoff = 0.1 * (2 ** (attempt - 1))` 这行看不太懂，为什么是 2 的幂次？为什么减 1？

**AI 通俗解释：**
指数退避的核心是"每次等待时间翻倍"：

```text
第1次重试前等 0.1s   = 0.1 * 2^0 = 0.1
第2次重试前等 0.2s   = 0.1 * 2^1 = 0.2
第3次重试前等 0.4s   = 0.1 * 2^2 = 0.4
```

为什么是 2 的幂：翻倍增长，前期快试探（赶紧试），后期慢等待（给下游恢复时间）。
为什么 `attempt - 1`：因为 attempt 从 1 开始，但第一次重试应该等 base 时间（2^0=1 倍），不是 2 倍。

类比：你打电话给朋友没人接，你会先等 1 分钟再打，再没人接等 2 分钟，再没有等 4 分钟——不会一上来就等 4 分钟。

**配套示例代码：**
```python
for attempt in range(1, max_retries + 1):  # attempt = 1,2,3
    try:
        result = handler(user_input)
        return result
    except Exception:
        pass
    if attempt < max_retries:
        backoff = 0.1 * (2 ** (attempt - 1))  # 0.1, 0.2, 0.4
        time.sleep(backoff)
```

**易错点总结：**
- attempt 从 1 开始，所以要减 1 才能让第一次等 base 时间
- 生产环境会加随机抖动（jitter），防止多个客户端同时重试撞车
- 不是所有失败都该重试（参数错误重试也没用）

## 问题 3：demo3 里业务 Agent 的重试逻辑为什么写在 `while` 循环里，而不是用 call_with_resilience？

**原问题：**
demo2 明明写了 `call_with_resilience` 这个标准容错模板，为什么 demo3 的业务 Agent 重试却用 `while state.retry_count <= max_retries` 手写？两套重试逻辑不冲突吗？

**AI 通俗解释：**
这是两种实现风格，目的一样：

```text
demo2：通用函数式   → call_with_resilience() 包裹任意 handler，适合独立工具
demo3：图节点式    → 重试写在图的节点循环里，因为要更新 state（retry_count、status）
```

demo3 的业务 Agent 是 LangGraph 节点，节点需要读写 `TicketState`（记日志、改状态）。
如果套 call_with_resilience，重试发生在函数内部，state 的 retry_count 和日志就没法同步更新。

所以 demo3 在图引擎层（TicketGraph.run）写 while 循环，每次重试都能 add_log 记录到 state。
两种写法本质都是"超时→重试→降级"，只是挂的位置不同。

**配套示例代码：**
```python
# demo3 的图引擎层重试（能更新 state）
while state.retry_count <= max_retries:
    try:
        state = process_business_node(state)  # 节点内自增 retry_count
        break
    except RuntimeError:
        if state.retry_count >= max_retries:
            state = degrade_node(state)  # 降级也写入 state
            break
        state.add_log("重试中...")
```

**易错点总结：**
- demo2 是"工具级容错"，demo3 是"图节点级容错"，不冲突
- 选哪种看是否需要在重试过程中更新共享状态
- 生产里如果用真 LangGraph，重试通常包在节点函数内部 + 外层图的降级边

## 问题 4：分层模式里 manager 怎么知道把任务分给哪个 worker？

**原问题：**
demo1 的 HierarchicalSystem 里 manager_handle 收到目标后，是怎么决定分给 order_worker 还是 consult_worker 的？

**AI 通俗解释：**
看 demo1 的 router 函数，本质就是 if/else 关键词匹配：

```text
manager 接收目标："客户要求退款，订单号12345"
       ↓
router(goal, workers) 判断：
  if "退款" in goal or "订单" in goal → return workers[0]  # order_worker
  else                                → return workers[1]  # consult_worker
```

真实场景里这个 router 会换成 LLM 分类，但逻辑一样：根据目标内容选 worker。
manager 本身不干活，只做"分发决策"，这是分层模式的核心。

**配套示例代码：**
```python
def router(goal: str, workers: list[Agent]) -> Agent:
    if "退款" in goal or "订单" in goal:
        return workers[0]   # 订单处理 Agent
    return workers[1]       # 咨询 Agent

# manager_handle 里调用 router 做分发
def manager_handle(self, goal: str) -> str:
    worker = router(goal, self.workers)
    return worker.handle(goal)
```

**易错点总结：**
- manager 的职责是分发，不是执行
- router 可以是规则匹配，也可以换 LLM 分类
- worker 太多时 router 会变成瓶颈，生产里会分多级 manager

## 问题 5：流水线模式和对等模式看起来都是多个 Agent 串着跑，区别到底在哪？

**原问题：**
PipelineSystem 是按 stages 顺序跑，对等模式也是 A→B→C 互相调用，感觉差不多？

**AI 通俗解释：**
关键区别是"有没有固定顺序"和"谁控制流程"：

```text
流水线：固定顺序，单向流动，上游不关心下游
  A → B → C → 结果    （A 干完就退出，不参与后续）

对等：  无固定顺序，互相驱动，可以往复
  A ⇄ B ⇄ C    （A 说完 B 可以反驳，B 反驳后 A 再回应）
```

流水线像工厂流水线：每道工序固定，做完传给下一道。
对等像开会讨论：没有固定发言顺序，谁有补充谁说话，直到达成共识。

**配套示例代码：**
```python
# 流水线：单向，固定顺序
class PipelineSystem:
    def run(self, goal: str) -> str:
        data = goal
        for stage in self.stages:       # 固定顺序遍历
            data = stage.handle(data)   # 上游产出喂下游
        return data

# 对等：可往复，靠 speaker 选举决定谁说话
class PeerToPeerSystem:
    def run(self, goal: str) -> str:
        # 多轮对话，每轮选一个发言，直到满足终止条件
        ...
```

**易错点总结：**
- 流水线是"单向无回头"，对等是"可往复"
- 对等模式必须有 speaker 选举 + 终止条件，否则无限循环
- CrewAI 的 kickoff 本质是流水线，AutoGen 的 GroupChat 本质是对等

## 问题 6：降级结果为什么要"明确标记"？不标记会有什么后果？

**原问题：**
demo2 和 demo3 都强调降级结果要标记（如"【降级】"前缀），为什么不能直接返回一个普通结果假装成功？

**AI 通俗解释：**
因为降级结果不是"真正的成功"，是"凑合的结果"：

```text
用户问："查我的订单状态"
正常结果：订单已发货，预计明天到
降级结果：【降级】订单查询暂不可用，已记录转人工
```

如果不标记，下游（或用户）会以为查到了真实数据，基于错误信息做决策。
标记的作用：
1. 下游看到标记可以决定要不要转人工
2. 监控可以统计降级率，发现系统健康度下降
3. 不会把"凑合结果"误当"成功结果"上报

**配套示例代码：**
```python
# 降级结果必须带明确标记
fallback = "【降级输出】该环节暂不可用，已用兜底结果"
# state 层面也要改 status
state.status = TicketStatus.DEGRADED  # 不是 PROCESSED
```

**易错点总结：**
- 降级 ≠ 成功，状态必须区分（DEGRADED vs PROCESSED）
- 降级结果必须能被监控统计到
- 降级后通常要触发人工跟进，不是默默吞掉
