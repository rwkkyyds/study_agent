# Week 6 Section 5：生产级高频面试题

## 1. 多智能体有哪几种经典设计模式？各自适合什么场景？

三种：

```text
分层（Hierarchical）：有 manager 统筹分发，适合分级指挥（客服分级、订单处理）
对等（Peer-to-Peer）：无中心，Agent 互相调用，适合讨论协商（方案评审、头脑风暴）
流水线（Pipeline）  ：串行传递，上游喂下游，适合流程固定（调研→写作→审核发布）
```

面试可以这样说：

```text
不是选一个用到底。主流程用流水线，需要讨论的环节用对等，需要分级指挥的环节用分层。
关键是匹配业务环节的特性。
```

## 2. 分层和对等的核心区别是什么？

```text
分层有中心（manager），控制流是单向分发：manager 接收 → 分给 worker → 汇总
对等无中心，控制流是互相驱动：Agent A 发言 → Agent B 回应 → 往复直到收敛
```

分层适合明确指挥链的场景，对等适合需要多方协商、没有固定顺序的场景。

## 3. 流水线模式和 CrewAI 的 kickoff 有什么关系？

思路一致：都是按依赖顺序串行，上游产出喂给下游。

```text
PipelineSystem.run() = 按顺序遍历 stages，上一个产出喂下一个
Crew.kickoff()       = 按 context_from 拓扑排序，上一个产出喂下一个
```

面试可以说：

```text
流水线模式就是 CrewAI 任务驱动的核心思想，任务依赖决定执行顺序，每步产出作为下步输入。
```

## 4. 多智能体系统为什么需要容错？

因为单个 Agent 可能：

```text
超时（LLM 响应慢、网络抖动）
报错（工具 API 挂了、参数错误）
输出垃圾（模型幻觉、格式错误）
无限循环（Agent 互相调用停不下来）
```

如果没有容错，一个 Agent 挂了会阻塞整个流程，甚至拖垮整个系统。

一句话：

```text
容错的本质是：单个 Agent 的故障不能传染给整个系统。
```

## 5. 四层容错分别是什么？从外到内的顺序？

```text
第1层 熔断：连续失败的 Agent 被隔离，后续直接跳过（CircuitBreaker）
第2层 超时：单个 Agent 执行有时间上限，防止卡死
第3层 重试：失败后指数退避重试（最多N次）
第4层 降级：重试耗尽用兜底结果，不阻塞下游
```

执行顺序（call_with_resilience 标准模板）：

```text
1. 熔断检查 → 已熔断直接返回兜底
2. 尝试执行 → 超过 timeout 抛 TimeoutError
3. 失败 → 指数退避等待 → 重试
4. 重试耗尽 → 返回 fallback 降级输出
5. 成功/失败都更新熔断器计数
```

## 6. 熔断器（CircuitBreaker）的三态是什么？

```text
closed（正常）   → 正常调用
open（熔断）     → 连续失败达 threshold 次，拒绝调用，直接返回兜底
half_open（试探）→ 冷却期过后，允许一次试探调用：成功则 closed，失败则 open
```

面试可以说：

```text
熔断器像电路保险丝，连续失败就断开保护系统。冷却期后会试探性恢复，避免永久隔离一个只是临时故障的 Agent。
```

## 7. 指数退避是什么？为什么用它？

指数退避：每次重试前等待时间翻倍。

```text
第1次重试前等 0.1s
第2次重试前等 0.2s
第3次重试前等 0.4s
```

为什么用：

```text
1. 避免雪崩：如果所有失败都立即重试，会瞬间打满下游
2. 给故障恢复时间：很多故障是瞬时的，等一会就恢复
3. 递增等待比固定等待更高效
```

## 8. 降级输出是什么？为什么不能直接抛异常？

降级：重试耗尽后返回一个兜底结果（fallback），不阻塞下游流程。

为什么不直接抛异常：

```text
多智能体系统的目标是"完成整体任务"，不是"每个 Agent 都成功"。
如果业务 Agent 挂了就抛异常，整个工单流程就卡住，用户拿不到任何结果。
降级让系统继续运转（哪怕结果不完美），并标记转人工跟进。
```

面试可以说：

```text
生产系统的容错哲学是：宁可给降级结果也不让流程卡死。降级结果要明确标记，触发人工跟进，不是假装成功。
```

## 10. HITL 在多智能体系统里放在哪一步？

放在高风险决策点，比如：

```text
退款超过阈值 → 暂停等人审
合同条款生成 → 暂停等人审
敏感数据访问 → 暂停等人审
```

不是所有步骤都加 HITL，只加在"一旦出错代价高"的节点。

面试可以说：

```text
HITL 只加在高风险节点，不是每个节点都暂停。判断标准是：这个动作一旦执行，撤销成本多高。退款金额大、合同发布、数据删除这类才加人审。
```

## 11. 多智能体系统怎么选设计模式？

从业务环节特性出发：

```text
环节有明确指挥链、可分级分发 → 分层
环节需要多方讨论、协商        → 对等
环节能拆成固定步骤、步骤固定  → 流水线
环节需要条件分支、循环、子图  → LangGraph 状态图
```

一个项目里不同环节可能用不同模式，组合使用。

## 12. 多智能体系统上线有什么风险？

```text
Agent 互相循环调用，停不下来
单个 Agent 超时拖垮整个流程
没有熔断，故障 Agent 被反复调用
降级结果没标记，假装成功
HITL 加太多，流程卡在人审
没有 max_round，对话型 Agent 无限聊
token 和成本不可控
```

生产建议：

```text
必须有 max_round / termination 兜底
每个 Agent 调用套四层容错
降级结果要明确标记并触发人工跟进
HITL 只加在高风险节点
加 trace 和 metrics 观测执行过程
```
