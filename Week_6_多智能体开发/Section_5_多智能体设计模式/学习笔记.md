# Week 6 Section 5 学习笔记：多智能体设计模式、异常处理与容错

## 1. 本节核心结论

前四节学了单个 Agent 怎么定义、多 Agent 怎么编排。这一节解决两个工程问题：

```text
1. 多个 Agent 怎么组织协作？用哪种结构？   ← 设计模式
2. 某个 Agent 挂了/超时了/输出垃圾怎么办？  ← 容错
```

一句话结论：

```text
设计模式不是选一个用到底，而是根据业务环节特性组合。
容错的本质是：单个 Agent 的故障不能传染给整个系统。
```

这一节也是第6周的收尾，把前四节串成第6周综合 Demo。

## 2. 三种经典设计模式（先记这张表）

| 模式 | 结构 | 谁适合 | 典型场景 |
|------|------|--------|----------|
| 分层（Hierarchical） | 有 manager 统筹，向下分发 | 流程可拆、有明确指挥 | 客服分级、订单处理 |
| 对等（Peer-to-Peer） | 无中心，Agent 互相调用 | 需要讨论/协商 | 方案评审、头脑风暴 |
| 流水线（Pipeline） | 串行传递，上游产出喂下游 | 流程清晰、步骤固定 | 调研→写作→审核发布 |

一句话类比：

```text
分层 = 公司有部门经理，经理派活给组员
对等 = 几个专家圆桌讨论，谁有信息谁发言
流水线 = 工厂流水线，上一道工序的半成品交给下一道
```

## 3. demo1 复盘：三种设计模式对比

文件：

```text
demo1_design_patterns.py
```

同一个目标"处理一个工单"，分别用三种结构跑一遍，看清控制流差异。

### 分层模式（Hierarchical）

核心：一个 manager 负责分发和汇总，worker 只管干自己的活。

```text
manager 接收目标 → router 判断分给谁 → worker 执行 → manager 汇总
```

关键抽象：
- `HierarchicalSystem`：有 manager + workers + router
- `router`：决定分给哪个 worker（对应 AutoGen 的 speaker 选择，但分层是单向分发，不是轮流发言）

适合：分级指挥场景，比如客服系统 manager 分类后分给技术组/业务组。

### 对等模式（Peer-to-Peer）

核心：没有 manager，Agent 之间直接互相调用，靠内容驱动推进。

```text
tech 开场 → legal 回应 → business 回应 → 检测收敛 → 结束
```

关键抽象：
- `PeerToPeerSystem`：只有 agents 列表，无中心
- 收敛条件：输出里出现"达成一致"就停（对应真实框架的 termination）

和分层的关键区别：对等没有中心，谁接话靠轮流或内容判断，适合讨论协商。

### 流水线模式（Pipeline）

核心：Agent 按固定顺序串行，上一个产出喂给下一个。

```text
collector → cleaner → analyzer → reporter
```

关键抽象：
- `PipelineSystem`：只有 stages 列表，按顺序执行
- 每一 stage 拿上一 stage 的产出继续加工

和分层的关键区别：流水线顺序固定，不分发不路由；和 CrewAI 的 kickoff 思路一致。

## 4. demo2 复盘：四层容错

文件：

```text
demo2_resilient_multiagent.py
```

单个 Agent 可能：超时、报错、输出垃圾、无限循环。多智能体系统必须保证一个 Agent 挂了不拖垮整个系统。

### 四层容错（从外到内）

```text
第1层 熔断：连续失败的 Agent 被隔离，后续直接跳过
第2层 超时：单个 Agent 执行有时间上限，防止卡死
第3层 重试：失败后指数退避重试（最多3次）
第4层 降级：重试耗尽用兜底结果，不阻塞下游
```

### CircuitBreaker 熔断器

三态（简化为两态 + 计数）：

```text
closed（正常）→ 连续失败 N 次 → open（熔断，拒绝调用）
                              ↓ 冷却时间过后
                          half_open（试探）→ 成功则 closed / 失败则 open
```

关键参数：
- `threshold`：连续失败多少次触发熔断
- `cooldown`：熔断后冷却多久才允许试探

### call_with_resilience 标准模板

这是多智能体容错的"标准调用模板"，生产里每个 Agent 调用都该套这层：

```text
1. 熔断检查（is_open）→ 已熔断直接返回兜底
2. 超时保护（timeout）→ 超过时间上限抛 TimeoutError
3. 重试 + 指数退避（max_retries + backoff = 0.1 * 2^attempt）
4. 重试耗尽 → 降级输出（fallback）
5. 成功/失败都更新熔断器计数
```

### 四个场景演示

```text
场景1 fast_agent   ：秒回，正常
场景2 slow_agent   ：0.8s 超过 0.3s 上限 → 重试3次全超时 → 降级
场景3 flaky_agent   ：前两次 RuntimeError，第三次成功 → 重试恢复
场景4 always_fail   ：永久故障 → 连续3次失败触发熔断 → 第4次直接跳过
```

## 5. demo3 复盘：第6周综合 Demo

文件：

```text
demo3_week6_demo.py
```

智能客服工单处理系统，整合第6周全部知识点。

### 整合的知识点

```text
Section 1 LangGraph 高级工作流 → 条件路由（classify → route_node）
Section 2 HITL                 → 高额退款暂停等人审（human_approval_node）
Section 3 Agent SDK 生态       → 多个 Agent 角色定义
Section 4 AutoGen/CrewAI       → 多 Agent 编排（分层 + 流水线）
Section 5 设计模式 + 容错       → 业务 Agent 重试 + 降级
```

### 工单处理流程

```text
用户提交工单
  ↓
classify_node（分类 Agent）
  ↓ route_node 条件路由
  ├─ 技术问题 → process_tech_node → 完成
  ├─ 普通退款 → process_business_node（带重试）
  │            ├─ 成功 → 完成
  │            └─ 重试耗尽 → degrade_node → 降级
  └─ 高额退款 → human_approval_node（HITL 暂停）
                ├─ 审批通过 → execute_refund_node → 完成
                └─ 审批拒绝 → 归档
```

### 三个场景

```text
T001 技术问题   → 自动处理，秒完
T002 普通退款100 → 业务 Agent 第1次失败，重试第2次成功
T003 高额退款2000 → HITL 暂停等人审 → 审批通过 → 执行退款
```

### 为什么用纯 Python 模拟 LangGraph

为了零依赖可运行，demo3 用纯 Python 模拟 LangGraph 的图执行逻辑。控制流和真实 LangGraph 完全对应：

```text
StateGraph → TicketState
Node       → classify_node / route_node / process_xxx_node
conditional_edges → route_node 返回下一节点名
interrupt  → human_approval_node 设 PENDING_APPROVAL 状态
```

真实项目里把这套结构换成 `langgraph.StateGraph` 即可，业务逻辑不变。

## 7. 本节一句话总结

```text
设计模式根据业务环节组合，容错保证单个 Agent 故障不传染。
```

三种模式不是互斥，真实项目可能：

```text
主流程用流水线（调研→写作→审核）
需要讨论的环节用对等（多方评审）
需要分级指挥的环节用分层（客服分级）
全程套四层容错（熔断+超时+重试+降级）
```
