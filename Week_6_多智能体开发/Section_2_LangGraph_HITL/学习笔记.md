# Week 6 Section 2 学习笔记：LangGraph HITL

## 1. 本节核心结论

HITL 是 Human-in-the-loop，核心不是简单地让用户 `input()` 一下，而是：

```text
Agent 流程执行到关键节点时可以暂停；
暂停时把需要人工判断的信息抛出去；
人工给出结果后，流程能从原来的暂停点继续。
```

本节通过三个 demo 跑通了：

- 最小人工审批
- 退款审批工作流
- 人工编辑后再发送

你要重点记住这四个关键词：

```text
interrupt()      暂停流程，向外抛出人工确认请求
MemorySaver      保存暂停时的流程状态
Command(resume=) 带着人工结果恢复流程
thread_id        找回同一条被暂停的流程
```

## 2. demo1 复盘：最小审批流程

运行文件：

```text
demo1_interrupt_approval_basic.py
```

流程：

```text
prepare_action
  -> approve_action
  -> execute_action
```

`approve_action` 是关键节点。

它里面调用：

```python
decision = interrupt(
    {
        "question": "是否批准执行这个动作？",
        "task": state["task"],
        "suggested_options": ["approve", "reject"],
    }
)
```

第一次运行到这里时，流程会暂停。

暂停结果会出现在：

```python
first_result["__interrupt__"][0].value
```

这份 value 就是要交给人的信息。

第二次恢复时：

```python
app.invoke(Command(resume="approve"), config=config)
```

LangGraph 会回到刚才 `interrupt()` 那一行，并让 `interrupt()` 返回 `"approve"`。

所以恢复后可以理解成：

```python
decision = "approve"
```

然后流程继续进入 `execute_action`。

## 3. demo2 复盘：退款审批工作流

运行文件：

```text
demo2_refund_approval_workflow.py
```

流程：

```text
analyze_refund
  -> auto_refund
  -> human_approval
  -> finish_refund
```

这里有一个条件路由：

```text
小额退款 -> 自动通过
大额退款 -> 暂停，等待人工审批
```

核心判断：

```python
need_human = state["amount"] >= 100
```

这个 demo 说明一个生产级思路：

```text
不是所有请求都要人工处理。
低风险请求自动化，高风险请求交给人。
```

这比“所有事情都让 Agent 自己做”更适合真实业务。

## 4. demo3 复盘：人工编辑后再发送

运行文件：

```text
demo3_edit_before_send.py
```

流程：

```text
generate_draft
  -> human_edit
  -> send_reply
```

这个 demo 最容易误解。

`human_version` 不是作为普通函数参数传给 `human_edit(state)` 的。

真实传入点是：

```python
app.invoke(Command(resume=human_version), config=config)
```

第一次运行时：

```python
edited_reply = interrupt(...)
```

流程会暂停，并把 `draft_reply` 抛给外部。

第二次恢复时：

```python
Command(resume=human_version)
```

会让 `interrupt()` 直接返回 `human_version`。

所以恢复后等价于：

```python
edited_reply = human_version
return {"final_reply": edited_reply}
```

完整理解：

```text
第一次 invoke：
generate_draft -> human_edit -> interrupt 暂停
                                ↓
                         把草稿交给人工审核

第二次 invoke：
Command(resume=human_version)
                                ↓
                         回到 interrupt 位置
                                ↓
                         interrupt 返回 human_version
                                ↓
                         final_reply = human_version
                                ↓
                         send_reply
```

真实项目里，`human_version` 一般来自前端客服输入框。

## 5. config 和 thread_id 为什么重要

每个 HITL demo 都有类似配置：

```python
config = {"configurable": {"thread_id": "edit-before-send"}}
```

`thread_id` 的作用是标识同一条流程。

你可以把它理解成：

```text
这次暂停的是哪一个用户、哪一笔订单、哪一条审批流。
```

如果没有稳定的 `thread_id`，第二次恢复时 LangGraph 就不知道要恢复哪条流程。

生产项目里，`thread_id` 常见来源：

- 用户会话 ID
- 工单 ID
- 订单 ID
- 审批单 ID
- 任务执行 ID

## 6. MemorySaver 是什么

`MemorySaver` 是一个内存版 checkpointer。

它负责保存图在暂停时的状态。

demo 里这样写：

```python
return graph.compile(checkpointer=MemorySaver())
```

注意：

```text
MemorySaver 适合 demo 和本地学习；
生产环境通常要换成持久化存储。
```

因为进程重启后，内存里的暂停状态会丢失。

生产里更常见的是：

- 数据库存储 checkpoint
- Redis 存储临时状态
- 专门的任务状态表
- 与审批系统/工单系统集成

## 7. HITL 和普通 input() 的区别

普通 `input()`：

```text
程序卡在当前终端里，等人输入。
```

LangGraph HITL：

```text
流程暂停；
状态保存；
请求可以发给前端、客服系统或审批系统；
人稍后再提交结果；
流程从暂停点恢复。
```

所以 HITL 更适合 Web 服务和生产系统。

## 8. 什么时候必须考虑 HITL

只要 Agent 要做会产生真实后果的事情，就应该考虑 HITL。

常见场景：

- 删除数据
- 退款
- 发邮件
- 提交代码
- 执行部署
- 修改数据库
- 调用付费 API
- 给客户最终答复
- 给出赔偿方案

简单判断标准：

```text
如果 Agent 做错了会造成损失，就不要让它完全自动拍板。
```

## 9. 生产级设计建议

设计 HITL 时，至少要想清楚：

- 哪些动作需要人工确认
- 暂停时要给人看哪些上下文
- 人可以返回哪些结果
- 拒绝后流程怎么走
- 超时未审批怎么办
- 审批记录怎么审计
- 流程状态保存在哪里
- 同一条流程如何用 thread_id 找回

不要只写一个 `approve/reject`。

真实业务里经常还有：

```text
approve      批准
reject       拒绝
edit         修改后通过
need_more    要求补充信息
escalate     升级给更高级别人工
timeout      超时自动关闭或提醒
```

## 10. 本节一句话总结

```text
HITL 是给 Agent 加可恢复的人工刹车：危险动作先暂停，人确认后再从原位置继续。
```

你先记住这条主线：

```text
interrupt 抛出问题 -> checkpointer 保存状态 -> 人给结果 -> Command(resume=结果) 恢复流程
```
