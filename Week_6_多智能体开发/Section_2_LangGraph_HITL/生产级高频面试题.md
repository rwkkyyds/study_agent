# Week 6 Section 2：生产级高频面试题

## 1. 什么是 HITL？

HITL 是 Human-in-the-loop，意思是人在关键节点参与 Agent 流程。

面试可以这样回答：

```text
在生产级 Agent 系统里，并不是所有动作都应该由模型自动决定。
对于删除数据、退款、发邮件、执行部署这类高风险动作，我会用 HITL 让流程先暂停，
把上下文交给人工确认，再根据人工结果恢复流程。
```

## 2. LangGraph 里 HITL 靠什么实现？

核心组件有四个：

- `interrupt()`：暂停当前流程，并抛出人工确认请求
- `Command(resume=...)`：带着人工输入恢复流程
- `checkpointer`：保存暂停时的状态
- `thread_id`：标识要恢复哪一条流程

面试表达：

```text
LangGraph 的 HITL 不是阻塞式 input，而是可暂停、可保存、可恢复的工作流机制。
```

## 3. interrupt() 的作用是什么？

`interrupt()` 的作用是让图执行到某个节点时暂停。

它会把需要人工处理的信息抛出去，比如：

```text
问题描述
当前任务
草稿回复
订单金额
建议选项
风险提示
```

恢复时，`interrupt()` 会返回 `Command(resume=...)` 传入的值。

## 4. Command(resume=...) 是怎么工作的？

`Command(resume=人工结果)` 用来恢复一条已经暂停的流程。

比如：

```python
app.invoke(Command(resume="approve"), config=config)
```

可以理解为：

```text
回到上次 interrupt() 暂停的位置，
让 interrupt() 返回 "approve"，
然后继续执行后面的节点。
```

## 5. thread_id 为什么重要？

`thread_id` 用来标识同一条流程。

没有 `thread_id`，系统不知道第二次恢复时应该恢复哪一个暂停点。

生产里可以用：

- 工单 ID
- 订单 ID
- 用户会话 ID
- 审批单 ID
- 任务执行 ID

面试表达：

```text
thread_id 是恢复流程的关键索引，我会用业务唯一 ID 来绑定一条 Agent 执行链路。
```

## 6. MemorySaver 能不能用于生产？

一般不建议。

`MemorySaver` 是内存版 checkpointer，适合 demo、本地学习和单进程验证。

生产里有几个问题：

- 服务重启后状态丢失
- 多实例部署时状态不共享
- 不方便审计和排查
- 无法支撑长时间审批流程

生产建议：

```text
使用数据库、Redis 或持久化 checkpoint 存储，把暂停状态和审批记录保存下来。
```

## 7. HITL 和普通 input() 有什么区别？

普通 `input()`：

```text
只能在当前终端阻塞等待输入。
```

HITL：

```text
流程可暂停；
状态可保存；
人工输入可以来自前端、审批系统、客服系统；
流程可以稍后恢复；
适合 Web 服务和分布式系统。
```

面试表达：

```text
input 是脚本级交互，HITL 是工作流级暂停恢复。
```

## 8. 什么场景必须做 HITL？

高风险、不可轻易回滚、涉及用户权益或资金的动作，都应该考虑 HITL。

典型场景：

- 删除用户数据
- 执行退款
- 发送客户邮件
- 执行线上部署
- 修改数据库
- 处理投诉赔偿
- 调用高成本 API
- 输出法律、医疗、金融等高风险建议

## 9. 如何设计一个退款审批 Agent？

可以这样回答：

```text
我会先让 Agent 分析退款金额、订单状态、用户原因和历史风险。
小额、低风险退款可以自动通过；
大额或异常退款进入 HITL 节点，暂停流程，把订单、金额、原因、风险提示交给客服主管审批。
审批通过后执行退款，拒绝后生成拒绝原因，并记录完整审计日志。
```

这个回答体现了：

- 自动化不是全自动
- 风险分层
- 人工审批
- 审计记录

## 10. 如何设计“人工编辑后再发送”的 Agent？

可以这样回答：

```text
Agent 先生成回复草稿，然后进入 human_edit 节点。
human_edit 通过 interrupt() 把用户问题和草稿回复交给客服审核。
客服可以直接通过，也可以修改内容。
后端拿到编辑后的内容后，用 Command(resume=edited_text) 恢复流程，
最终发送的是人工确认后的版本。
```

注意重点：

```text
edited_text 不是普通函数参数，而是 interrupt() 的恢复值。
```

## 11. HITL 的返回值只能是 approve/reject 吗？

不是。

`Command(resume=...)` 可以传字符串、字典等结构化结果。

比如：

```python
Command(
    resume={
        "decision": "approve",
        "edited_reply": "修改后的客服回复",
        "reviewer": "manager_001",
        "comment": "确认可发送",
    }
)
```

生产里更推荐结构化返回，方便记录和分支判断。

## 12. 如果人工拒绝了怎么办？

不能只考虑批准路径。

拒绝后可以：

- 直接终止流程
- 生成拒绝说明
- 要求 Agent 重新生成方案
- 升级给更高级别人工
- 回滚前置动作
- 记录审计日志

面试表达：

```text
HITL 设计必须覆盖 approve、reject、edit、timeout、escalate 等分支，而不是只处理 happy path。
```

## 13. 如果人工一直不处理怎么办？

需要超时机制。

常见处理方式：

- 超时提醒
- 自动升级
- 自动关闭任务
- 自动走保守策略
- 标记为 pending_review

生产建议：

```text
审批流要有超时策略，否则暂停任务会无限堆积。
```

## 14. HITL 怎么做审计？

至少记录：

- 谁发起的任务
- 暂停时的上下文
- 谁审批的
- 审批结果
- 审批时间
- 修改前后的内容
- 最终执行结果

面试表达：

```text
高风险 Agent 操作必须可追踪、可回放、可审计。
```

## 15. HITL 在生产里有什么坑？

常见坑：

- 使用内存 checkpoint，服务重启后状态丢失
- 没有稳定 thread_id，无法恢复正确流程
- 只设计批准路径，没有拒绝和超时
- 暂停时给人工的信息不够，导致人无法判断
- 审批结果没有审计记录
- 多实例部署时 checkpoint 不共享
- 让 LLM 决定高风险动作，缺少人工兜底

```text
基于 LangGraph 实现 Human-in-the-loop Agent 工作流，使用 interrupt()、Command(resume=...)、
checkpoint 和 thread_id 完成流程暂停、人工审批、状态恢复，支持退款审批和客服回复人工编辑后发送等高风险场景。
```

如果放到项目描述里，可以升级为：

```text

通过持久化 checkpoint 保存流程状态，并记录审批日志，提升系统安全性和可审计性。
```

## 17. 一句话面试总结

```text
HITL 的价值是让 Agent 在高风险节点“可暂停、可审核、可恢复、可审计”，这是生产级 Agent 必须具备的安全机制。
```
