# Week 6 Section 1 学习笔记：LangGraph 高级工作流

## 1. 本节核心结论

LangGraph 高级工作流的核心不是“更高级的语法”，而是：

```text
让复杂 Agent 流程变得可拆、可看、可维护。
```

这一节通过三个 demo 跑通了：

- 并行节点
- 条件路由
- 子图 subgraph

这三个能力以后会频繁出现在生产级 Agent 项目里。

## 2. demo1 复盘：并行评审

运行文件：

```text
demo1_parallel_review_workflow.py
```

流程：

```text
receive_task
  -> product_review
  -> engineering_review
  -> risk_review
  -> merge_reviews
```

注意：`product_review`、`engineering_review`、`risk_review` 是从同一个节点分出去的。

它们可以理解为多个角色同时看同一个任务。

本 demo 里三个角色分别负责：

- 产品：看用户价值
- 工程：看实现成本
- 风险：看上线风险

最后由 `merge_reviews` 汇总。

### 重点代码

```python
graph.add_edge("receive_task", "product_review")
graph.add_edge("receive_task", "engineering_review")
graph.add_edge("receive_task", "risk_review")
graph.add_edge(["product_review", "engineering_review", "risk_review"], "merge_reviews")
```

这段意思是：

```text
receive_task 完成后，分发到三个评审节点；
三个评审都完成后，再进入 merge_reviews。
```

### 容易误解

并行不是为了炫技。

它适合处理互不依赖的任务。

比如：

```text
查知识库和查订单可以并行
产品评审和风险评审可以并行
但“先登录再查用户信息”不能并行
```

## 3. demo2 复盘：条件路由

运行文件：

```text
demo2_conditional_ticket_router.py
```

流程：

```text
classify_ticket
  -> payment
  -> tech
  -> human
```

`classify_ticket` 先判断用户问题属于哪一类。

然后 `route_ticket` 决定下一步去哪。

### 重点代码

```python
graph.add_conditional_edges(
    "classify_ticket",
    route_ticket,
    {
        "payment": "payment",
        "tech": "tech",
        "human": "human",
    },
)
```

这段可以翻译成：

```text
如果 route_ticket 返回 payment，就去 payment 节点；
如果返回 tech，就去 tech 节点；
如果返回 human，就去 human 节点。
```

这就是 LangGraph 里的条件路由。

### 开发场景

真实 AI 客服可以这样用：

```text
订单问题 -> 订单处理流程
技术报错 -> 技术排障流程
售前咨询 -> 销售知识库
高风险投诉 -> 人工处理
```

### 容易误解

条件路由不是一定要靠大模型判断。

本 demo 用关键词判断，是为了先把流程跑通。

真实项目里可以换成：

- 规则判断
- 分类模型
- LLM 分类
- 数据库状态判断
- 权限判断

## 4. demo3 复盘：子图 subgraph

运行文件：

```text
demo3_subgraph_order_pipeline.py
```

主图：

```text
receive_order
  -> run_check_subgraph
  -> finish_order
```

子图：

```text
check_inventory
  -> check_payment
```

主图负责大流程。

子图负责订单检查这一小段流程。

### 重点代码

```python
check_subgraph = build_check_subgraph()
```

这句是先构建一个小图。

然后主图里调用：

```python
checked_state = check_subgraph.invoke(state)
```

这就像在主流程里调用了一个“流程函数”。

### 子图的价值

子图不是必须用，但项目复杂后很有用。

比如：

```text
RAG 子图
  检索 -> 重排 -> 上下文检查

审批子图
  权限检查 -> 风险检查 -> 人工确认

订单子图
  库存检查 -> 支付检查 -> 风控检查
```

主图只负责串联大方向，细节交给子图。

## 5. State 是整条流程的“共享背包”

三个 demo 都有一个 State：

```python
class ReviewState(TypedDict):
    ...
```

你可以把 State 理解成：

```text
整个流程一路带着走的共享数据。
```

节点从 State 里读数据，也可以往 State 里写数据。

比如：

```text
用户问题
分类结果
处理步骤
最终回复
日志
```

都可以放在 State 里。

## 6. operator.add 是干嘛的

你会看到：

```python
reports: Annotated[list[str], operator.add]
```

它的意思是：

```text
多个节点都返回 reports 时，不要互相覆盖，而是追加合并。
```

这在并行流程里很重要。

否则三个评审节点都写 `reports`，后面的可能把前面的覆盖掉。

## 7. 什么时候该用 LangGraph

适合用：

- 流程有多个步骤
- 流程有分支
- 流程要循环
- 多个工具需要编排
- 需要保存执行状态
- 需要人工确认
- 需要把复杂流程拆成子流程

不一定要用：

- 只是简单问答
- 只是调用一次 LLM
- 只是一个很短的脚本

不要为了用 LangGraph 而用 LangGraph。

## 8. 本节一句话总结

```text
LangGraph 让 Agent 不再是一坨函数，而是一张清楚的流程图。
```

本节你先记住：

```text
并行：多个角色同时做
路由：不同输入走不同路
子图：复杂流程拆小块
```
