# Week 6 Section 1：不理解的部分记录

## 1. 为什么需要 LangGraph，直接写函数不行吗？

### 通俗解释

简单流程当然可以直接写函数。

比如：

```text
输入 -> 调模型 -> 输出
```

这种没必要上 LangGraph。

但 Agent 项目一复杂，就会变成：

```text
先分类
再检索
再判断资料够不够
不够就补查
够了就生成
生成后还要检查
风险高要转人工
失败还要重试
```

这时候如果全写在一个函数里，就会变成一团乱麻。

LangGraph 是把这团流程拆开：

```text
每个节点只做一件事
每条边说明下一步去哪
State 保存过程数据
```

## 2. 并行节点是不是越多越好？

不是。

并行只适合互不依赖的任务。

适合：

```text
产品评审、工程评审、风险评审
同时查询多个知识库
同时做安全检查和质量检查
```

不适合：

```text
先登录，再查用户信息
先生成订单，再支付
先检索，再基于检索结果生成
```

判断方法很简单：

```text
如果 B 必须等 A 的结果，就不能并行。
如果 A 和 B 可以各干各的，就可以并行。
```

## 3. Conditional Edge 到底是什么？

Conditional Edge 就是“分岔路口”。

比如客服系统：

```text
用户说订单支付失败 -> 去支付处理
用户说接口报错 -> 去技术处理
用户说想了解套餐 -> 去人工或售前
```

代码里就是：

```python
return state["route"]
```

返回 `payment` 就去 payment 节点。

返回 `tech` 就去 tech 节点。

返回 `human` 就去 human 节点。

## 4. State 为什么要设计好？

State 是整个流程一路带着走的数据包。

如果 State 设计混乱，后面所有节点都会难受。

好的 State 像这样：

```text
user_message
route
steps
reply
```

每个字段都有明确意义。

差的 State 像这样：

```text
data
result
temp
info
other
```

后期你会不知道里面到底放了什么。

## 5. operator.add 是什么，为什么不用普通 list？

在并行流程里，多个节点可能同时返回同一个字段。

比如三个评审节点都返回：

```text
reports
```

如果没有 `operator.add`，后面的结果可能覆盖前面的。

用了：

```python
reports: Annotated[list[str], operator.add]
```

意思是：

```text
多个节点返回 reports 时，把列表合并起来。
```

这样产品、工程、风险三个评审结果都能保留下来。

## 6. 子图 subgraph 和普通函数有什么区别？

普通函数封装的是代码。

子图封装的是流程。

比如普通函数：

```text
check_payment()
```

只代表一个动作。

子图可以代表一整段流程：

```text
检查库存 -> 检查支付 -> 检查风控
```

所以子图适合封装复杂业务流程。

## 7. 这节为什么没有接大模型？

因为本节核心是 LangGraph 的流程能力，不是 LLM 的回答能力。

如果一上来就接大模型，你可能会被这些东西干扰：

- API Key
- 网络
- 模型输出不稳定
- tool calling 格式
- 费用

所以这节先用确定性的 Python 逻辑，把流程跑通。

后面再把节点里的普通函数换成 LLM 调用，就能变成真正的 Agent 流程。

## 8. 这节最容易混淆的点

```text
Node：做事情的人
Edge：下一步去哪条路
State：一路带着的资料包
Conditional Edge：分岔路口
Subgraph：封装起来的小流程
```

用一个客服系统来记：

```text
用户问题进入 State
分类节点判断问题类型
条件边决定去订单/技术/人工
处理节点生成结果
复杂订单处理可以做成子图
```
