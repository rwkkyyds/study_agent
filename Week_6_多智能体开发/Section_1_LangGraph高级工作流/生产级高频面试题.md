# Week 6 Section 1：生产级高频面试题

## 1. LangGraph 是做什么的？

LangGraph 是用来做 Agent 工作流编排的。

开发视角可以这样回答：

```text
当 Agent 流程不再是简单一问一答，而是需要分支、循环、工具调用、状态管理、人工确认时，
我会用 LangGraph 把流程拆成节点和边，让执行路径更清晰、可维护。
```

## 2. LangGraph 和普通 Chain / Agent 有什么区别？

普通 Chain 更像固定流水线：

```text
A -> B -> C
```

普通 Agent 更像黑盒决策：

```text
模型自己决定下一步做什么
```

LangGraph 更像可控流程图：

```text
不同节点负责不同任务
条件边决定下一步
State 保存过程数据
可以循环、分支、并行、暂停、恢复
```

面试表达：

```text
Chain 适合线性任务，LangGraph 适合复杂 Agent 流程。
LangGraph 的优势是显式控制流程，便于调试、扩展和生产维护。
```

## 3. 什么是 State？为什么重要？

State 是整个 LangGraph 执行过程中流动的数据。

可以理解为：

```text
流程里的共享上下文。
```

比如客服 Agent 的 State 里可以放：

- 用户问题
- 分类结果
- 检索结果
- 工具调用结果
- 当前处理步骤
- 最终回复

生产里 State 很重要，因为复杂 Agent 不能只靠一条 prompt 记住所有东西。

## 4. 什么是 Node？

Node 是 LangGraph 里的一个处理步骤。

比如：

```text
分类节点
检索节点
生成回复节点
检查结果节点
转人工节点
```

每个节点最好只做一件明确的事。

这样后期排查问题时，你能知道是哪一步出了问题。

## 5. 什么是 Edge？

Edge 是节点之间的连接关系。

简单说就是：

```text
这个节点执行完，下一步去哪。
```

普通边是固定路线。

条件边是根据状态判断下一步。

## 6. 什么是 Conditional Edge？

Conditional Edge 是条件路由。

它根据当前 State 决定下一步走哪个节点。

比如：

```text
订单问题 -> 订单节点
技术问题 -> 技术节点
投诉问题 -> 人工节点
```

面试表达：

```text
我会用 conditional edge 做任务分流，比如先分类用户问题，再把不同类型的问题路由到不同处理流程。
```

## 7. LangGraph 里的并行适合什么场景？

并行适合互不依赖的任务。

比如：

- 同时查询多个数据源
- 多角色同时评审
- 多个工具并行执行
- 同时做安全检查和业务检查

不适合并行的场景：

```text
后一步依赖前一步结果。
```

比如必须先登录，再查用户信息，这就不能并行。

## 8. 什么是 Subgraph？为什么要用？

Subgraph 是子图，也就是把一段流程封装成小图。

它的作用类似函数封装，但封装的是流程，不只是代码。

适合：

- 复杂流程拆分
- 重复流程复用
- 团队分模块维护
- 主图保持清晰

面试表达：

```text
当主流程变复杂时，我会把可复用的流程拆成 subgraph，例如 RAG 检索流程、审批流程、订单检查流程，
这样主图负责整体编排，子图负责局部细节。
```

## 9. 为什么不用一堆 if-else 写 Agent 流程？

简单项目可以用 if-else。

但生产级 Agent 流程复杂后，if-else 会带来问题：

- 流程不直观
- 分支越来越难维护
- 调试困难
- 状态管理混乱
- 很难插入人工确认、重试、监控

LangGraph 的优势是把流程显式表达出来。

```text
节点负责处理，边负责流转，State 负责保存上下文。
```

## 10. LangGraph 在生产项目里常见应用有哪些？

常见应用：

- AI 客服工单分流
- RAG 多步骤检索与生成
- 代码生成 + 自检 + 修复流程
- 多工具 Agent 编排
- 多智能体协作
- Human-in-the-loop 审批流程
- 失败重试和降级流程

## 11. 如何设计一个 AI 客服 Agent 工作流？

可以这样回答：

```text
我会先设计一个分类节点，把用户问题分成订单、技术、售前、投诉等类型。
然后用 conditional edge 路由到不同处理子流程。
订单类会调用订单查询工具，技术类会查询日志或知识库，投诉类可能进入人工确认。
最后统一进入回复生成节点，并记录日志和监控指标。
```

这能体现你不是只会调模型，而是在设计工程流程。

## 12. 如何设计一个 RAG Agent 工作流？

可以这样回答：

```text
我会把 RAG 拆成检索、重排、上下文检查、生成、答案校验几个节点。
如果上下文不足，就通过条件边返回补充检索；
如果答案风险高，就进入人工确认或安全检查；
如果通过校验，再输出最终答案。
```

重点是体现：

- 不是一次检索就结束
- 可以根据结果继续分支
- 可以循环修正

## 13. LangGraph 怎么帮助调试？

LangGraph 把执行流程拆成节点，所以排查问题更清楚。

比如：

```text
是分类错了？
是检索没召回？
是工具调用失败？
是生成节点输出不稳定？
是路由规则错了？
```

每一步都可以单独打日志、记录状态、加监控。

## 14. LangGraph 有什么风险？

常见风险：

- State 设计太乱，字段越来越多
- 节点职责不清，一个节点做太多事
- 路由条件不稳定
- 流程图过度复杂
- 子图拆分过细，反而难理解
- 没有限制循环次数，可能死循环

生产建议：

```text
节点职责要小，State 字段要清楚，条件路由要可解释，循环必须有退出条件。
```
