# Week 6 Section 1 学习资料：LangGraph 高级工作流到底有什么用

## 1. 先说人话

LangGraph 高级工作流不是为了让代码看起来高级。

它解决的是一个很现实的问题：

```text
Agent 项目一复杂，流程会越来越多。
如果全靠 if-else 写，很快就会乱。
```

比如一个 AI 客服系统，用户一句话进来后，可能要做这些事：

```text
判断问题类型
查询订单
检索知识库
调用大模型
判断是否要转人工
记录日志
生成最终回复
```

如果这些都塞进一个函数里，后期维护会非常难。

LangGraph 的价值就是：**把复杂流程拆成一个个节点，让每一步都清楚地知道自己负责什么、下一步去哪里。**

## 2. 这节你真正要掌握什么

本节不是让你背 API，而是让你掌握三种开发能力：

```text
并行：同一个任务，多个角色同时处理
路由：不同输入，自动走不同处理流程
子图：复杂小流程，封装起来复用
```

这三个能力，是后面做多智能体系统和生产级 Agent 项目的基础。

## 3. demo1：并行评审工作流

文件：

```text
demo1_parallel_review_workflow.py
```

这个 demo 模拟一个需求评审：

```text
一个需求进来
  -> 产品角色看用户价值
  -> 工程角色看实现成本
  -> 风险角色看上线风险
  -> 最后统一汇总
```

你可以把它理解成真实公司里的小评审会。

为什么要并行？

因为很多 Agent 任务不是一步一步排队做，而是可以同时分工。

比如：

```text
代码助手：
  -> 一个节点分析需求
  -> 一个节点检查安全风险
  -> 一个节点检查影响范围
  -> 最后统一生成方案
```

这样比一个节点从头干到尾更清晰。

### 开发里什么时候用

- 多角色评审
- 多角度分析
- 多数据源同时查询
- RAG 里同时检索多个知识库
- Agent 同时调用多个不互相依赖的工具

## 4. demo2：条件路由工单系统

文件：

```text
demo2_conditional_ticket_router.py
```

这个 demo 模拟客服工单分流：

```text
用户问题进来
  -> 先分类
  -> 支付问题走 payment
  -> 技术问题走 tech
  -> 不明确问题走 human
```

这就是 Agent 系统里非常常见的“路由”。

你可以把它理解成：

```text
不是所有用户问题都应该走同一套处理流程。
```

比如：

```text
用户说支付失败
  -> 查订单、查支付流水

用户说接口报错
  -> 查日志、查服务状态

用户说想了解价格
  -> 转销售或人工确认
```

如果不用 LangGraph，你可能会写成一大堆 if-else。

用 LangGraph 后，流程会更清楚：

```text
classify_ticket
  -> payment
  -> tech
  -> human
```

### 开发里什么时候用

- 客服问题分流
- Agent 工具选择
- RAG 问题分类
- 任务优先级判断
- 失败后走重试、降级或人工处理

## 5. demo3：子图订单处理流程

文件：

```text
demo3_subgraph_order_pipeline.py
```

这个 demo 模拟订单处理：

```text
主图：
  收到订单
  -> 进入订单检查子图
  -> 根据检查结果决定是否继续

子图：
  检查库存
  -> 检查支付
```

子图的作用是：**把一段小流程封装起来。**

你可以把它理解成函数。

普通函数封装代码逻辑，子图封装流程逻辑。

### 为什么要子图

如果一个 Agent 系统越来越大，主流程可能变成这样：

```text
分类 -> 检索 -> 重排 -> 生成 -> 校验 -> 反思 -> 重试 -> 人工确认 -> 记录日志 -> 监控
```

这时候主图会很乱。

你可以把其中一段拆出去：

```text
RAG 子图：
  检索 -> 重排 -> 资料检查

安全检查子图：
  敏感词检查 -> 权限检查 -> 合规检查

订单处理子图：
  库存检查 -> 支付检查 -> 风险检查
```

主图只需要知道：

```text
这里进入一个子流程
子流程跑完后给我结果
```

### 开发里什么时候用

- 一段流程会重复用
- 主流程太长
- 团队里不同人负责不同模块
- 想把复杂 Agent 拆成更小的可维护单元

## 6. 三个能力放到真实 Agent 项目里怎么用

假设你做一个 AI 客服 Agent，可以这样设计：

```text
用户问题进入
  -> 条件路由：订单 / 技术 / 售前 / 投诉
  -> 并行处理：查订单 + 查知识库 + 查历史对话
  -> 子图封装：订单处理流程、技术排障流程、转人工流程
  -> 汇总回复
```

这就比一个大函数可靠很多。

## 7. 面试或项目里怎么表达

你可以这样说：

```text
我使用 LangGraph 做 Agent 工作流编排，把复杂任务拆成多个节点，
通过 conditional edge 实现任务路由，通过并行节点提升处理效率，
通过 subgraph 封装可复用流程，避免业务逻辑堆成难维护的 if-else。
```

这句话就比较像真实开发表达。

## 8. 本节你真正要带走什么

不要把 LangGraph 只理解成“写 Agent 的库”。

更准确地说：

```text
LangGraph 是用来管理 Agent 执行流程的。
```

当流程简单时，你可以不用它。

当流程开始出现：

```text
多分支
多角色
多工具
重试
人工确认
状态保存
子流程复用
```

这时候 LangGraph 就很有价值。
