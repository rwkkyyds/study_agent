# 第2周-Section_1：Query Transformation — 生产级高频面试题

## Q1: 什么是 Query Transformation？为什么需要它？

**答**：Query Transformation 是在检索前对用户问题进行改写/变换的技术。需要它的原因：
1. 用户问题太短，Embedding 语义信息不足
2. 用户口语化表述和文档书面化表述存在"语义鸿沟"
3. 单一问题可能包含多个子意图，检索覆盖面不够

**常见方法**：HyDE、多查询改写、问题分解、Step-Back Prompting。

---

## Q2: HyDE 的原理是什么？优缺点？

**答**：
**原理**：让 LLM 先生成一个"假设性答案文档"，用这个文档的 Embedding 去检索，而不是用原始问题。

**优点**：
- 假设文档比问题更长、语义更丰富，检索效果更好
- 实现简单，只需多一次 LLM 调用

**缺点**：
- 增加一次 LLM 调用的延迟和成本
- 假设文档质量依赖 LLM 能力，如果 LLM 幻觉严重，反而会误导检索
- 不适合实时性要求极高的场景

**适用场景**：用户问题短小、口语化，需要精确检索的场景。

---

## Q3: 多查询改写的原理？和 HyDE 有什么区别？

**答**：
**原理**：用 LLM 把一个问题从多个角度改写成多个子问题，分别检索，合并去重结果。

**和 HyDE 的区别**：
| 维度 | HyDE | 多查询改写 |
|------|------|-----------|
| 目标 | 让问题更像答案 | 让问题覆盖更多角度 |
| 输出 | 1个假设文档 | N个子问题 |
| 检索次数 | 1次 | N次 |
| 适用 | 问题短/口语化 | 多意图/模糊问题 |

**可组合使用**：先多查询改写，再对每个子问题做 HyDE。

---

## Q4: 多查询改写如何做结果去重？

**答**：
```python
seen = set()
unique_docs = []
for doc in all_docs:
    content_hash = hash(doc.page_content)
    if content_hash not in seen:
        seen.add(content_hash)
        unique_docs.append(doc)
```

**生产级优化**：
- 用文档ID去重（如果有唯一标识）
- 用内容相似度去重（cosine > 0.95 视为重复）
- 按相关性分数排序，保留最高分的去重结果

eg:相关性分数 ：
 步骤 1：把所有检索结果（包含重复）按分数从高到低排序
[
  文档A(0.92),
  文档B(0.90),
  文档A(0.85),  ← 重复
  文档C(0.83),
  文档A(0.78),  ← 重复
  文档B(0.70)   ← 重复
]

## Q5: HyDE 在什么情况下会失效？

**答**：
1. **LLM 对问题领域不熟悉**：生成的假设文档质量差，反而误导检索
2. **问题本身已经很具体**：如"Python 3.12 的 match 语法怎么用？"，直接检索就够了
3. **实时性要求高**：多一次 LLM 调用增加 200-500ms 延迟
4. **成本敏感**：大量请求下，多一次 LLM 调用成本显著

5. **判断标准**：如果直接检索 Top-1 的相似度 > 0.8，通常不需要 HyDE。意思即使加了 HyDE 也很难提升了。
---

## Q6: 除了 HyDE 和多查询改写，还有哪些 Query Transformation 方法？

**答**：
1. **Step-Back Prompting**：让 LLM 生成一个更通用/更高层的问题
   - 原问题："Python 的 GIL 是什么？"
   - Step-Back："Python 的并发机制有哪些？"

2. **问题分解（Query Decomposition）**：把复杂问题拆成子问题
   - 原问题："比较 RAG 和 Fine-tuning 的优缺点"
   - 子问题1："RAG 的优缺点是什么？"
   - 子问题2："Fine-tuning 的优缺点是什么？"

3. **HyPE（Hypothetical Prompt Embeddings）**：生成假设性问题（而非答案）

---

## Q7: 如何评估 Query Transformation 的效果？

**答**：
**评估指标**：
- **Recall@K**：改写后检索到的相关文档数是否增加
- **MRR（Mean Reciprocal Rank）**：正确文档的排名是否提前
- **NDCG**：检索结果的排序质量

**评估方法**：
1. 准备标注数据集（问题 + 相关文档）
2. 对比：直接检索 vs 改写后检索
3. 计算上述指标的提升幅度

**A/B 测试**：线上分流，对比用户满意度和答案准确率。

---

## Q8: 生产环境中如何控制 Query Transformation 的成本？

**答**：
1. **缓存**：相同问题的改写结果缓存（Redis / 本地缓存）
2. **路由判断**：简单问题直接检索，复杂问题才做改写
3. **用小模型**：改写不需要强模型，用 GPT-3.5 / GLM-4-Flash 即可
4. **异步并行**：多查询改写的子问题并行检索
5. **限制改写数量**：最多改写 3 个子问题，控制成本上限
