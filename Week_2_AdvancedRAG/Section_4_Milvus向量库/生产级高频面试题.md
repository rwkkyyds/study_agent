# Section 4 面试题：Milvus 生产级向量库

## 基础题

### 1. Milvus 和 FAISS 的核心区别是什么？

**答：**
- **FAISS** 是向量检索**库**，本质是一个算法库，提供向量索引和搜索算法，没有数据库特性
- **Milvus** 是向量**数据库**，提供完整的数据库能力：持久化、CRUD、分布式、多租户、标量过滤

具体对比：

| 维度 | FAISS | Milvus |
|------|-------|--------|
| 持久化 | 需手动 save/load | 自动 |
| 分布式 | 不支持 | 支持（K8s） |
| 删除 | 非常麻烦 | 标准 DELETE |
| 标量过滤 | 不支持 | 支持 |
| 数据规模 | 百万级 | 十亿级 |
| 部署方式 | Python 库 | Docker/K8s |

---

### 2. Milvus 的 HNSW 索引是什么？适合什么场景？

**答：**
HNSW（Hierarchical Navigable Small World）是一种基于图的近似最近邻搜索算法。

**原理**：构建多层跳表结构的图，上层稀疏用于快速定位，下层密集用于精确搜索。搜索时从顶层开始，逐层向下导航到最近邻。

**参数**：
- `M`：每个节点的最大连接数（越大召回率越高，内存越大）
- `efConstruction`：构建时的搜索宽度（越大构建越慢，质量越高）
- `ef`：查询时的搜索宽度（越大查询越慢，召回率越高）

**适用场景**：中小规模（百万到千万级）、对召回率要求高、内存充足的场景。

**不适用**：超大规模（十亿级）或内存受限场景，应选 IVF_SQ8 或 DISKANN。

---

### 3. Milvus 的 Schema 设计要注意什么？

**答：**
1. **主键字段**：`INT64` + `auto_id=True`，让 Milvus 自动生成
2. **向量字段**：`FLOAT_VECTOR` + 指定 `dim`（必须与 Embedding 模型输出维度一致）
3. **文本字段**：`VARCHAR` + `max_length` 要够长（2048+），否则长文本会被截断
4. **元数据字段**：用于标量过滤的字段（source、category、timestamp 等）
5. **JSON 字段**：`DataType.JSON` 可存储灵活的元数据结构

## 进阶题

### 4. 什么是向量数据库的"标量过滤"？为什么重要？

**答：**
标量过滤是在向量搜索的同时，对非向量字段（标量）进行条件过滤。

**示例**：
```python
# 只在 source="tech_doc" 的文档中搜索
results = client.search(
    data=[query_vector],
    filter='source == "tech_doc"',
    limit=3,
)
```

**为什么重要**：
1. **多租户**：`filter='tenant_id == "user_123"'` 隔离不同用户数据
2. **时间范围**：`filter='timestamp > "2024-01-01"'` 只搜近期数据
3. **分类过滤**：`filter='category in ["tech", "science"]'` 限定领域
4. **混合检索**：先过滤再向量搜索，比"搜全部再过滤"高效得多

### 5. 如何选择向量索引类型？

**答：**

| 索引 | 查询速度 | 召回率 | 内存占用 | 构建速度 | 适用规模 |
|------|---------|--------|---------|---------|---------|
| FLAT | 最慢 | 100% | 最大 | 最快 | <10万 |
| IVF_FLAT | 快 | 高 | 大 | 快 | 百万级 |
| IVF_SQ8 | 快 | 中 | 小 | 快 | 千万级 |
| HNSW | 最快 | 最高 | 最大 | 慢 | 百万级 |
| DISKANN | 中 | 高 | 最小 | 慢 | 十亿级 |

**选择策略**：
- 数据量小 + 追求精确 → FLAT
- 中等规模 + 高召回 → HNSW
- 大规模 + 节省内存 → IVF_SQ8
- 超大规模 → DISKANN

---

### 6. Milvus 的 load_collection() 是做什么的？为什么搜索前必须调用？

**答：**
`load_collection()` 将 Collection 的数据从磁盘加载到内存中。


**为什么必须调用**：
- Milvus 的搜索是在**内存**中进行的（为了速度）
- 数据默认持久化在磁盘（MinIO/本地存储）
- 不 load 就搜索会报错：`collection not loaded`

**生产注意事项**：
- 内存有限时，可以只 load 需要搜索的 Collection
- 可以用 `release_collection()` 释放内存
- 分区（Partition）级别的 load/release 更精细

## 生产实践题

### 7. 生产环境 Milvus 部署架构怎么选？

**答：**

| 模式 | 架构 | 适用场景 |
|------|------|----------|
| Lite | 嵌入式，无需服务 | 本地开发、测试 |
| Standalone | 单机，含 etcd + MinIO | 小规模生产 |
| Cluster | 分布式，多节点 | 大规模生产 |

**Standalone 部署**：
```yaml
# docker-compose.yml
services:
  etcd:      # 元数据
  minio:     # 对象存储
  milvus:    # 数据库核心
```

**Cluster 部署**（Kubernetes）：
- Proxy：接入层
- QueryNode：查询节点（可水平扩展）
- DataNode：数据节点
- IndexNode：索引构建节点
- etcd + MinIO + Pulsar：基础设施

---

### 8. 如何优化 Milvus 的搜索性能？

**答：**
1. **选对索引**：HNSW 适合高召回，IVF_SQ8 适合省内存
2. **调整搜索参数**：增大 `ef`（HNSW）或 `nprobe`（IVF）提升召回率
3. **标量过滤优化**：对过滤字段创建索引
4. **分区（Partition）**：按时间/类别分区，减少搜索范围
5. **资源分配**：给 Milvus 足够的内存和 CPU
6. **批量搜索**：一次搜多个向量比多次搜一个高效

### 9. langchain-milvus 的已知问题是什么？如何解决？

**答：**
**问题**：langchain-milvus 0.3.x 与 pymilvus 3.x 存在兼容性问题。langchain-milvus 内部用 `MilvusClient` 建立连接，但后续操作用旧的 `Collection` API（需要 `connections.connect()`），导致 `ConnectionNotExistException`。

**解决方案**：
1. **手写 VectorStore 适配器**（推荐）：直接用 `MilvusClient` API，绕过兼容性问题
2. **降级 pymilvus**：用 pymilvus 2.x + langchain-milvus 0.2.x
3. **等待官方修复**：langchain-milvus 后续版本应该会修复

**手写适配器的核心**：只需实现 `from_texts()` 和 `similarity_search()` 两个方法。
