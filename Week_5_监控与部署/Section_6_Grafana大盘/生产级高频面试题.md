# Week 5 Section 6: Grafana 监控大盘 — 生产级高频面试题

## 基础题

### Q1: Grafana 和 Prometheus 的分工是什么？为什么要把它们分开？

**Grafana** 负责展示（可视化），**Prometheus** 负责采集和存储指标。

分离的原因：
- 职责单一：Prometheus 专注做时序数据库，Grafana 专注做图表
- 可替换：你可以用 Grafana 连接 InfluxDB、ClickHouse、CloudWatch，不绑定 Prometheus
- 扩展性：一个 Grafana 可以对接多个 Prometheus 实例，适合多服务多环境

### Q2: Counter、Histogram、Gauge 的区别？什么时候用哪个？

| 类型 | 特点 | 使用场景 |
|------|------|----------|
| Counter | 只增不减 | 请求总数、错误总数、订单总数 |
| Histogram | 分桶统计分布 | 请求耗时 P95/P99、响应大小分布 |
| Gauge | 可增可减 | 当前在线人数、CPU 使用率、队列长度 |

### Q3: Grafana Provisioning 是什么？有什么好处？

Provisioning 是 Grafana 的自动导入机制，启动时自动创建 DataSource 和 Dashboard。

好处：
- 无需手动在 UI 中点"添加数据源"、"导入 JSON"
- 配置可版本化管理（Git 仓库）
- 新环境启动即可用，适合 CI/CD 和 Docker 部署

### Q4: Histogram 的 bucket 应该怎么设置？

原则：覆盖实际耗时的 95% 范围，在关键区域加密。

比如接口耗时通常在 0.01s~2s 之间：
```python
buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.0]
```

- 0.01~0.1 加密：正常响应集中在低延迟区域
- 0.1~1.0 稀疏：过渡区域
- 1.0~2.0 兜底：异常慢请求

## 进阶题

### Q5: P95 耗时是怎么算出来的？为什么不是精确值？

Prometheus 的 Histogram 是**分桶统计**，不是记录每个请求的精确耗时。

P95 计算的原理：

1. 每个 bucket 记录落入该区间的请求数
2. `histogram_quantile(0.95, ...)` 估算：先找到第 95% 的请求落在哪个桶，再用线性插值计算

所以 P95 是估算值，不是精确值。bucket 越密，估算越准。

### Q6: 线上服务突然 5xx 暴增，你怎么用 Grafana 快速定位？

三步定位法：

**第一步：看整体**
- 打开大盘，看 5xx 错误曲线
- 确认是某条路径还是所有接口

**第二步：看关联指标**
- 请求量是否暴增（流量突增导致过载）
- P95 耗时是否变长（慢请求堆积导致超时）
- CPU/内存是否异常（资源瓶颈）

**第三步：看时间窗口**
- 对比 24 小时前的同期曲线
- 如果是刚发布，回滚确认

### Q7: Grafana 大盘的三个核心 Panel 分别用什么 PromQL？

**请求量面板**（Counter + rate）
```promql
sum by (path, status) (rate(demo_http_requests_total[1m]))
```

**错误量面板**（Counter + rate + 正则过滤）
```promql
sum by (path) (rate(demo_http_requests_total{status=~"5.."}[1m]))
```

**P95 耗时面板**（Histogram + quantile）
```promql
histogram_quantile(0.95, sum by (le, path) (rate(demo_http_request_duration_seconds_bucket[1m])))
```

### Q8: 为什么 Grafana 大盘要用 `rate()` 而不是直接用 Counter？

Counter 是累积值，直接画出来是一条不断上升的直线，看不出趋势。

`rate` 算的是**每秒变化率**，把累积值变成流量曲线，能看出：
- 请求量是涨了还是跌了
- 有没有异常尖刺

### Q9: 什么是 `rate()` 和 `irate()` 的区别？

| 函数 | 行为 | 适用场景 |
|------|------|----------|
| `rate[1m]` | 取 1 分钟的平均每秒增长率 | 平滑曲线，适合长期趋势 |
| `irate[1m]` | 取最后两个样本的瞬时增长率 | 敏感曲线，适合捕捉瞬时尖刺 |

生产环境大盘默认用 `rate`，调优时用 `irate` 辅助。

## 实战题

### Q10: 写一个 FastAPI 中间件，给所有接口自动统计请求量和耗时

```python
from fastapi import Request
from prometheus_client import Counter, Histogram
import time

http_requests_total = Counter("http_requests_total", "...", ["method", "path", "status"])
http_request_duration = Histogram("http_request_duration_seconds", "...", ["method", "path"])

@app.middleware("http")
async def metrics_middleware(request: Request, call_next):
    start = time.perf_counter()
    response = await call_next(request)
    cost_seconds = time.perf_counter() - start
    http_requests_total.labels(request.method, request.url.path, str(response.status_code)).inc()
    http_request_duration.labels(request.method, request.url.path).observe(cost_seconds)
    return response
```

### Q11: 如果 Grafana 大盘显示接口 P95 从 100ms 涨到 800ms，你排查步骤是什么？

1. 用 `rate` 确认请求量有没有变化（流量突增）
2. 看错误率是否有同步上升（慢请求导致超时）
3. 查看数据库慢查询日志（SQL 变慢拖慢接口）
4. 查看外部依赖（调用的下游服务变慢）
5. 查看资源指标（CPU/内存/连接池是否打满）
6. 对比最近一次代码发布的时间点

### Q12: 能否用 Grafana 监控非 HTTP 服务？

可以。Grafana 不关心数据类型，只要 Prometheus 能抓取到指标就可以。

常见场景：
- Celery 任务队列：任务数量、成功率、执行耗时
- 数据库连接池：活跃连接数、等待队列长度
- 缓存命中率：Redis/Memcached 的命中率
- 消息队列：RabbitMQ/Kafka 的积压量
