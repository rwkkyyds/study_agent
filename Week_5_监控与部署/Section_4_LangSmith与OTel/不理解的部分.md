# 第5周 Section_4：不理解的部分记录

## 问题1：LangSmith 是做什么的？demo1 的代码流程是什么意思？

### 通俗解释

LangSmith 不要先想成框架，可以先把它理解成 **AI 应用的行车记录仪**。

普通日志只能告诉你“程序运行了、回答出来了、某一步可能报错了”。LangSmith 更想告诉你：

- 用户问了什么
- 系统检索了哪些资料
- 拼出来的 Prompt 长什么样
- 模型拿到了什么输入
- 模型返回了什么输出
- 中间每一步有没有慢、错、空结果

所以它不是用来“让模型更聪明”的，而是用来 **看清楚 AI 应用到底是怎么回答出这个结果的**。

`demo1_langsmith_trace.py` 可以看成一个迷你 RAG 问答系统：

```text
用户问题：LangSmith 能观察什么？
        ↓
answer_question 总负责人
        ↓
retrieve_context 去资料库找相关资料
        ↓
build_prompt 把资料和问题拼成 Prompt
        ↓
fake_llm_call 模拟大模型回答
        ↓
返回最终答案
```

### 配套示例代码

```python
contexts = retrieve_context(request.question)
prompt = build_prompt(request.question, contexts)
answer = fake_llm_call(prompt)
```

这三行就是整条 AI 链路。`@traceable` 的意思是：这个函数很关键，请 LangSmith 帮我记录它干了什么。

```python
@traceable(name="retrieve_context", run_type="retriever")
def retrieve_context(question: str):
    ...
```

### 易错点总结

- LangSmith 不是模型本身，它是观察和调试 AI 应用链路的工具。
- 没有 `LANGSMITH_API_KEY` 时，本 demo 只走本地演示，不会上报到 LangSmith 平台。
- `answer_question()` 是总流程，`retrieve_context()`、`build_prompt()`、`fake_llm_call()` 是子步骤。

## 问题2：demo2 里的 trace、span、attribute、event 是什么意思？

### 通俗解释

OpenTelemetry 可以先理解成：**给程序每个关键步骤装秒表，再贴几张标签**。

`trace` 是一次完整请求，`span` 是请求中的一个子步骤。

```text
trace: rag_request
  ├── span: retrieve_documents
  └── span: generate_answer
```

一句话记住：

```text
trace 是整趟旅程，span 是旅程里的每一站。
```

`attribute` 是贴在步骤上的标签，比如问题长度、检索到几条资料、模型输出多长。`event` 是这个步骤里发生的重要时间点，比如请求收到、请求完成。

### 配套示例代码

```python
with local_span("rag_request"):
    logger.info("attribute app.query_length=%s", len(query))
    logger.info("event request.received")

    with local_span("retrieve_documents"):
        docs = retrieve_documents(query)

    with local_span("generate_answer"):
        answer = generate_answer(query, docs)
```

这里的 `local_span()` 是教学版小秒表：进入时记录开始，退出时计算耗时。

### 易错点总结

- demo2 的重点不是 RAG，而是“如何观察 RAG 每一步花了多久”。
- 当前环境没有安装 OpenTelemetry SDK，所以 demo 会走本地 fallback 输出。
- `attribute` 适合记录可排查的信息，但不要放密码、token、身份证等敏感数据。

## 问题3：demo3 的 FastAPI middleware 是什么？为什么能记录每次请求？

### 通俗解释

`demo3_fastapi_otel.py` 可以理解成：**给 FastAPI 服务门口装一个门禁记录员**。

每个请求进来时，它先登记：

- 请求方法：GET / POST
- 请求路径：/health /chat
- 开始时间

请求处理完后，它再补全：

- 状态码：200 / 422 / 500
- 耗时：cost_ms
- 是否异常

整体流程是：

```text
请求进门
  -> middleware 先记录 trace-start
  -> call_next(request) 放行到真正接口
  -> 接口返回 response
  -> middleware 记录 trace-end、状态码、耗时
  -> 返回给客户端
```

### 配套示例代码

```python
@app.middleware("http")
async def trace_http_request(request: Request, call_next) -> Response:
    span_name = f"HTTP {request.method} {request.url.path}"
    start = time.perf_counter()

    response = await call_next(request)
    cost_ms = (time.perf_counter() - start) * 1000
    logger.info("status=%s cost_ms=%.2f", response.status_code, cost_ms)
    return response
```

`call_next(request)` 可以理解成：我已经记录完入口信息了，现在把请求交给真正的接口函数处理。

### 易错点总结

- middleware 不是业务接口，它是包在所有接口前后的公共通道。
- demo3 观察的是 HTTP 请求外壳，demo2 观察的是函数内部步骤。
- 即使参数校验失败返回 422，middleware 也能记录这次请求。
