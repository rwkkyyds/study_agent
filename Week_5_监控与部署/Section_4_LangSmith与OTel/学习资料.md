# 第5周 Section_4 学习资料：把 AI 请求看清楚

## 1. 这节到底在学什么

这一节不是在学“怎么让模型回答更好”，而是在学：

```text
当一个 AI 应用回答错了、变慢了、报错了，我怎么知道问题出在哪一步？
```

真实 AI 应用不是一句 `llm.invoke()` 就结束。它通常会经历：

```text
用户问题
  -> 参数校验
  -> 查询改写
  -> 检索资料
  -> 重排资料
  -> 拼 Prompt
  -> 调用模型
  -> 解析输出
  -> 返回结果
```

如果没有链路追踪，你只能猜。可观测性的目标就是：少猜，多看证据。

## 2. 三个 demo 分别看什么

### demo1：LangSmith 看 AI 链路

它像 AI 应用的行车记录仪，适合看：

- 用户问题
- Prompt
- 检索上下文
- 模型输入输出
- Agent 工具调用

适合回答：

```text
这个 AI 答案到底是怎么来的？
```

### demo2：OpenTelemetry 看函数步骤

它像给代码步骤装秒表，适合看：

- 检索花了多久
- 模型调用花了多久
- 哪个子步骤报错
- 每一步带了哪些标签

适合回答：

```text
这次请求到底慢在哪一步？
```

### demo3：FastAPI middleware 看请求入口

它像服务门口的记录员，适合看：

- 请求路径
- 请求方法
- 状态码
- 总耗时
- 是否异常

适合回答：

```text
接口整体是否健康？哪个接口慢？哪个接口报错多？
```

## 3. 这几个词怎么记

```text
trace：一次完整请求
span：请求里的一个步骤
attribute：贴在步骤上的标签
event：步骤里发生的重要时间点
middleware：FastAPI 请求进出接口前后的公共通道
```

生活化理解：

```text
trace = 一单外卖
span = 接单、备餐、骑手取餐、配送
attribute = 店铺名、距离、餐品数量
event = 已接单、已出餐、已送达
middleware = 小区门口保安，所有外卖进出都要经过它
```

## 4. LangSmith 和 OpenTelemetry 怎么分工

```text
LangSmith：看 AI 内部链路
OpenTelemetry：看系统运行链路
```

更具体一点：

| 场景 | 更适合 |
|------|--------|
| Prompt 拼错了 | LangSmith |
| 检索上下文不相关 | LangSmith |
| Agent 工具调用顺序混乱 | LangSmith |
| HTTP 接口变慢 | OpenTelemetry |
| 数据库查询慢 | OpenTelemetry |
| 多服务调用链路排查 | OpenTelemetry |

生产项目里两者不是二选一，经常一起用。

## 5. 一次 RAG 请求应该怎么观察

建议观察结构：

```text
HTTP POST /chat
  ├── validate_request
  ├── rewrite_query
  ├── retrieve_documents
  ├── rerank_documents
  ├── build_prompt
  ├── call_llm
  └── parse_response
```

排查思路：

- 答案不准：优先看检索上下文和 Prompt。
- 接口很慢：优先看每个 span 的耗时。
- 偶发报错：看异常发生在哪个 span。
- 成本太高：看模型输入输出长度。

## 6. 学完这一节要能说出来的话

你可以这样总结：

```text
LangSmith 帮我看清 AI 应用内部是怎么生成答案的；
OpenTelemetry 帮我看清系统请求链路是怎么执行的。
trace 表示一次完整请求，span 表示请求里的一个子步骤。
FastAPI middleware 可以统一记录每个接口的状态码和耗时。
```

这段话能说顺，说明这一节主线已经通了。

@app.get("/slow")
