# 第5周 Section_5 学习笔记：Prometheus 监控

## 1. 本节主线

Prometheus 的核心价值是让服务把运行状态暴露出来。

```text
FastAPI 服务
  -> 统计请求、错误、耗时、业务事件
  -> 暴露 /metrics
  -> Prometheus 定时抓取
  -> Grafana 展示趋势
```

本节先解决 `/metrics` 和指标类型，Grafana 下一节再讲。

## 2. 什么时候该用 Prometheus

只要服务准备长期运行，就应该考虑指标监控。

常见场景：

- 接口上线后看请求量和错误率
- AI 服务看 LLM 调用耗时
- RAG 服务看检索耗时和命中文档数
- 任务系统看队列长度和失败任务数
- 管理后台看业务动作发生次数

## 3. 三类核心指标

### Counter：累计次数

Counter 只增不减，适合：

- 请求总数
- 错误总数
- 登录次数
- Agent 工具调用次数

### Gauge：当前状态

Gauge 可增可减，适合：

- 当前在线用户数
- 当前队列长度
- 当前运行任务数
- 当前内存占用

### Histogram：耗时分布

Histogram 用桶统计耗时，适合：

- HTTP 接口耗时
- LLM 调用耗时
- 数据库查询耗时
- RAG 检索耗时

## 4. 三个 demo 的意义

- `demo1_metrics_plain_text.py`：先看懂 Prometheus 文本格式。
- `demo2_fastapi_metrics_middleware.py`：用 middleware 自动统计接口请求。
- `demo3_prometheus_client_real.py`：使用真实 `prometheus-client` 包生成标准指标。

真实项目里优先使用 `prometheus-client`，不要自己长期维护手写指标格式。

## 5. /metrics 是什么

`/metrics` 是给 Prometheus 抓取的接口，不是给普通用户看的业务页面。

它返回的是类似这样的文本：

```text
# HELP demo_requests_total Total demo requests.
# TYPE demo_requests_total counter
demo_requests_total{endpoint="/chat",status="200"} 3.0
```

Prometheus 会定时请求这个接口，把指标存进自己的时间序列数据库。

## 6. labels 要谨慎使用

label 是指标的维度，比如：

```text
endpoint="/chat"
status="200"
```

好用，但不能乱放。

不要把这些放进 label：

- user_id
- request_id
- 完整用户问题
- token
- 手机号

这些值太分散或太敏感，会导致监控系统压力变大，甚至泄露数据。

## 7. Prometheus 和上一节 OTel 的区别

```text
OpenTelemetry trace：看一次请求经过了哪些步骤
Prometheus metrics：看一段时间里整体情况怎么样
```

简单判断：

- 想看“这一次请求为什么慢”：看 trace
- 想看“最近 5 分钟接口整体是不是变慢”：看 metrics

## 8. 本节最小复盘

你需要掌握：

1. Prometheus 通过 `/metrics` 拉取指标。
2. Counter 记录累计次数。
3. Gauge 记录当前状态。
4. Histogram 记录耗时分布。
5. FastAPI middleware 适合统一统计 HTTP 请求。
